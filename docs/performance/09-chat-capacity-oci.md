# 채팅 동시 접속 — OCI 실측 (진행 중)

> **이 문서는 측정하면서 쓴다.** 확정된 것과 아직 못 믿는 것을 나눠 적는다.
> 측정 위치를 정한 근거는 [`08-network-floor-oci.md`](08-network-floor-oci.md) 에 있다.

---

## 0. 무엇을 물었나

> **"이 하드웨어에서 채팅이 몇 명까지 되는가."**

노트북에서는 답할 수 없는 질문이다. 그래서 **앱을 OCI 에, 부하 생성기를 노트북에** 두었다.

---

## 1. 측정 구성

```
앱          OCI  oci-aarch64-1  2 OCPU / 12GB (aarch64, Rocky 9.6)
            perf 프로파일, 전용 MySQL(3307) · Redis(6380)
            운영 앱은 측정 창 동안 정지 — 2코어를 나눠 쓰지 않기 위해
k6          노트북에서 네트워크 너머
네트워크     p50 15ms / p95 28ms (HTTP 왕복 기준)
```

### 배경 부하를 먼저 치웠다

이 서버에는 다른 프로젝트 컨테이너가 11개 돌고 있었다.

```
치우기 전   load average 1.43   CPU idle 42.9%
치운 뒤     load average 0.13   CPU idle 98.5%
```

**범인은 컨테이너 자신이 아니라 `dockerd` 였다.** `docker stats` 상 컨테이너 CPU 합은 4% 남짓인데,
`cadvisor` 가 `--docker_only=true` 로 Docker API 를 계속 폴링하면서 **일을 `dockerd` 가 대신 하고 있었다.**

> `ps` 의 `%CPU` 는 **프로세스 생존 기간 평균**이지 현재값이 아니다.
> 128일 떠 있는 `dockerd` 가 32%로 보이는 것은 "지금 32%" 가 아니라 "128일 평균 32%" 다.
> 현재값은 `top` 으로 봐야 한다. 이걸 헷갈리면 원인을 엉뚱한 데서 찾는다.

**볼륨은 지우지 않았다.** 프로메테우스 3개월치 567MB 와 Grafana 대시보드 15MB 가 그 안에 있고,
compose 파일도 그대로라 `docker compose up -d` 로 복구된다.

## 2. 워크로드 모양을 둘로 나눴다

부하 시험 하나로 "채팅 성능" 을 말할 수 없다. **모양이 다르면 무너지는 곳도 다르다.**

| | fan-out | 대칭(symmetric) |
|---|---|---|
| 누가 보내나 | 소수 발행 : 다수 구독 | **전원이 보내고 전원이 받는다** |
| 닮은 상황 | 라이브·오디오 **방송** 채팅 | 화상 **수업** 채팅 |
| 인바운드 | N 과 무관하게 고정 | **N 에 비례** |
| 아웃바운드 | N 에 비례 | **N² 에 비례** |
| EduMeet 모드 | `BROADCAST` · `AUDIO_BROADCAST` | `INTERACTIVE` |

**방송 모드가 셋이라 하나만 재면 나머지를 잘못 말하게 된다.**

fan-out 비율은 임의로 정한 것이 아니다. EMQX 같은 브로커 벤치마크가
**발행 10 : 구독 2,000** 처럼 소수 발행 : 다수 구독으로 잰다. 같은 계열이다.

## 3. 결과 — fan-out (방송형)

발행자 4명 × 20 msg/s = **80 msg/s 고정**, 구독자만 늘렸다. 60초.

| 구독자 | 발행 | 수신 | fan-out | **e2e p95** | e2e max | 연결오류 |
|---:|---:|---:|---:|---:|---:|---:|
| 200 | 4,676 | 792,458 | 169.5배 | **45 ms** | 247 ms | 0 |
| 500 | 4,660 | 1,755,866 | 376.8배 | **1,313 ms** | 7,648 ms | 0 |

### 읽는 법

**연결은 하나도 안 끊겼다. 무너진 것은 지연이다.**

```
인원 2.5배  →  전송량 2.2배  →  e2e p95 29배
```

45ms 는 "즉시" 로 느껴지고 1,313ms 는 **채팅으로 못 쓴다.**
p95 가 1.3초면 max 는 7.6초다 — 말을 걸고 8초 뒤에 뜨는 채팅은 대화가 아니다.

> **상한은 "몇 명이 붙나" 가 아니라 "몇 명까지 채팅답나" 로 결정된다.**
> 연결 수만 세면 500명도 "된다" 고 말하게 된다.

200명 구간에서 `system_cpu_usage` 가 **0.99 까지 올라갔다.** 2코어가 포화한다.
힙은 133MB 로 평온했다 — **이 구간의 병목은 메모리가 아니라 CPU 다.**

### ★ 수신 건수가 기대값에 못 미쳤다 — 갈랐다 (#145 · #159)

발행 × 구독자로 계산하면 이렇게 나와야 한다.

| 구독자 | 발행 | 기대 수신 | 실제 수신 | 비율 |
|---:|---:|---:|---:|---:|
| 200 | 4,676 | 935,200 | 792,458 | **84.7%** |
| 500 | 4,660 | 2,330,000 | 1,755,866 | **75.4%** |

섞여 있을 수 있는 것이 셋이었다 — 램프업, 집계 종료, 실제 유실.
**어느 쪽인지 모르면 지연 수치도 못 믿는다.** 늦게 온 것이 집계에서 빠졌다면 p95 는 실제보다 좋게 나온다.

**셋을 가르는 스크립트를 따로 만들어 다시 쟀다**(`k6/chat-delivery.js`).

| | 어떻게 |
|---|---|
| 램프업 | 구독자마다 **자기가 붙은 시각**을 기록하고, 그 뒤에 발행된 것만 기대값에 넣는다 |
| 집계 종료 | 발행을 끊고도 **30초를 더 받아** 그 구간 도착을 "지연 도착" 으로 따로 센다 |
| 유실 | 기대 − (제때 + 지연) |

기대 건수를 `발행 × 구독자` 로 계산하지 않는 이유는 그 식이 **"전원이 처음부터 붙어 있었다"** 를 가정하기 때문이다.

### 결과 — 유실은 0 이었다

발행 4×20/s · 발행 60초 + drain 30초.

| 구독자 | 발행 | 기대(구독 후) | 제때 도착 | 지연 도착 | **유실** | 중복 |
|---:|---:|---:|---:|---:|---:|---:|
| 200 | 3,349 | 669,800 | 668,758 (99.84%) | 1,042 (0.16%) | **0** | 0 |
| 500 | 2,106 | 1,053,000 | 717,536 (68.14%) | 335,464 (**31.86%**) | **0** | 0 |

**500명에서 31.86% 가 발행이 끝난 뒤에 도착했다.** 3절의 75.4% 가 이것이다.
60초에서 끊은 그 측정은 늦게 온 3분의 1을 못 셌다.

```
3절의 미달분  =  지연 도착
유실          =  0 건
중복          =  0 건
```

### 그래서 3절의 지연 수치는 낙관 편향이다

늦게 온 것을 못 세면 p95 는 **좋게 나온다.** 3절의 `500명 p95 1,313ms` 는 그렇게 나온 값이다.
이번 측정에서 같은 500명 구간의 e2e p95 는 **31,273ms**, 지연 도착분만 보면 **41,534ms** 였다.

### 부하 생성기를 서버 밖으로 옮겨 한 번 더 (#160)

위 표는 부하 생성기가 **같은 서버 안**이다. 밖(노트북, SSH 터널)에 두고 200명을 다시 쟀다.

| | 서버 안 | **서버 밖** |
|---|---:|---:|
| 발행 (목표 4,800) | 3,349 (**69.8%**) | 4,738 (**98.7%**) |
| 기대(구독 후) | 669,800 | 947,600 |
| 제때 도착 | 99.84% | 76.91% |
| 지연 도착 | 0.16% | **23.09%** |
| **유실** | **0** | **0** |
| 중복 | 0 | 0 |
| e2e p95 | 11,488 ms | **18,466 ms** |

**유실 0 은 양쪽에서 같다.** 전달률 결론은 생성기 위치와 무관하다.

**그런데 다른 것이 드러났다 — 같은 서버 안에서 재면 부하가 목표에 못 미친다.**

```
서버 안   목표 4,800건 중 3,349건만 발행   (69.8%)
서버 밖   목표 4,800건 중 4,738건 발행     (98.7%)
```

생성기가 2코어를 나눠 쓰느라 **애초에 덜 밀어 넣었다.** 그래서 큐가 덜 쌓였고,
그래서 제때 도착률이 99.84% 로 **좋게 나왔다.**

> **같은 서버 안에서 재면 잡음이 끼는 것이 아니라 부하가 약해진다.**
> 약한 부하에서 나온 좋은 숫자는 서버가 좋다는 뜻이 아니다.
> 밖에서 재니 목표에 도달했고, 도달하니 지연 도착이 0.16% 에서 23.09% 로 늘었다.

터널 종단(sshd)이 서버 안에 있는 것은 남는 조건이다. 측정 중 CPU 는 `21.9 us / 9.4 sy` 로
포화와는 거리가 있었다.

## 4. 결과 — 대칭 (수업형)

전원이 **분당 6건**(10초에 한 번)씩 보낸다. 60초.

| 참가자 | 발행 | 수신 | 증폭 | **연결 p95** | e2e p95 | e2e max |
|---:|---:|---:|---:|---:|---:|---:|
| 100 | 489 | 48,900 | 100배 | **415 ms** | 12 ms | 55 ms |
| 200 | 979 | 195,800 | 200배 | **713 ms** | 20 ms | 54 ms |
| 300 | 1,468 | 440,396 | 300배 | **1,313 ms** | 33 ms | 79 ms |

**증폭이 정확히 참가자 수와 같다.** 대칭에서는 정의상 그렇게 되고,
그래서 아웃바운드가 **N² 에 비례**한다 — 300명이면 발행 1,468건이 44만 건이 된다.

### fan-out 과 다른 곳이 무너진다

| | 먼저 무너지는 것 |
|---|---|
| fan-out | **e2e 지연** (45 → 1,313 ms) |
| 대칭 | **연결 수립** (415 → 1,313 ms), e2e 는 33ms 로 여유 |

이 대칭 측정은 `INTERACTIVE` 방이라 **메시지가 MySQL 에 저장된다**(`persists: true`).
DB 쓰기를 하면서도 e2e 33ms 다.

## 5. ★ 아직 못 믿는 것

**연결 수립 시간이 서버 탓인지 k6 탓인지 아직 못 갈랐다.**

k6 를 한 프로세스에서 돌리므로, 300개 소켓을 여는 데 걸린 시간이
**클라이언트 쪽 직렬화** 때문일 수 있다. 근거가 양쪽으로 있다.

- 서버 쪽 의심: 인원에 거의 정비례한다 (415 → 713 → 1,313, 3배 인원에 3.2배)
- 도구 쪽 의심: `p95` 와 `max` 가 거의 붙어 있다 (1,313 vs 1,354) —
  고정 속도로 빠지는 큐의 모양이고, 그 큐가 클라이언트에 있을 수도 있다

**가르려면** k6 를 여러 대에서 분산 실행하거나, 서버의 연결 수락 지표와 대조해야 한다. 아직 안 했다.
**그래서 이 숫자는 "연결이 인원에 비례해 느려진다" 까지만 말하고, 원인은 말하지 않는다.**

## 6. 측정 과정에서 틀렸던 것

기록해 두는 이유는 **잘못된 발견을 보고할 뻔했기** 때문이다.

### "세션이 201에서 막힌다" — 아니었다

fan-out 500명 시험 중 서버 지표가 60초 내내 `chat_sessions_active = 201` 로 보였다.
Spring Boot 의 `server.tomcat.threads.max` 기본값이 **정확히 200** 이라,
"Tomcat 스레드 상한에 걸렸다" 는 결론이 바로 나올 뻔했다.

**서버에서 다시 세어 보니 504 였다.** 201 은 내 폴링 스크립트의 아티팩트였다
(그 스크립트는 매달려서 죽기도 했다).

> 숫자가 그럴듯한 기본값과 맞아떨어질 때가 제일 위험하다.
> **설명이 먼저 떠오르면 그 설명을 의심해야 한다.**

### 죽인 줄 알았던 k6 가 살아 있었다

`k6-500` 재실행에서 `listen tcp 127.0.0.1:6565: bind: address already in use` 경고가 났다.
앞 회차 k6 가 남아 있었다는 뜻이다. **부하 생성기가 둘이면 그 회차 숫자는 못 믿는다.**
전부 정리하고 서버 세션이 0 으로 돌아온 것을 확인한 뒤 다시 쟀다.

## 7. 한계 (정직하게)

- **k6 가 한 대에서 돈다.** 클라이언트가 상한이 아니라는 증거가 아직 없다 (5절)
- **집 인터넷을 지난다.** 응답이 큰 경로에는 회선이 먼저 걸린다. 채팅은 페이로드가 작아 덜 하다
- **60초 시험이다.** 몇 시간 유지했을 때의 누수·GC 누적은 안 봤다
- **재연결을 안 봤다.** WebSocket 부하 시험의 표준 항목인데 빠져 있다
- 대칭과 fan-out 의 **인바운드 속도가 달라** 두 표를 한 축에서 비교하면 안 된다.
  비교해야 할 것은 숫자가 아니라 **무너지는 지점의 모양**이다
- ~~수신 건수가 기대값의 84.7% / 75.4% 다~~ → **갈랐다(#159). 유실 0, 중복 0.
  미달분은 전부 지연 도착이었다**(3절). 대신 그때의 지연 수치가 낙관 편향이라는 것이 새로 드러났다
- **두 지점만 쟀다.** 실사용 상한은 200명과 500명 사이에 있다는 것까지만 말할 수 있다
- **지연 판정 기준을 측정 전에 선언하지 않았다.** *"1.3초면 채팅으로 못 쓴다"* 는 결과를 보고 정한 값이라,
  다음 측정부터는 e2e p95 목표를 먼저 적고 시작한다
