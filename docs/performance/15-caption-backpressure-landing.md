# 역압 착지점을 옮기고 다시 쟀다 (#151 · #157)

> 측정 2026-08-28 · OCI aarch64 2 OCPU / 12GB

## 0. 왜 다시 쟀나

[`07`](07-chat-unbounded-queue-oom.md) 에서 무한 큐를 유계로 바꾸고 `CallerRunsPolicy` 를 걸었다.
그때 *"역압을 위로 전달한다"* 고 적었는데 **위가 어디인지는 확인하지 않았다.**
나중에 찍어 보니 자막 경로에서 그 "위" 는 **Tomcat 요청 스레드**였다
(`BackpressureLandingTest`, 실측 `http-nio-auto-1-exec-1`).

자막 발행을 전용 스레드로 갈랐다(#151). **그런데 옮긴 것만으로 "나아졌다" 고 할 수는 없다.**
옮긴 뒤를 재야 한다.

---

## 1. 측정 설계

```
k6 --> toxiproxy:18081 --[bandwidth 1KB/s]--> app:8081     느린 구독자 150명
k6 --> app:8081                                             자막 POST
k6 --> app:8081                                             REST 프로브
```

**프로브를 401 경로로 잡았다.** JWT 필터에서 끊겨 DB 도 비즈니스 로직도 안 탄다.
이 숫자가 늘었다면 원인은 하나뿐이다 — **요청 스레드를 못 받았다.**

전/후는 같은 커밋 쌍이다. `before` = `3b23b42^`, `after` = `3b23b42`.

## 2. 결과

구독자 150명을 1KB/s 로 조여 아웃바운드를 포화시키고, 자막 45/s 를 밀어 넣으면서
자막과 무관한 REST 프로브(401 경로)를 10/s 로 같이 쳤다. 90초.

| | 고치기 전 | 고친 뒤 |
|---|---:|---:|
| REST 프로브 p50 | 2.99 ms | 2.83 ms |
| REST 프로브 p95 | 25.11 ms | 12.49 ms |
| **REST 프로브 p99** | **2,926 ms** | **46.20 ms** |
| REST 프로브 최대 | 3,784.69 ms | 249.87 ms |
| **500ms 를 넘긴 프로브** | **22 / 886 건 (2.48%)** | **0 / 901 건** |
| 자막 POST p95 | 9,767.07 ms | 20.01 ms |
| 자막 POST 최대 | 30,001.34 ms | 257.23 ms |
| 자막 실패(타임아웃) | 69 건 | **0 건** |
| **자막 전송 (목표 4,050)** | 3,582 (**88.4%**) | 4,050 (**100.0%**) |
| 버린 자막 | — | **1,094 건** |

**자막과 아무 상관 없는 401 응답이 886건 중 22건에서 0.5초를 넘겼다.**
그것이 "REST API 전체를 막는다" 의 실체다.

### ★ p95 로 보면 이 장애가 거의 안 보인다

25.11ms 와 12.49ms 는 두 배지만 눈에 안 띈다. **p99 는 2,926ms 와 46ms 로 64배**다.

```
p50   2.99 ms  ->  2.83 ms      차이 없음
p95  25.11 ms  -> 12.49 ms      두 배
p99   2,926 ms ->    46 ms      64배
max   3,785 ms ->   250 ms      15배
```

역압은 **모든 요청을 고르게 느리게 하지 않는다.** 큐가 꽉 찬 순간에 마침 들어온 요청만
전송을 떠안는다. 그래서 분포가 아니라 **꼬리에서만** 보이고,
p95 를 대표값으로 쓰면 *"별 차이 없다"* 는 결론이 나온다.

> **꼬리로 나타나는 장애는 꼬리로 봐야 한다.**
> 이 표에서 p95 만 남기면 이 문서의 결론이 뒤집힌다.

### 대가

고친 뒤 **자막 1,094건을 버렸다.** 그것이 이 설계의 값이다.
버린 것은 `caption.broadcast.dropped` 로 세고 0을 넘으면 경보한다.
전사는 [`13`](13-caption-archive-transcript.md) 의 저장 큐가 들고 있어 다시보기와 요약 입력은 남는다.

> 고치기 전에는 **아무것도 안 버리는 대신 자막 POST 가 최대 30초 걸리고 69건이 타임아웃했다.**
> 1,094건을 버리고 그것을 되찾은 것이다.

### 부하 생성기가 원인이 아니었다

고친 뒤 회차가 **목표 45/s 를 100.0% 달성**했다(4,050 / 4,050).
같은 서버에서 같은 k6 로 도달한다.

**그래서 고치기 전 회차의 88.4% 는 측정 결함이 아니라 증상이다.**
자막 POST 자체가 최대 30초 걸리고 69건이 타임아웃했으니 못 보낸 것이다.
전에 이 문서가 *"2코어를 나눠 써서 목표가 떨어졌다"* 고 적은 것은 **원인을 잘못 짚은 것**이었다.

### 두 번째 회차 — 방향은 같고 크기는 다르다 (#159)

같은 조건으로 한 번 더 쟀다.

| | 고치기 전 | 고친 뒤 |
|---|---:|---:|
| REST 프로브 p50 | 2.77 ms | 2.69 ms |
| REST 프로브 p95 | 14.66 ms | 12.63 ms |
| **REST 프로브 p99** | **491.63 ms** | **35.48 ms** |
| REST 프로브 최대 | 1,408.17 ms | 126.62 ms |
| **500ms 를 넘긴 프로브** | **9 / 898 건 (1.00%)** | **0 / 901 건** |
| 자막 POST p95 | 3,182.17 ms | 17.60 ms |
| 자막 POST p99 | 20,011.39 ms | 54.17 ms |
| 자막 전송 (목표 4,050) | 3,828 (94.5%) | 4,051 (**100.0%**) |
| 버린 자막 | — | 1,521 건 |

두 회차를 나란히 놓으면 이렇다.

| | 1회차 | 2회차 |
|---|---:|---:|
| 고치기 전 REST p99 | 2,926 ms | 492 ms |
| 고친 뒤 REST p99 | 46 ms | 35 ms |
| 고치기 전 500ms 초과 | 2.48% | 1.00% |
| 고친 뒤 500ms 초과 | 0% | 0% |
| 고치기 전 자막 달성률 | 88.4% | 94.5% |
| 고친 뒤 자막 달성률 | 100% | 100% |

**방향은 두 번 다 같고 크기는 6배까지 벌어진다.**
고치기 전 쪽이 흔들리는 이유는 그 상태의 지연이 **큐가 꽉 찬 순간에 요청이 들어왔는가**에 달려 있어서다.
운(타이밍)이 섞이는 구간이므로 **한 회차 숫자를 대표값으로 쓰면 안 된다.**

고친 뒤는 두 회차 모두 **500ms 초과 0건 · 자막 달성률 100%** 로 흔들리지 않는다.
**이 측정이 말할 수 있는 것은 "고치기 전에는 회차마다 다르게 나쁘고, 고친 뒤에는 일정하게 괜찮다" 이다.**

## 3. 못 만든 조건에서 나온 "차이 없음" 은 결론이 아니다

처음에는 구독자를 **5KB/s** 로 조이고 쟀다. 결과가 이랬다.

| | 고치기 전 | 고친 뒤 |
|---|---:|---:|
| REST 프로브 p95 | 15.69 ms | 16.64 ms |
| 자막 POST p95 | 22.57 ms | 19.87 ms |

**차이가 잡음 수준이다.** 그대로 적었으면 *"고쳐도 안 나아졌다"* 가 됐을 것이다.

원인은 부하 쪽이었다. 목표 45/s 인데 실제로는 **15.9/s** 밖에 안 나갔고,
그 정도면 구독자 150명 × 5KB/s = 750KB/s 가 감당하는 양이라 **아웃바운드가 포화되지 않았다.**
포화가 없으면 `CallerRunsPolicy` 가 발동하지 않고, 발동하지 않으면 착지점이 어디든 상관없다.

1KB/s 로 5배 더 조이고서야 조건이 성립했다.

## 4. 세션 안 발행 순서 (#157 · #158)

아웃바운드 채널은 스레드 풀이라 **같은 세션으로 가는 메시지의 순서가 보장되지 않는다.**
`setPreservePublishOrder(true)` 로 켤 수 있지만 세션마다 직렬화된다.
**켤지 말지를 재고 정하려고 상수를 설정으로 뺐다.**

### 4-1. 켜는 비용

구독자 150명 · 발행 4×20/s · 60초.

| | 끔(현재) | 켬 |
|---|---:|---:|
| 발행 | 4,232 | 4,218 |
| 수신 | 529,281 | 526,493 |
| fan-out | 125.1배 | 124.8배 |
| **e2e p95** | **3,070 ms** | **8,297 ms** |
| e2e 최대 | 3,886 ms | 9,852 ms |
| 연결오류 | 0 | 0 |

**처리량은 같은데 지연이 2.7배가 된다.**

### 4-2. 그런데 끄는 대가는 안 쟀었다 (#158)

위 표는 **켜는 비용**만 말한다. *"안 켜도 괜찮은가"* 는 다른 측정이다.
순서가 실제로 뒤집히는지 세는 스크립트를 따로 만들었다(`k6/chat-order.js`).

발행자마다 자기 번호를 1씩 올려 보내고, 구독자는 **발행자별로** 마지막 번호를 들고 있다가
더 작은 번호가 오면 센다. 서로 다른 발행자 사이의 순서는 애초에 보장 대상이 아니라 섞어 보지 않는다.

| 조건 | 구독자 | 발행 | e2e p95 | 순서대로 | 뒤집힘 | **뒤집힘 비율** |
|---|---:|---:|---:|---:|---:|---:|
| **끔** | 150 | 4×20/s | 3,489 ms | 92,890 | 388,661 | **80.71%** |
| **켬** | 150 | 4×20/s | 6,093 ms | 531,860 | 3,783 | **0.71%** |
| **끔** | 30 | 4×5/s | **16 ms** | 29,800 | 0 | **0.00%** |

**켠 쪽이 0.71% 로 떨어지는 것이 이 스크립트의 대조군이다.** 재려던 것을 재고 있다.

그리고 셋째 줄이 판단을 정한다.

```
e2e p95   16ms  ->  뒤집힘 0.00%   (29,800건 중 0건)
e2e p95  3.5초  ->  뒤집힘 80.71%
```

**순서는 상시로 깨지는 것이 아니라 큐가 밀릴 때만 깨진다.**
그리고 3.5초까지 밀린 시점은 **순서와 무관하게 이미 채팅으로 못 쓰는 상태**다.

### 4-3. 그래서 끈 채로 둔다 — 이유를 다시 적는다

전에는 *"켜면 2.7배라 안 켠다"* 였다. 그건 비용만 보고 대가를 안 본 문장이다.
지금은 이렇게 말할 수 있다.

> **순서가 깨지는 구간은 지연이 이미 무너진 구간과 같다.**
> 거기서 순서를 지키려고 8.3초를 내는 것보다, **애초에 밀리지 않게 하는 쪽**이 답이다.
> 밀리는 순간에는 켜 놨어도 못 쓴다.

밀리는 것을 막는 장치는 이미 있다 — 상한(`07`), 자막 전용 경로와 드롭(`2절`),
그리고 큐 점유율·fan-out 경보(`observability/rules/edumeet.yml`).

**다만 켠 쪽의 0.71% 를 0 으로 만들지 못했다.** 원인을 안 갈랐고, 그래서 이것이 이 측정의 바닥이다.
*"켜면 0"* 이 아니라 **"켜면 0.7%, 끄면 80.7%"** 로만 읽는다.

## 5. 느린 소비자 한 명은 격리되는가 (#160)

지금까지의 측정은 구독자 150명을 **전부** 1KB/s 로 조였다. 최악을 만들려던 것인데,
현실에서 흔한 모양은 그게 아니다. **정상 149명 사이에 느린 1명이 섞이는 쪽**이 훨씬 잦다.

그 조건에서 물어야 하는 것이 다르다. *"서버가 사나"* 가 아니라
**"느린 쪽만 걷히고 나머지는 멀쩡한가"** 다.

느린 쪽은 토식을 지나고 정상 쪽은 앱에 직접 붙게 갈라, 수신·지연을 따로 셌다.

| | 느린 1 + 정상 149 | 전원 150 느림 |
|---|---:|---:|
| 느린 쪽 수신 | **237** | 35,421 (연결당 236) |
| **정상 쪽 수신** | **536,998** | — |
| 정상 쪽 e2e p95 | 2,854 ms | — |
| REST 프로브 p99 | 96.20 ms | 40.40 ms |
| 500ms 넘은 프로브 | **0 / 901** | **0 / 901** |
| 자막 전송 (목표 4,050) | 4,051 (**100%**) | 4,051 (**100%**) |

**느린 한 명이 방을 끌고 내려가지 않는다.** 그 한 명은 237건만 받고 굶었지만,
나머지 149명은 536,998건을 받았고 REST 는 500ms 를 한 번도 안 넘었다.

연결당 수신이 **237 대 236** 으로 거의 같은 것도 읽을 거리다.
느린 쪽이 못 받는 양은 **토식이 정한 것**이지 서버가 차별한 결과가 아니다.

### 느린 한 명이 있는 방이 서버에는 일이 더 많다

REST p99 가 **전원 느림 40ms · 한 명만 느림 96ms** 로 뒤집혀 있다.

전원이 느리면 서버가 밀어낼 수 있는 양 자체가 막혀 **실제 작업이 줄어든다.**
한 명만 느리면 나머지 149명에게는 **전부 밀어내야** 한다.

> **"느린 소비자" 를 최악으로 놓고 재면 오히려 부하가 약해질 수 있다.**
> 최악은 전원이 느린 쪽이 아니라, **대부분 빠르고 몇이 느린** 쪽이었다.

**정상 쪽 149개 연결이 전부 닫힌 것으로 집계됐는데**, 시험 종료 때문인지
서버가 끊은 것인지는 이 시험으로 못 가른다. 끊긴 시각을 안 기록했다.

## 6. 운영 앱은 얼마나 방해했나 (#161)

*"운영 앱을 띄운 채로 쟀다"* 를 한계로 적어 뒀는데, **정지 권한이 없어 못 내렸다.**
내리는 대신 **부하 창 동안 운영 앱이 CPU 를 얼마나 가져가는지를 쟀다.**
질문은 결국 *"그게 2코어를 얼마나 먹나"* 이므로, 재면 답이 나온다.

부하 143초 동안 1초마다 두 컨테이너의 CPU 를 찍었다. 2코어이므로 200% 가 만점이다.

| | 평균 | 중앙 | 최대 |
|---|---:|---:|---:|
| 측정 앱 | 95.12% | 81.46% | **190.02%** |
| **운영 앱** | **0.48%** | 0.25% | 3.85% |

```
부하 구간에서 운영 앱이 쓴 CPU  =  2코어의 평균 0.24% · 최대 1.93%
두 앱이 쓴 것 중 운영 앱 몫      =  0.50%
```

**운영 앱은 2코어의 0.24% 를 썼다.** 측정 앱이 최대 190% 까지 올라가 두 코어를 거의
다 쓰는 동안, 운영 앱은 트래픽이 없어 사실상 놀고 있었다.

> **이 한계는 이제 "모른다" 가 아니라 "0.24% 다".**
> 내리고 다시 재도 이 측정의 숫자는 유의미하게 안 바뀐다.
> 반대로 **부하 생성기는 같은 서버 안에서 목표의 69.8% 밖에 못 밀어 넣었다**(`09` 문서).
> 방해한 것은 운영 앱이 아니라 **부하 생성기 자신**이었다.
