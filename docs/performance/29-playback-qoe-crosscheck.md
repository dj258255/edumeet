# 29. 시청 품질을 모았다 — 그 숫자가 맞는지 먼저 쟀다 (#197)

> 측정 2026-09-23 · 운영(studywithtymee.com) · 합성 방송 1 + 헤드리스 Chromium 시청자 5~20
> 부하 생성기는 **서버 밖**(노트북)이다. 운영 서버의 다른 컨테이너는 측정 직전 CPU 0.00%

[#193](28-latency-knobs.md) 에서 지연을 1.51초까지 줄일 수 있다는 것을 재고도 안 바꿨다.
대가인 재생 끊김을 잴 수단이 없었다. 그래서 수단을 만들었다(#208) —
시청자 브라우저가 30초마다 끊김 시간·횟수·첫 화면 시간을 서버로 보낸다.

**그 숫자로 결정하기 전에, 그 숫자가 맞는지부터 쟀다.**

---

## 1. 세 지점을 대조한다

```
① 정답     브라우저 안에서 앱과 독립적으로 센 끊김
② 보낸 값  앱이 서버로 보낸 보고 본문
③ 받은 값  서버가 기록한 값 (Loki 세션 로그)
```

①≠② 면 앱의 계측이 틀렸고, ②≠③ 이면 전송·검증에서 빠졌다.

**정답은 앱 코드를 쓰지 않는다.** 같은 코드로 같은 코드를 검증하면 둘이 같이 틀려도 모른다.
그리고 정답을 **정의가 다른 둘**로 뒀다.

| 정답 | 정의 |
|---|---|
| 이벤트 기준 | 첫 `playing` 이후 `waiting` → 다음 `playing` |
| 진행 기준 | 재생 중인데 `currentTime` 이 0.25초 표본마다 0.1초 미만 전진한 구간이 0.5초 이상 — **이벤트를 안 믿는다** |

끊김은 네트워크를 조여 **일부러** 만든다 (CDP, 시청자마다).

```
0~60s 제한 없음(워밍업) · 60~120s 제한 없음 · 120~150s 800kbps(송출 2.5Mbps 보다 낮게)
150~210s 제한 없음 · 210~225s offline · 225~285s 제한 없음
```

재현: `scripts/run-qoe-crosscheck.sh` (하네스 `perf/browser/`)

## 2. 한 번 틀렸다 — 결과가 전부 0 이었다

첫 회차는 시청자 5대 모두 **끊김 0초, 보고 0건**이었다. 표만 보면 "끊김 없음" 이다.

영상이 한 번도 재생되지 않은 것이었다. 로그인 가드는 토큰만이 아니라 `localStorage.user` 도
있어야 로그인으로 보는데, 하네스는 토큰만 넣었다. 전원이 로그인 화면으로 튕겼고
`alert` 은 브라우저 자동화가 조용히 닫았다.

**하네스가 그것을 실패로 알리지 않고 정상처럼 보이는 표를 냈다는 것이 진짜 결함이었다.**
이제 첫 화면이 안 뜬 시청자가 하나라도 있거나, 시청자·방송·서버 기록 중 하나라도 없으면
"측정 조건 불성립" 으로 종료 코드 2 를 낸다. 고친 뒤 그 회차에 다시 돌려 2 가 나오는 것을 봤다.

## 3. 결과 — 보내는 쪽은 맞았다

| 회차 | 시청자 | ① 정답(이벤트) | ① 정답(진행) | ② 보낸 값 | ③ 받은 값 | 보고 누락 |
|---|---:|---:|---:|---:|---:|---:|
| r2 | 5 | 77.80초 | 76.50초 | 77.79초 | 77.79초 | 0 / 30 |
| r3 | 10 | 156.64초 | 154.75초 | 156.65초 | 156.65초 | 0 / 60 |

- **①↔② 차이 0.01초.** 앱의 계측은 독립 정답과 맞는다
- 진행 기준 정답은 1~2초 적다 — 0.25초 표본의 경계 오차다. **두 독립 정의가 1% 안에서 같은 구간을 잡았다**
- **②↔③ 0초 · 누락 0.** 서버 검증(`rejected`)에서 버려진 보고도 0
- 탭을 닫는 경우(`pagehide` + `fetch keepalive`, api. 서브도메인이라 preflight 가 붙는다)와
  SPA 안에서 떠나는 경우 모두 **마지막 보고가 15/15 도착했다.** 계획에서 가장 불확실하다고 적은 항목이다

### 첫 화면 시간은 앱이 약 0.5초 짧게 보고한다

| | 5대 중앙값 | 10대 중앙값 |
|---|---:|---:|
| 정답 (영상 요소 생성 → 첫 재생) | 1,357ms | 1,180ms |
| 앱 (플레이어 부착 → 첫 재생) | 781ms | 717ms |

앱은 부착부터 잰다. 그 앞의 **방송 주소 조회와 hls.js 동적 로딩**이 빠진다.
사용자가 체감하는 시간은 앱이 보고하는 것보다 길다. 정의의 차이이지 결함은 아니지만,
이 숫자로 판단할 때는 **하한으로 읽어야 한다.**

## 4. 결과 — 받는 쪽에 편향이 있었다

20대로 늘리자 처음으로 차이가 났다.

| 회차 | 시청자 | ② 보낸 값 | ③ 받은 값 | 보고 누락 |
|---|---:|---:|---:|---:|
| r4 | 20 | 1,047초 | 957초 (**−8.6%**) | 3 / 128 (2.3%) |

사라진 3건은 전부 **offline 구간에 보내진 보고**였고, 셋 다 `stallMs` 30,000 — **30초 전체가 끊김인 보고**였다.

#208 에서 "실패한 보고는 재전송하지 않는다 — 단순함을 택한다" 로 정했다. 그 대가를 "합계가 약간 과소할 수 있다" 로 적었다.
**약간이 아니었다.** 보고가 실패하는 때는 네트워크가 나쁠 때이고, 그때가 바로 끊김이 일어나는 때다.
**유실이 측정 대상과 상관관계를 가진다.** 보고는 2.3% 잃었는데 끊김은 8.6% 잃었다.

5대·10대에서 안 보인 이유는 운이다. 보고 시점(30초 주기)이 15초짜리 offline 구간을 비껴갔다.

### 운을 빼고 다시 쟀다 — offline 을 보고 주기보다 길게

offline 을 **35초**로 늘리면 모든 시청자의 보고 하나가 반드시 끊긴 구간에 걸린다.

| 회차 | 시청자 | ② 보낸 값 | ③ 받은 값 | 보고 누락 |
|---|---:|---:|---:|---:|
| r6 | 10 | 321.25초 | 64.27초 (**−80%**) | 20 / 70 |

**35초 장애가 서버에는 1/5 로 기록된다.** 가장 중요한 장면만 골라서 지운다.

### 고쳤다 — 실패한 보고를 버리지 않는다 (#212)

실패한 보고를 **본문 그대로** 큐에 두고 다음 주기에 먼저 보낸다. 네트워크 실패와 5xx 만 다시 보내고 4xx 는 버린다.
합치지 않은 이유는 긴 장애면 합친 간격이 서버 상한(120초)을 넘어 다시 거부되기 때문이다.

**같은 조건**(시청자 10 · offline 35초)으로 다시 쟀다.

| | 고치기 전 (r6) | 고친 뒤 (r7) |
|---|---:|---:|
| ① 정답 / ② 보낸 값 | 321.25 / 321.25초 | 314.80 / 314.82초 |
| ③ 받은 값 | 64.27초 (−80%) | **314.82초 (0%)** |
| 받지 못한 보고 | 20 | **0** |

보낸 요청 90건, 서버 기록 70줄 — 실패한 20건이 **같은 seq 로** 다시 가서 중복 없이 들어왔다.
잃는 것은 "요청은 도착했는데 응답만 잃은 경우의 중복" 이다. seq 를 보존해 뒀고 서버 중복 제거는 필요해지면 한다.

## 5. 같이 드러난 것 — 35초 끊기면 플레이어가 죽는다 (#210)

r6 · r7 두 회차 모두 **10대 전원이 복구 뒤 `error` 를 받았다.**

```
playing → waiting → playing → stalled → waiting → error(MediaError code 4) → pause
```

- 재생 위치 124초에서 멈췄고 버퍼는 158초까지 차 있었다
- **화면 오류 문구는 비어 있다.** 사용자는 멈춘 화면만 본다
- 오류 뒤의 `pause` 는 앱 계측과 정답 모두 **"사용자가 멈춤" 으로 분류해 끊김으로 세지 않는다.**
  방송이 끝날 때까지 이어지는 가장 긴 장애가 품질 지표에 한 줄도 안 남는다

15초 offline(r2~r4)에서는 안 죽었다. 어디서부터 죽는지, 왜 code 4 인지는 #210 에서 잰다.
**#198(liveSync 를 줄이는 결정)보다 먼저다** — 버퍼를 깎기 전에 죽는 조건부터 알아야 한다.

## 6. 한계

- **부하 생성기가 노트북 하나다.** 하네스 CPU 평균이 5대 34% · 10대 71% · 20대 116% 였고,
  20대에서는 시청자당 끊김이 스로틀 일정 이상으로 3배(15.7초 → 52.4초) 늘었다. **20대 회차의 끊김은 부하 생성기 몫이 섞였다.**
  다만 대조(①↔②)는 20대에서도 0.02초로 맞았다 — 끊김의 원인과 무관하게 계측은 정확하다
- 한 회차(r5)에서 시청자 10대 중 9대가 첫 재생 0.2초 뒤 `pause` 를 받고 멈췄다. **같은 조건으로 다시 돌렸을 때 재현되지 않았고 원인을 모른다.**
  그 회차는 대조에서 뺐다. 그때는 콘솔·최종 상태를 기록하지 않았다 — 지금은 한다
- 합성 방송은 ffmpeg 출력이다. 실제 발표자의 MediaRecorder 와 키프레임 간격이 다를 수 있다
- 운영의 다른 시청자가 같은 창에 있었으면 Prometheus 합계에 섞인다. 대조는 회의 번호로 거른 Loki 로 했다

## 7. 이어서 — 플레이어가 죽던 것은 Chrome 네이티브 경로였다 (#210 · #217)

5절의 "35초 끊기면 죽는다" 를 끊김 길이별로 재려고 hls.js 오류 기록을 붙였더니(#215) **기록이 0줄**이었다.
하네스의 Chromium 이 HLS 를 네이티브로 재생하고 있었다.

```
Chromium 153 (하네스) · Google Chrome 153.0.8010.53 (실제 안정판)
video.canPlayType('application/vnd.apple.mpegurl') === "maybe"
```

앱은 "네이티브 HLS = Safari" 라고 가정하고 네이티브를 먼저 골랐다. **실제 Chrome 사용자 전원이 hls.js 를 안 탔다.**
그래서 Chrome 에서 자막 정렬(#185)과 지연 설정(#193)이 꺼져 있었다. hls.js 를 먼저 고르게 고쳤다(#218).

| 끊김 | Chrome 네이티브 (고치기 전) | hls.js (#218 이후) |
|---:|---|---|
| 15초 | 3/3 영구 정지 (MediaError code 4) | **3/3 복구** |
| 35초 | 3/3 영구 정지 | **3/3 복구** |
| 60초 | 3/3 영구 정지 | **3/3 복구** |

남은 네이티브 경로(iOS Safari 등)는 오류가 나면 소스를 다시 붙이게 했다(1→15초 백오프, ±30% 지터, #219).
오류부터 다음 재생까지를 **끊김으로** 센다 — 전에는 브라우저가 내는 `pause` 때문에 "사용자 일시정지" 로 빠져 지표에서 사라졌다.
정답 계측도 같은 정의로 고쳤다. 사용자는 그 시간 멈춘 화면을 본다.

네이티브 경로를 강제로 골라(진단용 설정) 35초 끊김을 다시 쟀다.

| 네이티브 경로 · 35초 끊김 | 고치기 전 | 고친 뒤 |
|---|---|---|
| 복구 | 0/3 | **5/5** (시청자당 재부착 1회) |
| 정답 · 보낸 값 · 받은 값 | - | **187.08 · 187.08 · 187.08초** |
| 보고 | - | 40건 (전송 시도 50 · 재전송 10 · 누락 0) |

### 하네스를 노트북에서 뺐다

6절의 한계(부하 생성기가 노트북 하나)는 같은 리전의 다른 VM 에서 시청자를 띄워 없앴다.
측정 전후로 그 VM 의 다른 서비스 CPU 를 기록한다(0~2%, 영향 없음).

첫 원격 회차는 **조건이 성립하지 않았다.** 이미지 내려받기로 시청자가 방송보다 83초 늦게 붙어,
일정의 마지막 43초가 방송이 끝난 뒤였다. 그 구간의 재연결 반복·사라진 보고가 결함처럼 보였다.
대조는 이것을 못 잡았다 — 이제 방송이 어느 시청자의 일정보다 먼저 끝나면 조건 불성립으로 종료 코드 2 를 낸다.
원격 준비는 방송 시작 전에 끝내고, 방송은 시청자가 모두 끝난 뒤 내린다.

## 8. hls.js 를 먼저 고른 대가 — 첫 화면 +1초, 그중 0.5초를 되찾았다

3절의 "앱이 첫 화면을 0.5초 짧게 보고한다" 는 정의를 고쳐 없앴다(#221). 방송 중인 화면에 들어오면
**화면 진입부터**, 방송을 기다리다 들어가면 **주소를 찾은 조회부터** 잰다(기다린 시간은 플레이어 탓이 아니다).
고친 뒤 원격 시청자 10대에서 앱과 정답의 차이는 **0~34ms** 다.

그렇게 재자 #218(hls.js 우선)의 대가가 보였다. 같은 원격 환경, 시청자 10대, 첫 화면 중앙값:

| | 첫 화면 | |
|---|---:|---|
| 네이티브 | 1,625ms | 자막 정렬·지연 설정·복구 없음 |
| hls.js (#218) | 2,639ms | **+1,014ms** |
| + hls.js 로딩을 주소 조회와 겹침 (#222) | 2,243ms | 둘은 서로 기다릴 이유가 없었다 |
| + 첫 조각을 미디어 소스보다 먼저 (#223) | 2,116 · 2,173ms | 두 회차 |

**남은 약 0.5초는 hls.js 가 TS 조각을 fMP4 로 바꾸는 일이다.** 서버가 처음부터 fMP4 조각을 만들면 없어질 수 있다.
조각 형식은 #198(liveSync·조각 길이)과 같은 축이라 그 실험에서 함께 잰다.

| | 얻는 것 | 잃는 것 |
|---|---|---|
| hls.js 우선 | Chrome 에서 자막 화면 정렬 · 지연 설정 · 끊김 뒤 복구(15·35·60초 전부) | 첫 화면 약 +0.5초 (최적화 후) |

자막이 곧 내용인 사용자에게 **자막이 화면보다 4~6초 앞서는 것(#185)과 0.5초 늦게 시작하는 것**은 무게가 다르다. 앞쪽을 택했다.
