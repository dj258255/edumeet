# WebSocket 이 프록시 뒤에서 60초에 끊긴다 — 실측 (#88)

> **같은 코드, 같은 부하, 같은 경로.** 바뀐 것은 nginx 설정 한 줄이다.

---

## 결과

경로: 노트북 → Cloudflare → nginx → Spring. 조용한 연결 3개를 90초 유지.

| `proxy_read_timeout` | 유지 시간 | 조기 종료 |
|---|---:|---:|
| **60s** (nginx 기본값) | **60.9초** | **3 / 3** |
| **3600s** (설정한 값) | **90.1초** | **0 / 3** |

**60.9초**가 기본값 60초 + 왕복 지연과 정확히 맞는다.

---

## 왜 이 함정이 오래 사는가

### 1. 에러 로그가 안 남는다

nginx 는 이것을 **정상 종료**로 처리한다. `error.log` 에 아무것도 없다.
서버 쪽에서는 클라이언트가 나간 것으로 보이고, 클라이언트 쪽에서는 서버가 끊은 것으로 보인다.
**양쪽 다 상대를 탓하는 모양**이 된다.

### 2. 개발 중에는 안 보인다

60초 안에 새로고침하니까. 실제 수업이 시작돼야 드러난다.

### 3. 트래픽이 있으면 가려진다

`proxy_read_timeout` 은 **업스트림에서 데이터가 올 때마다 갱신**된다.
채팅이 활발하면 절대 안 걸린다. **조용할 때만 걸린다.**

> 그래서 이 시험은 **일부러 조용한 연결**을 만든다.
> 구독만 하고 아무것도 보내지 않는다. 부하를 걸면 이 버그는 사라진다 —
> **부하 시험으로는 못 잡는 종류다.**

### 4. 증상이 "가끔"이다

1분 넘게 조용한 구간이 있어야 걸리므로, 재현이 산발적이다.
`가끔 끊겨요` 로 보고되고 재현이 안 돼 닫히기 쉽다.

## 왜 3600초인가

| 후보 | 판단 |
|---|---|
| 애플리케이션 하트비트 | **본래 해법.** STOMP `heart-beat` 를 켜면 짧은 타임아웃도 안전하다. 다만 지금 클라이언트가 `0,0` 으로 붙는다 |
| `proxy_read_timeout 0` (무제한) | 죽은 연결을 영원히 잡는다. 파일 디스크립터가 샌다 |
| **3600s** | **채택.** 한 시간이면 수업 한 회차를 덮는다. 죽은 연결도 한 시간이면 정리된다 |

**하트비트를 켜는 것이 더 나은 해법이다.** 그때는 이 값을 60초로 되돌려도 된다.
지금 3600초는 **클라이언트가 하트비트를 안 보내는 상태에 맞춘 값**이고, 그 사실을 여기 적어 둔다.

---

## 함께 잘못되는 나머지 둘

`proxy_read_timeout` 만 문제가 아니다. nginx 기본값 세 개가 동시에 잘못된다.

| 기본값 | 증상 |
|---|---|
| `proxy_http_version 1.0` | `Upgrade` 헤더 미전달 → **핸드셰이크가 400 으로 끝난다** |
| `proxy_read_timeout 60s` | 60초마다 끊긴다 (이 문서) |
| `proxy_buffering on` | 프레임이 버퍼에 고여 지연이 는다 |

첫 번째는 **바로 드러난다** — 아예 연결이 안 되니까.
두 번째가 제일 고약하다. **되긴 되는데 가끔 끊긴다.**

## 측정 방법

```bash
k6 run -e BASE_URL=wss://api.studywithtymee.com -e TOKEN=... \
       -e MEETING_ID=2 -e DURATION_SEC=90 k6/ws-longevity.js
```

`ws_survived_ms` 가 목표 시간에 가까우면 유지된 것이고,
60초 언저리에서 멈추면 프록시가 끊은 것이다.

## 한계

- **Cloudflare 도 자체 타임아웃이 있다.** 이 측정은 CF+nginx 를 함께 지난 값이라
  60.9초가 nginx 탓이라는 것은 **설정을 바꿔 가며 비교해서** 확인한 것이지,
  경로를 분리해서 확인한 것이 아니다
- 3개 연결로만 쟀다. 연결 수가 늘 때 달라지는지는 안 봤다
- 90초까지만 봤다. 3600초를 실제로 채워 보지는 않았다
