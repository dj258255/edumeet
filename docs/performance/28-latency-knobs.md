# 28. 지연을 줄이는 손잡이를 재고, 안 돌리기로 했다 (#193)

자막-영상 어긋남을 0으로 맞춘 뒤([#185](25-caption-video-sync.md)) 남은 비용은
**사용자가 자막을 기다리는 시간**이다. 화면이 그 시점에 올 때까지 붙잡기 때문이다.

```
중앙값 4.82초 · p95 5.85초
```

교육 현장 기준이 **5초**(자막이 그 안에 와야 수업 참여가 된다)이므로
중앙값은 안에 들어오고 **p95 가 넘는다.** 줄일 값은 있다.

---

## 손잡이 둘을 재 봤다

지연은 **세그먼트 길이**와 **라이브 엣지에서 몇 세그먼트 뒤를 따라가나**에 비례한다.

| 조합 | 실제 세그먼트 | 화면 지연 |
|---|---|---|
| **A. 지금** (서버 2초 · 송출 2초 · liveSync 2) | 2.00초 | **4.82초** (p95 5.85) |
| C. **서버만** 1초 (송출 2초 그대로) | **2.00초** | **4.75초** |
| B. 서버 1초 · **송출도** 1초 · liveSync 2 | 1.00초 | 2.51초 |
| B′. 위 + liveSync 1 | 1.00초 | **1.51초** |

브라우저 없이 재려고 hls.js 의 라이브 동기화 규칙을 그대로 따라 했다 —
마지막 세그먼트 끝에서 `liveSyncDurationCount` × 타깃 길이만큼 뒤가 지금 보이는 장면이다.
같은 방송 한 번에서 liveSync 1과 2를 같이 계산한다.

### C 가 이 측정의 요점이다

**서버 설정만 1초로 줄였더니 매니페스트의 `TARGETDURATION` 이 2로 나왔다.**

서버는 브라우저가 H264 를 주면 `-c:v copy` 로 컨테이너만 바꾼다.
그러면 **키프레임에서만 자를 수 있어서** `hls_time` 은 최솟값이 되고
실제 길이는 **보내는 쪽이 정한다.**

설정만 보고 *"1초로 줄였다"* 고 적었으면 거짓말이 될 뻔했다.
**실제 세그먼트 길이를 같이 안 쟀으면 못 봤다.**

이건 [`../../docs`](.) 밖 블로그 2편에 이미 적어 둔 문장이 그대로 나온 것이다 —
*"리먹싱은 CPU 를 아끼는 대신 세그먼트 길이의 통제권을 브라우저에 넘긴다."*
그때는 원리로 적었고 이번에 숫자로 확인했다.

---

## 그런데 이 손잡이는 버퍼를 깎는다

4.82초 → 1.51초는 **버퍼가 4.8초에서 1.5초로 준다**는 뜻이다. 같은 값이다.

그래서 이 맞바꿈을 깨려고 **LL-HLS** 가 있다 —
part 를 200~500ms 로 잘라 **버퍼를 유지한 채** 엣지에 붙는다.

즉 *"설정 두 줄로 되는데 왜 LL-HLS 냐"* 는 틀린 질문이다. **얻는 것이 다르다.**

---

## 현업은 어떻게 하나

| | |
|---|---|
| 송출 | **`MediaRecorder` 를 안 쓴다.** WebRTC(WHIP)나 RTMP 를 쓴다. 이유 중 하나가 정확히 우리 문제 — 브라우저가 키프레임을 고르지 않게 내고 통제할 API 가 없다. WebRTC 면 서버가 **PLI** 로 키프레임을 요구할 수 있다 |
| 패키징 | 대개 **재인코딩**한다. 리먹싱은 CPU 를 아끼는 대신 통제권을 포기하는 선택이고, 현업은 CPU 를 쓴다 |
| 지연 | **LL-HLS** 로 지연을 세그먼트 길이에서 떼어낸다 |

### 우리 조건에서는 셋 다 막힌다

| 현업 경로 | 막히는 지점 |
|---|---|
| WebRTC 송출 + 서버 패키징 | RTP 를 받아 다시 포장하는 일 = **egress 가 하던 일 = 4코어.** 2코어다 |
| 재인코딩으로 GOP 통제 | 같은 이유. **리먹싱을 고른 것이 애초에 CPU 때문**이다 |
| LL-HLS | **blocking playlist reload** 가 필요하다. `nginx` 정적 서빙에는 요청을 붙잡고 있을 주체가 없다 |

---

## 그래서 안 바꿨다

- **어긋남은 이미 0** 이다. 남은 것은 대기 시간이고 중앙값은 기준 안이다
- 줄이려면 **버퍼를 깎아야 하는데 그 대가(재생 끊김)를 못 잰다.**
  실제 브라우저를 여러 대 띄워 중단을 세야 하는데 지금 하네스는 매니페스트만 본다
- **못 재는 것을 바꾸면 이 저장소가 지켜 온 규칙을 스스로 어긴다**

바꿀 조건은 정해 뒀다.

```
p95 가 5초를 계속 넘고, 재생 끊김을 잴 수단이 생기면  ->  liveSync 를 1로 내린다
송출을 WebRTC 로 바꿀 CPU 예산이 생기면              ->  GOP 통제를 서버가 가져온다
그 둘로도 모자라고 origin 을 세울 수 있으면           ->  LL-HLS
```

## 기각 근거를 갈아 끼웠다

`CLAUDE.md` 의 LL-HLS 기각 사유는 이랬다.

> LiveKit egress 가 TS 세그먼트라 CMAF 가 아님

**egress 를 안 쓰기로 한 순간 이 근거는 죽었다.** 지금은 ffmpeg 를 직접 부른다.
근거가 낡은 채로 남아 있으면 *"검토했다"* 가 아니라 *"한 번 보고 잊었다"* 가 된다.

실측 기반으로 바꿨다 — **설정 두 줄로 1.51초까지 가고, LL-HLS 가 더 주는 것은 그 아래인데
origin 을 새로 세워야 한다. 그리고 지금 4.82초는 기준 안이다.**
