# 32. 송출 비트레이트를 화질·판독·끊김 세 축으로 정했다 (#199)

> 측정 2026-09-24 · 화질·판독: 로컬 macOS(Apple Silicon), Playwright Chromium 과 설치된 Chrome stable
> 끊김: 운영(studywithtymee.com), 원격 시청자 10 · 합성 방송(x264) · 3Mbps + 5초 끊김 제한망 · 각 2회

재현: `perf/bitrate/run.sh <이름> 40` (녹화 없이 다시 채점: `RESCORE=1`),
끊김 축 `BITRATE_K=1500 scripts/run-qoe-crosscheck.sh`

---

## 1. 문제

표준 송출 2.5Mbps(720p30) · 데이터 절약 700kbps(360p15) 에는 근거가 적혀 있지 않았다.
강의 화면은 대부분 슬라이드라 거의 정지해 있다. 고정값은 "가장 복잡한 화면" 을 기준으로 잡는 값이라
남을 수 있고, 남는 비트레이트는 약한 네트워크 시청자의 끊김으로 돌아온다.

**한 지표로 정하지 않았다.** VMAF 는 자연 영상으로 학습됐다 - 슬라이드 글자가 읽히는지를 재는지 모른다.
그래서 글자 인식(OCR)을 나란히 두고, 끊김을 세 번째 축으로 뒀다.

## 2. 실제 인코더를 쟀다

ffmpeg x264 로 대신 인코딩하면 다른 인코더를 잰 것이다. 브라우저 `MediaRecorder` 가 **실제로 만든 파일**을 원본과 비교했다.
강의형 원본 셋(슬라이드 · 손글씨 · 움직임이 많은 카메라형)을 가짜 카메라로 넣고 300k ~ 4M 사다리로 녹화했다.

## 3. 채점기를 다섯 번 고쳤다

결과보다 이쪽이 먼저다. 틀린 채점기가 낸 숫자는 모두 "그럴듯했다".

| 순서 | 방법 | 무엇이 틀렸나 |
|---|---|---|
| 1 | 녹화 프레임과 원본을 **순번**으로 짝 | 녹화가 프레임을 떨어뜨리면 그 뒤가 전부 어긋난다. PSNR 43dB 인데 VMAF 24 |
| 2 | PSNR 이 가장 높은 **오프셋을 탐색** | 정지에 가까운 슬라이드는 어느 오프셋이나 비슷하게 맞는다. 틀린 값을 골라 슬라이드 VMAF 1% 가 전부 0 |
| 3 | 원본 프레임마다 **번호 띠**(15비트 + 패리티)를 새겨 읽음 | 패리티 한 비트는 두 비트 반전을 못 잡는다 → 읽은 번호와 재생 시각(PTS)의 차이가 일정해야 한다는 검사를 더했다 |
| 4 | 순서 검사 | 오독 값이 '이전 번호' 로 남아 정상 프레임 8개까지 버렸다 → PTS 검사를 먼저 |
| 5 | 짝 영상 생성 | 띠를 뽑은 프레임 번호와 ffprobe 의 번호가 달라 **중복이 있는 행이 전부 한 칸 밀렸다**(Chrome 슬라이드 32.7dB 고정) → 채점에 넣는 두 영상의 띠를 **다시 읽어** 번호가 전부 같아야 통과 |

**자기 검증**: 원본을 녹화본인 척 넣으면 판독 실패 0 · 탈락 0 · VMAF 97.7(정지 화면에서 libvmaf 의 상한)/99.99(카메라형).
100kbps 로 압축해도 판독 실패 0. 일부러 두 비트를 뒤집으면 PTS 검사가 1건 잡고 나머지는 정상.

5번은 표가 알려 줬다. **중복이 있는 행만 PSNR 이 비트레이트와 무관하게 일정했다** - 실제 화질이 300k ~ 4M 에서 같을 수는 없다.

## 4. 화질 · 판독

| | 요청 kbps | 실제 kbps | VMAF 평균 | 한국어 OCR (원본 천장 0.82) |
|---|---:|---:|---:|---:|
| Chrome 카메라형 | 1,000 · 1,500 · 2,500 · 4,000 | 1,005 · 1,506 · 2,502 · 4,002 | 89.0 · **93.3** · 96.0 · 97.9 | - |
| Chromium 카메라형 | 1,500 · 2,500 · 4,000 | **914** · 1,245 · 1,990 | 78.9 · 86.9 · 92.3 | - |
| 슬라이드 (둘 다) | 300 ~ 4,000 | **75 ~ 170** | 90.7 ~ 97.2 | **0.81 ~ 0.83** |
| 손글씨 (둘 다) | 300 ~ 4,000 | 75 ~ 106 | 95.9 ~ 97.4 | - |

- **슬라이드는 설정이 거의 의미가 없다.** 인코더가 요청과 무관하게 140kbps 안팎만 내고, 글자는 모든 사다리에서 원본만큼 읽힌다
- **설정은 상한이지 결과가 아니다**(#193). Chromium(Playwright) 소프트웨어 인코더는 1.5Mbps 요청에 914kbps 를 냈고, Chrome stable(macOS 하드웨어 인코더)은 요청을 거의 그대로 따랐다
- VMAF 와 OCR 은 슬라이드에서 같은 방향이 아니다(순위상관 -0.20 ~ 0.14). 모순이 아니라 **OCR 이 천장에 붙어 변화가 없어서**다

## 5. 끊김

| 합성 방송 | 실제(조각 크기) | 끊김 합 | 연쇄 끊김 | 화면 지연 p50 |
|---|---:|---:|---:|---:|
| **1.5Mbps** | 1,636 kbps | **20.3 / 6.6초** | **10 / 0** | 8.3 / 9.0초 |
| 2.5Mbps | 2,635 kbps | 329.8 / 348.7초 | 233 / 236 | 11.1 / 11.4초 |

2.5Mbps 는 3Mbps 선에 여유가 없다. 요청한 비트레이트가 실제로 나갔는지는 조각 크기로 확인했다(1.5Mbps 요청 → 조각 전체 1,636kbps, 오디오 96k·컨테이너 포함).

## 6. 결정

**표준 2.5Mbps → 1.5Mbps** (#250). 카메라형 VMAF 96.0 → 93.3 을 내주고 제한망 끊김을 94~98% 줄인다. 슬라이드 판독은 그대로.
데이터 절약(700k)은 재지 않아 그대로 두고 코드 주석에 그렇게 적었다.

## 7. 한계

- 화질 축은 **macOS Chrome 하드웨어 인코더** 기준이다. 사용자 OS·브라우저마다 인코더가 다르다(Chromium 은 같은 요청에 절반 조금 넘게 냈다)
- 끊김 축은 합성 방송(x264)이다. 끊김은 인코더가 아니라 비트레이트가 정한다고 보고 두 축을 나눴다
- 카메라형 원본은 합성(testsrc2)이다. 실제 얼굴·조명이 아니다
- 끊김은 10명 · 한 VM · 한 가지 제한망 일정이다
