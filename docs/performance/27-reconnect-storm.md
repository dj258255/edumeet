# 27. 전원이 같은 순간에 돌아온다 (#191)

무중단 배포(#180)를 넣고 나서 생긴 문제다.

전에는 **앱이 죽어야** 전원이 끊겼다. 이제는 **배포할 때마다** 옛 슬롯을 내리면서
붙어 있던 사람이 전부 동시에 끊긴다. 그리고 화면은 이렇게 돼 있었다.

```js
reconnectDelay: 3_000      // 고정. 지터도 백오프도 없다
```

**그 전원이 정확히 3초 뒤에 한꺼번에 돌아온다.**

---

## 업계에서 반복적으로 장애를 낸 모양이다

Slack 은 WebSocket 160만 개가 끊긴 뒤, 재접속 폭주가 **살아 있던 서버까지 무너뜨려**
복구에 135분이 걸렸다. Discord 도 2020년(5만 연결)과 2026년 3월에 같은 원인으로 장애를 냈다.

우리 규모에서 그렇게까지 가지는 않는다. 그래도 **원인의 모양은 같고**,
우리는 방금 그 사건을 **배포마다 일어나게** 만들었다.

---

## 측정

측정한 fan-out 상한인 **300명**에서, 전원을 동시에 끊고 정책만 바꿔 봤다.

| 300명 동시 재접속 | 고정 3초 | 흩뿌림 |
|---|---|---|
| 재접속 성공 | 300/300 | 300/300 |
| 연결 지연 중앙값 | **1,326 / 1,250ms** | **13 / 14ms** |
| 연결 지연 p95 | 1,927 / 1,654ms | 33 / 40ms |
| 연결 지연 p99 | 2,141 / 1,725ms | 65 / 138ms |
| 그동안 REST p99 | **1,144 / 1,016ms** | **479 / 337ms** |
| 실패 | 0 | 0 |

두 회차씩 쟀고, 두 번째는 **순서를 바꿔** 앞 회차의 잔열이 결과를 만들지 않았는지 확인했다.

### 접속 수만 세면 이 차이가 안 보인다

**양쪽 다 300/300 성공한다.** 다르게 나오는 것은
*얼마나 기다리는가*와 *그동안 다른 요청이 얼마나 밀리는가*다.

#164 에서 재접속을 재고 "150/150 · p95 292ms" 라고 적었다. 그건 맞는 숫자였지만
**성공률만 본 숫자**였다. 같은 실수를 한 번 더 하지 않으려고
이번에는 그 시간 동안 REST 가 얼마나 밀리는지도 같이 쟀다.

---

## 지수 백오프가 아니다

흔히 같이 나오는 말이지만 다른 것이다.

| | 무엇에 대한 것 |
|---|---|
| 지수 백오프 | **반복 실패**. 계속 안 되면 점점 덜 자주 시도한다 |
| 흩뿌림 | **첫 시도**. 여럿이 같은 순간에 오는 것을 막는다 |

여기서 폭주를 만드는 것은 재시도 횟수가 아니라 **동시에 오는 것**이다.
그래서 기준값의 1~3배 사이에서 각자 고르게 했다.

위쪽을 3배까지 연 이유는 폭이다 — 300명을 9초 창에 흩으면 초당 33명이고,
측정에서 그 정도는 연결 지연이 두 자리 ms 로 끝났다.

---

## 상수를 넣으면 안 흩어진다

라이브러리 설정에 값을 그대로 넣으면 **모듈이 로드될 때 한 번 계산된 값**이 박힌다.
그러면 한 브라우저 안에서는 매번 같고, 여러 브라우저 사이에서만 갈린다 —
정작 필요한 것은 **각 재연결마다 다른 값**이다.

getter 로 두어 읽을 때마다 계산되게 했다.

```js
get reconnectDelay() {
  return reconnectDelay()
}
```
