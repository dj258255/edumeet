# 25. 자막이 영상보다 먼저 도착한다 (#185)

이 서비스의 존재 이유는 **실시간 자막**이다. 그런데 방송 모드에서 그 자막이
화면보다 **먼저** 나가고 있었다.

```
자막   WebSocket   1초 미만
영상   HLS         6초쯤
```

말하는 입 모양과 글자가 어긋나고, 화면에서 아직 안 일어난 일이 글자로 먼저 나온다.

---

## 업계에서 알려진 문제다

**chat-to-stream sync** 라고 부른다. 표준 HLS 는 10~30초가 보통이고,
실시간 채팅·반응이 뜻을 가지려면 1초 이내여야 한다.
스포츠 중계에서 *"채팅이 중계보다 먼저 결과를 알려 주는"* 문제로 알려져 있고,
Twitch 가 LL-HLS 로 옮긴 이유 중 하나다.

**여기서는 더 나쁘다.** 청각장애 학습자에게 자막은 곁들이가 아니라 내용 그 자체다.
그 내용이 화면보다 앞서 간다.

교육 현장 기준도 있다 — 자막이 **5초** 안에 와야 학생이 수업에 참여할 수 있다는
연구가 있고, 상용 서비스는 2~3초를 목표로 한다. 우리 문제는 방향이 반대라
"늦다" 가 아니라 "앞선다" 지만, **어긋난 만큼 못 쓰는 것은 같다.**

---

## 원래 상태를 정확히 적는다

처음에 *"방송 화면에 자막이 없다"* 고 봤는데, 정확하지 않았다.
자막은 **채팅 칸에 한 줄로** 나오고 있었다. 문제는 둘이었다.

| | |
|---|---|
| 자리 | 영상이 아니라 옆 칸. 자막이 곧 내용인 사용자가 시선을 옮겨야 한다 |
| 시각 | 도착하는 대로 띄운다. **화면보다 앞선다** |

---

## 맞추려면 "지금 화면이 몇 시 것인가" 를 알아야 한다

플레이어가 아는 것은 *"재생 위치 12.3초"* 뿐이다.
그 화면이 몇 시에 촬영된 것인지는 모른다.

HLS 에는 그걸 적는 자리가 있다 — `EXT-X-PROGRAM-DATE-TIME`.
우리 매니페스트에는 없었다.

```
#EXTM3U
#EXT-X-VERSION:6
#EXT-X-TARGETDURATION:2
#EXT-X-MEDIA-SEQUENCE:14
#EXT-X-INDEPENDENT-SEGMENTS      <- 벽시계가 없다
#EXTINF:2.000000,
seg_00014.ts
```

ffmpeg 플래그 한 단어면 된다. 인코딩은 그대로고 세그먼트마다 한 줄이 늘 뿐이다.

```
delete_segments+omit_endlist+independent_segments+program_date_time
```

이게 있으면 hls.js 가 `playingDate` 로 **지금 보여 주는 장면의 시각**을 준다.
자막에는 이미 말한 시각(`spokenAt`)이 실려 있었다. 두 개를 맞추면 된다.

---

## 규칙은 한 줄, 예외가 셋

```
화면 시각이 말한 시각을 지나갈 때까지 자막을 붙잡는다.
```

붙잡기만 하면 안 되는 경우가 셋이다. 이게 이 작업의 실제 내용이다.

| | 왜 | 어떻게 |
|---|---|---|
| 화면 시각을 모른다 | Safari 기본 재생이나 매니페스트에 태그가 없는 경우. 붙잡으면 **자막이 영영 안 나온다** | 바로 내보낸다. **어긋난 자막보다 없는 자막이 훨씬 나쁘다** |
| 시각이 이상하다 | 기기 시계가 틀어져 있으면 영원히 못 따라잡는다 | 상한(12초)을 넘기면 어긋난 채로라도 내보낸다 |
| 순서 | 전사는 순서가 곧 내용이다 | 앞의 것이 아직 때가 아니면 뒤의 것도 안 내보낸다 |

규칙은 화면 코드에 섞지 않고 순수 함수로 뽑아 **시험 7개로 고정**했다.
시간과 화면 시각을 손으로 움직이는 시험이라 방송 없이도 돈다.

그리고 붙잡는 동안 *"화면보다 N초 앞 · 기다리는 중"* 을 보여 준다 —
**자막이 안 뜨는 동안 "고장" 과 "기다리는 중" 을 사용자가 구분할 수 있어야 한다.**
조용히 비어 있으면 둘이 같아 보인다.

---

## 연결을 하나 더 열지 않았다

자막을 영상 위에 띄우려면 자막 프레임이 그 화면까지 와야 한다.
쉬운 길은 화면에서 STOMP 를 하나 더 여는 것이었다.

그러면 **시청자당 연결이 두 개**가 된다. fan-off 상한을 300명으로 재 뒀는데
(`docs/performance/09-chat-capacity-oci.md`) 그러면 150명이 된다.
채팅 컴포넌트가 이미 같은 회의에 붙어 있으므로, 그 연결이 받은 자막을 위로 넘긴다.

---

## 측정

**같은 방송 한 번으로 전후를 다 쟀다.** 바꾸는 변수는 정렬 규칙 하나다 —
두 번 돌려 비교하면 방송 조건 차이가 섞인다.

| | 1회차 (120초) | 2회차 (100초) |
|---|---|---|
| 자막 전달 지연 (말한 시각 → 도착) | 0.01초 | 0.01초 |
| **전** — 도착 즉시 표시했을 때 화면보다 앞선 시간 | **중앙값 4.37초** (2.16~6.44) | **중앙값 5.88초** (2.11~6.34) |
| **후** — 화면 시각에 맞췄을 때 어긋남 | **0** | **0** |
| 상한을 넘겨 못 맞춘 것 | 0건 | 0건 |
| 표본 | 자막 59건 | 자막 49건 |

**자막은 0.01초 만에 도착하고 영상은 4~6초 뒤에 온다.** 그 차이가 그대로 어긋남이다.
한 회차로는 못 말하니 두 번 쟀고, 중앙값이 4.37초와 5.88초로 재현됐다.

폭이 2.1초에서 6.4초까지 벌어지는 이유는 **자막이 세그먼트 어디쯤에서 나왔는가**다.
세그먼트가 2초이고 플레이어가 라이브 엣지에서 2세그먼트 뒤를 따라가므로,
방금 시작한 세그먼트의 말은 6초를 기다리고 끝나가는 세그먼트의 말은 2초만 기다린다.

### 어떻게 쟀나

브라우저 없이 재려고 **hls.js 의 라이브 동기화 규칙을 그대로 따라 했다** —
마지막 세그먼트 끝에서 `liveSyncDurationCount`(앱 설정 2) × 타깃 길이만큼 뒤가
지금 보이는 장면이다. 이 가정은 앱의 `hlsPlayer.js` 에서 가져왔고 하네스에 적어 뒀다.

방송은 진짜 경로로 넣었다. 브라우저의 MediaRecorder 대신 ffmpeg 출력을 조각으로 잘라
같은 업로드 API 로 올린다 — 서버가 보는 것은 브라우저가 보내는 것과 같은 모양이다.

### 재다가 만난 것 셋

**방송이 측정 도중에 끝나면 숫자가 무한히 커진다.** 매니페스트가 멈춘 채 벽시계만
흐르므로 어긋남이 89초까지 갔다. 값이 단조롭게 커지는 것 자체가 신호였다 —
정상 구간이라면 세그먼트 길이 안에서 오르내린다.

**`Host` 를 헤더 목록으로 주면 nginx 가 400 을 준다.** 라이브러리가 URL 에서 만든
Host 와 중복된다. `host=` 로 주고 SNI 도 같이 맞춰야 한다.

**`/hls/` 는 API 호스트가 아니라 사이트 호스트에서 나간다.** api 로 부르면 401 이라
표본이 0건이었다.
