# 30. 다시보기 채팅을 강제 종료에도 잃지 않는다 (#201)

> 측정 2026-09-23 · 로컬 perf (`docker-compose.perf.yml` — 운영과 같은 MySQL 8.0, Redis 7)
> 운영 `chat_message` 는 측정 시점 0행이다. 이 문서의 숫자는 전부 perf 환경의 것이다

방송 채팅은 발행 경로 밖에서 배치로 저장한다(#61). 유실 경로가 넷인데 잰 것은 "큐 가득 참" 하나였다.
#196 에서 DB 실패 유실을 지표로 보이게 했고, 남은 것을 쟀다.

재현: `scripts/run-chat-archive-loss.sh`, `scripts/run-chat-archive-recovery.sh`,
`scripts/run-chat-archive-throughput.sh`, `scripts/run-chat-archive-redis-down.sh`

## 1. 게이트 — 잃는가, 그리고 보이는가

**세는 시점을 먼저 정했다.** 사건 뒤 발행을 멈추고 대기열이 다 빌 때까지 기다린 뒤 DB 를 센다.
처음에는 사건 직후 셌는데, 그러면 **아직 저장되지 않은 것**이 유실로 섞였다(1,378건 중 764건이 그것이었다).

DB 장애는 **기존 연결까지 멈추게** 만들었다. 처음 쓴 방식(Toxiproxy 비활성화)은 새 연결만 막아
30초 동안에도 풀에 있던 연결로 저장이 계속됐다 — 장애라고 부를 수 없었다.

| 경우 (100건/초) | 지금 방식(메모리 큐) | 보이나 |
|---|---:|---|
| DB 30초 장애 | **994 · 807건 유실** | ✅ = 큐 넘침 852·770 + 저장 실패 142·37 (정확히 일치) |
| **kill -9** | **145 · 156건 유실** | ❌ **지표 0 — 지표를 남길 주체가 사라진다** |
| 정상 종료 (슬롯 전환 신호) | 0 · 0 | - |

**가장 나쁜 것은 kill -9 다.** 잃고, 아무도 모른다. 큐 상한이 2,000 이므로 최악은 2,000건이다.

## 2. 무엇으로 바꿀까

| | 얻는 것 | 잃는 것 |
|---|---|---|
| 로컬 디스크에 먼저 쓰기 | 외부 의존 없음 | 블루·그린 슬롯이 서로의 파일을 못 읽는다. 죽은 슬롯의 기록을 누가 재생하나 |
| **Redis Stream (채택)** | 이미 쓰는 Redis. 죽은 슬롯이 못 끝낸 항목을 **살아 있는 슬롯이 가져간다**(소비 그룹) | 발행 경로에 Redis 왕복 하나. 최소 한 번 전달이라 **중복** → 메시지 ID + DB 유니크 제약 |
| Kafka · NATS | - | 이미 기각 (CLAUDE.md §6) |

## 3. 결과

| 경우 | 메모리 큐 | Redis Stream |
|---|---:|---:|
| DB 30초 장애 | 994 · 807 | **0 · 0** |
| kill -9 | 145 · 156 | **0 · 0** (재기동 뒤 9.7~11.9초 안에 회수) |
| 정상 종료 | 0 · 0 | 0 · 0 |
| 발행 p50 | 1.09~1.23ms | 1.24~1.73ms |

### 중복을 일부러 만들었다

발행 중 kill -9 를 **10번**, 저장 주기 안의 흩어진 시점에 걸었다. "저장은 끝났는데 확인(ACK) 전에 죽는" 순간이
세 번 걸려 **실제 중복 배달이 6건** 났다. DB 의 중복 행은 **0** 이다 — 유니크 제약과 사전 조회가 막았다.

## 4. 어디서 못 따라가나 — 처리량 사다리

| 목표(건/초) | 메모리 큐 저장 | Stream 저장 |
|---:|---:|---:|
| 100 | 65.5 (= 수락) | 65.0 |
| 200 | **101** (큐 넘침 2,724) | 172 |
| 400 | 100 | 369 |
| 800 | 101 | **743** |
| 1,600 | 100 | **789~819** (뒤처짐 56,000~60,000건) |

- 메모리 큐는 **초당 100건이 구조적 상한**이었다. `@Scheduled(fixedDelay=1000)` 은 이전 실행이 끝난 **뒤** 1초라,
  배치 200건을 저장하는 시간까지 합쳐 주기가 약 2초가 된다
- Stream 은 800건/초까지 따라가고 1,600 에서 꺾인다. 처음에는 200 에서 꺾였다 — 소비 루프가 주기당 배치 하나만 읽고 있었다

## 5. 재다가 고친 것 — 유실을 없애려던 장치가 유실 경로가 될 뻔했다

| | 무엇이었나 | 고친 것 |
|---|---|---|
| 근사 트리밍 | `XTRIM MAXLEN ~ 100000` 이 16만 건에서 1만 건만 지웠다 — **Redis 메모리가 발행량을 따라 무한히 큰다**(#43 의 OOM 이 Redis 로 옮겨 간다) | 정확 트리밍 → 다시 아래로 |
| 정확 트리밍 | 길이로 자르면 **아직 안 읽은·확인 안 된 항목까지 지운다** | `XTRIM MINID` — 소비 그룹이 확인을 끝낸 지점 앞만 지운다. 메모리는 삭제가 아니라 경보로 지킨다(1분 밀리면 `ChatArchiveStreamBehind`) |
| 독 메시지 | 영원히 실패하는 항목이 배치 전체를 30초마다 막는다 | 5번 넘게 배달된 항목은 격리 스트림으로 — **원본 ID 그대로** 옮겨 두 번 옮겨지지 않게 |
| 유니크 위반 | 중복 한 건이 배치 전체를 롤백한다 | 행 단위로 다시 넣으며 중복만 건너뛴다 |
| 가져가기 기준 | 30초면 DB 장애(30초 정지 + 풀 대기 10초) 중인 **살아 있는 슬롯**의 항목을 빼앗는다 | 90초 |

## 6. Redis 가 죽으면 — 서킷 브레이커를 숫자로 넣었다

CLAUDE.md §6 은 서킷 브레이커를 "LiveKit 장애가 3초에 끝남, 근거 없음" 으로 **기각**했다. 여기서는 쟀다.

| Redis 정지 중 발행 (100건/초, 각 2회차) | 차단 창 없음 | 차단 창 있음 |
|---|---:|---:|
| 발행 p50 | **1,824 · 1,829ms** | **1.2ms** |
| 1초 넘긴 발행 | 55.3 · 56.2% | 2.6% |

없으면 발행의 절반 넘게가 Redis 명령 타임아웃(2초)을 기다린다. 연속 3번 실패하면 5초 동안 Redis 를 건너뛰고 메모리 큐로 보낸다.
살아났는지는 **발행 경로가 아니라 1초 폴링이** 확인한다 — 발행이 확인하면 그 한 건이 2초를 문다.

**같은 장치를 한 곳에서는 기각하고 한 곳에서는 채택했다. 근거가 달랐다.** LiveKit 은 장애가 3초에 끝나 기다리는 비용이 작았고,
Redis 는 명령마다 2초를 물어 발행의 56% 가 막혔다.

### 시험이 잡은 것

만료 시각을 `System.nanoTime()` 으로 계산하면 음수가 나올 수 있고, 그러면 `max` 가 0 을 골라 **차단 창이 아예 열리지 않았다.**
시험(`breaker_opens_only_after_consecutive_failures`)이 잡았다. 위 표는 고친 뒤 코드로 다시 잰 값이다.

## 7. 남은 것

- Stream 저장은 초당 약 800건에서 꺾인다. `ChatMessage` 의 키 생성이 `IDENTITY` 라 Hibernate 가 INSERT 를 배치로 묶지 못한다.
  **이 한계는 다음 작업에서 잰다** (JDBC 배치 삽입)
- 운영 채팅 규모에서는 800건/초에 닿지 않는다. 방송형 채팅 상한 300명(#163)이 초당 1건씩 보내도 300건이다
