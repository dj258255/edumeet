# 20. 배포가 디스크를 채우고 있었다 (#173)

`df` 를 쳐 보고 알았다. 46GB 중 39GB, **86%**.

경보는 이미 있었다(#139). 그런데 **디스크에 대한 규칙은 하나도 없었다** —
있을 수가 없었다. Prometheus 가 긁는 것은 앱의 관리 포트뿐이라
호스트 디스크는 **물어볼 지표조차 없었다.**

---

## 무엇이 차고 있었나

```
docker system df
  Images   96개   16.19GB   회수 가능 9.249GB (57%)
```

배포할 때마다 이미지가 하나씩 쌓이고, 지우는 곳이 없었다.

```
2026-08-23   27개
2026-08-24   22개
2026-08-25    2개
2026-08-27    5개
2026-08-28   13개
2026-08-29    7개
```

이미지 하나가 945MB 지만 밑단은 공유하므로 **배포 한 번의 실제 증가분은 약 106MB** 다
(미사용 9.249GB ÷ 87개). 남은 여유 6.6GB 로는 62번, 바쁜 날 기준 **6일치**였다.

디스크가 차면 앱만 죽는 게 아니다. 같은 볼륨 위에 MySQL·Loki·Prometheus 가 전부 쓴다.
**무슨 일인지 볼 수단까지 같이 사라진다.**

---

## 치웠다

지금 것과 되돌릴 것 둘, 그리고 다른 컨테이너가 쓰는 것을 남기고 나머지를 지웠다.
지운 것도 GHCR 에 그대로 있으니 더 옛것이 필요하면 `pull` 로 가져온다.

| | 전 | 후 |
|---|---|---|
| 디스크 | 39G / 46G (**86%**) | 32G / 46G (**70%**) |
| 여유 | 6.6GB | **15GB** |
| edumeet 이미지 | 76개 | 3개 |
| 빌드 캐시 | 402MB | 0 |

---

## 다시 쌓이지 않게

한 번 치우는 것은 답이 아니다. 원인이 배포 파이프라인이므로 거기에 넣었다.

배포 스텝 **다음** 스텝이다 — 실패한 배포에서 되돌릴 이미지를 지우면 안 된다.
치우고도 90% 를 넘으면 배포를 실패시킨다. 경보는 사람이 보고 움직이는 경로지만,
배포는 자동으로 도는데 그때 디스크가 없으면 그 배포부터 깨진다.

---

## 경보를 붙였다 — 없던 지표를 만들고 나서

호스트 지표 수집기(node-exporter)를 관측 프로필에 넣고 Prometheus 가 긁게 했다.

이미 돌고 있는 Alloy 에도 같은 수집기가 들어 있다. 안 쓴 이유는
Alloy 쪽은 스크레이프가 아니라 remote_write 로 내보내는 구조라
Prometheus 에 수신기를 열어야 하기 때문이다.
12MB 짜리 컨테이너 하나를 지금까지와 똑같이 긁는 편이 움직이는 부품이 적다.

### 임계값의 근거

#139 의 규칙을 그대로 지킨다 — **근거를 못 대는 숫자는 쓰지 않는다.**

| 경보 | 임계값 | 근거 |
|---|---|---|
| `DiskTooLowToDeploy` | 여유 < 3GB | 배포는 945MB 이미지를 받는 것으로 시작한다. 받을 자리가 없으면 배포도 롤백도 실패한다 |
| `DiskFillingUp` | 4일 뒤 0 | 실측 최악 속도가 2.9GB/일(27회 × 106MB). 금요일에 울려도 월요일 전에 사람이 본다 |
| `HostMetricsMissing` | 10분 | 위 둘은 수집기가 살아 있어야 값이 나온다 |

"몇 % 찼나" 가 아니라 **"한 번 더 배포할 수 있나"** 로 묻는다.
디스크가 커지거나 이미지가 작아지면 % 는 의미가 변하지만 이 질문은 그대로다.

`predict_linear` 의 창을 6시간으로 잡은 이유는, 짧게 잡으면
배포 한 번이 만드는 계단이 추세로 읽혀 오탐이 되기 때문이다.

### 세 번째 경보가 있는 이유

`HostMetricsMissing` 은 경보에 대한 경보다.

수집기가 죽으면 디스크 질의는 **에러가 아니라 빈 결과**를 낸다.
빈 결과는 "정상" 과 구분되지 않는다 — 디스크가 100% 가 돼도 아무 일도 안 일어난다.
#139 에서 정리한 네 가지 조용한 단절 중 ②가 정확히 이것이다.

## 시험이 막고 있던 것을 놓치지 않게

`AlertMetricsExposedTest` 는 **경보 규칙이 물어보는 지표를 앱이 실제로 내는지** 대조한다.
호스트 지표를 넣으면 이 시험이 깨진다. 앱이 안 내니까 당연하다.

여기서 쉬운 길은 예외 목록을 만들어 검사를 면제하는 것이다.
그러면 **이 시험이 막으려던 구멍이 그대로 다시 열린다** — 규칙은 있는데 지표가 없고,
빈 결과는 "정상" 과 구분되지 않는다.

그래서 면제 대신 **보증하는 곳을 옮겼다.**

```
앱이 내는 지표      -> AlertMetricsExposedTest 가 /actuator/prometheus 와 대조
호스트가 내는 지표  -> scripts/verify-alerting.sh 가 실행 중인 Prometheus 에 질의
```

그리고 **옮겼는지를 시험으로 고정했다.** 호스트 규칙군의 지표가
`verify-alerting.sh` 의 확인 목록에 없으면 빨개진다.
확인용 지표를 하나 심어 실제로 그 시험만 빨개지는 것을 먼저 봤다.

## 붙이고 나서 발견한 것 — 규칙이 8월 27일에 멈춰 있었다

배포가 끝난 뒤 확인해 보니 호스트 지표가 **0개**였다. 규칙도 7개만 로드돼 있었다.

파일은 최신이었다. 컨테이너 안에서도 최신이었다. 그런데 Prometheus 는
**8월 27일에 뜬 뒤 설정을 한 번도 다시 읽지 않았다.**

규칙 파일은 볼륨 마운트다. 배포가 새 파일을 올려도 컨테이너 정의는 그대로라
compose 가 다시 만들지 않는다. #139 에서 `--web.enable-lifecycle` 을 켠 이유가
바로 이 리로드인데, **부르는 곳을 만들지 않았다.**

그동안 커밋한 규칙 9개가 파일에만 있었다. 배포는 전부 성공했다.
`docs/ops/07-declared-but-unused.md` 의 **열 번째**다.

리로드를 배포에 넣되, 부르는 것으로 끝내지 않았다 —
설정에 문법 오류가 있으면 Prometheus 는 새 설정을 버리고 옛것으로 계속 돌기 때문에
`/-/reload` 가 200 을 주는 것과 적용된 것은 다른 일이다.
**파일의 alert 개수와 `/api/v1/rules` 가 보고하는 개수를 대조**하고, 다르면 배포를 실패시킨다.

리로드 후 확인:

```
로드된 규칙                     16개 (파일과 일치)
node_filesystem_avail_bytes    시계열 1개 · 루트 여유 15.0 GB
```

## 곁가지 — 여기 오게 된 경위

원래 재려던 것은 다른 것이었다. `server.shutdown` 이 설정돼 있지 않아
**배포할 때마다 처리 중이던 요청이 끊긴다**고 보고 전후를 재려 했다.

운영 앱은 건드리지 않고 같은 이미지를 한 벌 더 띄워, 환경변수 하나만 바꿔 쟀다.

| 동시 60, 로그인 요청 | 기본 | `graceful` |
|---|---|---|
| 처리 중 끊긴 요청 | **1건** | **0건** |
| 종료에 걸린 시간 | 4.8초 | 4.6초 |

**차이가 없었다.** Tomcat 이 이미 처리 중 요청을 기다리고 있었다 —
종료에 4.8초가 걸린 것이 그 증거다. 즉시 끊었다면 1초도 안 걸린다.

측정이 없었으면 "graceful shutdown 을 적용해 요청 유실을 없앴습니다" 라고
쓸 뻔했다. 실제로는 없앨 유실이 없었다.

대신 같은 측정에서 **훨씬 큰 숫자**가 나왔다.

```
재시작 중단 시간   20.5초
```

종료 신호부터 다시 응답할 때까지 20.5초 동안 모든 요청이 거부된다.
배포의 실제 비용은 끊긴 요청 1건이 아니라 이 20.5초다.
무중단 배포는 앱을 두 벌 띄워야 하는데, 그러면 채팅 중개자가 메모리에 있어
그 창 동안 방이 갈린다. 재기 전에는 20.5초가 얼마인지도 몰랐다 —
그래서 이건 다음 작업으로 두고 숫자를 남긴다.

### 측정하다 만난 함정

**호스트 포트 매핑을 거치면 프록시가 먼저 병목이 된다.**
매 요청 새 연결을 여는 방식이라 초당 수천 개가 `docker-proxy` 로 몰렸고,
서버가 멀쩡한데 16만 건이 전부 끊긴 것으로 나왔다. 컨테이너 IP 로 직접 붙어 해결했다.

**갓 뜬 JVM 부터 재면 처리 중 요청 수가 부풀려진다.** 워밍업을 분리했다.
