# 26. 부하 도구는 다 통과했는데 브라우저만 막혀 있었다 (#186)

자막-영상 싱크를 재려고 WebSocket 클라이언트를 붙이다가 나왔다.

```
Origin 없음                                    101 Switching Protocols
Origin: https://studywithtymee.com             403
```

**같은 요청인데 헤더 하나로 갈린다.**

---

## 무슨 뜻인가

`Origin` 은 브라우저가 붙이는 헤더다. 사람이 쓰는 요청에는 항상 있고,
`curl`·k6·python 같은 도구는 안 붙인다.

동일 출처 정책은 **그 헤더가 있을 때만** 검사한다.
그래서 이렇게 됐다.

| 무엇이 확인했나 | Origin | 결과 |
|---|---|---|
| 부하 측정 (k6·python) | 없음 | 전부 통과 |
| 배포 스모크 검사 | 없음 (정적 페이지 200) | 통과 |
| 통합 시험 | 같은 프로세스라 교차 출처가 아님 | 통과 |
| **진짜 브라우저** | 있음 | **403** |

프론트는 사이트 도메인에서 나가고 API 는 `api.` 서브도메인이라 **모든 호출이 교차 출처**다.
즉 **로그인부터 채팅, 실시간 자막까지 브라우저에서 하나도 안 됐다.**

이 서비스의 존재 이유가 실시간 자막인데, 그게 안 되는 상태로 배포돼 있었고
**모든 신호가 초록이었다.**

---

## 원인은 줄바꿈 하나 — 그런데 사람이 친 게 아니었다

운영 `.env` 48번째 줄이다.

```
FRONT_URL=http://localhost:3000FRONT_URL2=http://localhost:5173
                               ↑ 여기서 줄이 안 나뉘었다
```

`FRONT_URL` 의 값이 `http://localhost:3000FRONT_URL2=http://localhost:5173` 이 되고,
`FRONT_URL2` 는 **아예 존재하지 않아** 기본값(개발용)으로 떨어졌다.

이 두 값이 브라우저가 붙을 수 있는 출처를 정한다. 둘 다 개발용이니 운영 브라우저는 못 붙는다.

앱이 들고 있던 값을 그대로 찍어 확인했다.

```
$ printenv FRONT_URL | cat -A
http://localhost:3000FRONT_URL2=http://localhost:5173$
$ printenv FRONT_URL2
(없음)
```

### 그 줄바꿈은 템플릿이 먹고 있었다

`.env` 는 Ansible 이 만든다. 템플릿은 이렇게 생겼다.

```jinja
{% raw %}{% if front_url %}FRONT_URL={{ front_url }}{% endif %}
{% if front_url2 %}FRONT_URL2={{ front_url2 }}{% endif %}{% endraw %}
```

Ansible 의 `template` 모듈은 Jinja 를 **`trim_blocks=True`** 로 돌린다.
블록 태그 **바로 뒤의 줄바꿈을 지우는** 옵션이다.
그래서 `{% raw %}{% endif %}{% endraw %}` 로 끝나는 한 줄짜리 조건문은 전부 다음 줄과 붙는다.

더미 값으로 모든 조건을 참으로 만들어 렌더링해 보니, **설정 13개가 5줄로 합쳐졌다.**

```
MAIL_USERNAME + MAIL_PASSWORD
AWS_S3_ENDPOINT + AWS_ACCESS_KEY + AWS_SECRET_KEY + AWS_S3_BUCKET
KAKAO_CLIENT_ID + KAKAO_CLIENT_SECRET
LIVEKIT_URL + LIVEKIT_API_KEY + LIVEKIT_API_SECRET
FRONT_URL + FRONT_URL2
```

운영에서 `FRONT_URL` 만 터진 이유가 여기 있다 — **다른 묶음은 값이 비어 있어
한 줄만 렌더링됐다.** 즉 이 함정은 **인접한 선택 설정이 둘 다 채워질 때만** 나타난다.
AWS 키를 채우는 순간 S3 도, LiveKit 자격증명을 채우는 순간 화상강의도 같은 모양이 된다.

그리고 템플릿 맨 위에는 이렇게 적혀 있었다.

> ★ 값이 비면 줄 자체를 쓰지 않는다. (#51)

**빈 값을 조심하려고 넣은 그 조건문이 줄바꿈을 먹는 장치였다.**

태그를 각자 줄에 두면 없어진다 — 고친 뒤 다시 렌더링하니 합쳐진 줄 0개, 설정 31개가
전부 제 줄에 나왔다.

### 공개 도메인을 vault 에서 꺼냈다

프론트 주소는 비밀이 아니다. 그런데 vault 안에 있으면 **코드 검토에서 안 보인다.**
개발용 `localhost` 가 운영에 남아 있는 것을 아무도 못 본 이유다.
`vars.yml` 로 옮겨 평문으로 뒀다 — 보이는 곳에 둬야 틀린 것이 보인다.

## 두 겹으로 막았다

### ① 앱이 안 뜬다

운영 프로필에서 허용 출처가 개발용이거나 모양이 이상하면 **기동을 거부한다.**
이 저장소가 이미 `APP_IMAGE` 와 `GRAFANA_PASSWORD` 에 쓰는 기준과 같다 —
**조용히 잘못 뜨는 것보다 안 뜨는 게 낫다.**

무엇을 거부하는지 시험으로 고정했다. 첫 사례는 **실제로 운영을 막고 있던 그 값**이다.

| 거부 | 왜 |
|---|---|
| 값에 `=` 가 있다 | 줄바꿈이 빠져 다음 변수가 붙은 모양. **이번 사고가 정확히 이것이다** |
| `localhost` · `127.0.0.1` | 운영 브라우저의 출처와 다르다 |
| `https://` 가 아니다 | https 페이지에서 http 출처로 못 붙는다 |
| 공백이 있다 | 두 값을 한 줄에 넣은 모양 |

무중단 배포(#180)와 맞물려 **안전하게** 실패한다 — 새 슬롯이 안 뜨면
nginx 를 안 옮기고 그만두므로, 잘못된 설정으로 배포해도 **서비스는 옛 슬롯이 계속한다.**

### ①-2 템플릿이 줄을 합치면 CI 가 막는다

값이 비어 있으면 안 터지므로 이 함정은 잠복한다.
그래서 **더미 값으로 모든 조건을 참으로 만들어** 렌더링해 본다 —
채워졌을 때의 모양을 봐야 잡힌다.

`scripts/verify-env-template.sh` 가 CI 에서 돌고, Ansible 도 서버에서
**만든 파일을 다시 검사**한다. 규칙을 넣고 위반을 심어 실제로 빨개지는 것을 먼저 봤다.

```
한 줄에 설정이 둘 이상 들어간다:
  76:FRONT_URL=(값)RL2=(값)
```

### ② 배포가 브라우저처럼 한 번 붙어 본다

앱이 떴다고 끝이 아니다. nginx·CORS 설정까지 지나야 사람이 쓸 수 있다.
그래서 배포가 **사람이 하는 것과 같은 요청**을 한 번 보낸다.

```bash
curl --http1.1 -H "Origin: https://studywithtymee.com" \
     -H 'Upgrade: websocket' -H 'Connection: Upgrade' ... /ws
# 101 이 아니면 배포 실패
```

`--http1.1` 이 필요하다. **HTTP/2 로는 WebSocket 업그레이드가 안 된다** —
처음에 그냥 `curl` 로 쳤더니 400 이 나와서 한참 다른 데를 봤다.
브라우저도 이때는 1.1 로 내려간다.

## 고치는 중에 하나 더 나왔다 — 같은 함정의 두 번째 자리

`.env` 를 다시 만들었더니 **배포가 다른 데서 죽었다.**

```
error while interpolating services.livekit.environment.LIVEKIT_KEYS:
  required variable LIVEKIT_API_KEY is missing a value
```

옛 `.env` 에는 LiveKit 값이 손으로 들어가 있었고 vault 에는 비어 있었다.
Ansible 이 다시 만들면서 그 줄이 사라졌고, compose 가 멈춰 섰다.

문제는 **LiveKit 을 켜지도 않는데 배포가 죽었다**는 것이다.
Compose 는 프로필이 꺼진 서비스라도 **변수 보간을 먼저 한다** —
프로필 필터링은 그 다음이다.

이 저장소는 같은 함정을 이미 한 번 만났다. `ai` 서비스의 `AI_IMAGE` 다(#110).
**거기만 고치고 같은 모양을 찾지 않았다.**

### 규칙을 만들다 알게 된 것

"프로필이 있으면 `:?` 를 쓰지 마라" 로 규칙을 쓰니 **grafana 가 걸렸다.**
그런데 grafana 는 배포가 실제로 켜는 프로필이고, 비밀번호가 없으면
**안 뜨는 게 맞다** — 자리표시자로 뜨면 알려진 비밀번호로 관측 화면이 열린다.

그래서 기준을 바꿨다. **"프로필이 있는가" 가 아니라 "배포가 켜는가"** 다.
규칙을 쓰다가 오탐이 나온 덕에 진짜 기준이 무엇인지 정리됐다.

곁가지로 `HLS_ENABLED` 도 사라졌는데, 저장소 어디서도 안 읽는 값이었다.
손으로 넣었다가 잊힌 것이다.

---

## 남는 질문 — 왜 이제야 나왔나

이 저장소는 부하도 재고, 장애도 주입하고, 경보도 붙이고, 로그도 모았다.
그런데 **아무것도 브라우저가 아니었다.**

측정과 감시는 "많이 보내면 버티는가" 를 물었지, **"사람이 쓸 수 있는가"** 를 안 물었다.
그 둘은 다른 질문이고, 이번에는 두 번째만 틀려 있었다.

배포에 넣은 브라우저 모양 요청 하나가 그 질문을 처음으로 던진다.
