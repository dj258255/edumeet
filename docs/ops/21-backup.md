# 21. 백업이 없었다 (#175)

찾아봤다. `mysqldump` 도, cron 도, systemd 타이머도, 저장소 어디에도 없었다.

운영 DB 는 컨테이너 볼륨 하나에만 있었다. 그것이 사라지면 되돌릴 방법이 없다.
잘못된 `DELETE` 한 번이면 끝이다.

---

## 만든 것

| | |
|---|---|
| 백업 | 매일 04:00, `mysqldump --single-transaction`, gzip, 7개 보관 |
| 복구 훈련 | 매주 일요일 05:00, 버릴 컨테이너에 부어 운영과 행 수 대조 |
| 지표 | 타이머가 파일로 쓰고 node-exporter 가 읽어 올린다 |
| 경보 | 백업이 36시간째 없음 / 지표 자체가 없음 / 훈련이 9일째 없음 / 훈련 실패 |

`--single-transaction` 은 InnoDB 를 잠그지 않고 일관된 스냅숏을 뜬다.
없으면 덤프 중에 들어온 쓰기가 절반만 담겨, 복구했을 때 외래키가 안 맞는다 —
그런 백업은 있으나 마나다.

---

## ★ 뜨는 것과 세워지는 것은 다른 일이다

백업은 **"선언은 있는데 아무도 안 쓴다"** 의 교과서다
([`07-declared-but-unused.md`](07-declared-but-unused.md) 에 열 번 적은 그 모양).

덤프 파일이 매일 쌓이는 것을 보면 일이 된 것 같다. 그런데 그 파일로 DB 를
**실제로 세울 수 있는지**는 아무도 확인하지 않는다.
확인하는 날은 보통 이미 늦은 날이다.

그래서 훈련을 따로 돌린다 — 버릴 MySQL 컨테이너를 띄워 최신 덤프를 붓고,
표마다 행 수를 운영과 대조한다.

```
  표                                    운영  복구본
  class_room_seq                              1          1
  flyway_schema_history                       9          9
  ...
★ 복구 확인 - 표 20개의 행 수가 전부 일치. 18초 걸렸다
```

### 훈련이 실제로 잡는지 먼저 확인했다

행이 전부 0이면 훈련은 아무것도 안 하고도 통과할 수 있다.
그래서 **일부러 망가뜨린 덤프**로 돌려 봤다 — `flyway_schema_history` 의
`INSERT` 만 빼고 나머지는 그대로 둔 것이다.

```
  flyway_schema_history                       9          0  <-- 다르다
★ 복구본이 운영과 다르다
```

정확히 그 표만 잡았다. 안 잡히는 검사는 없는 것보다 나쁘다 —
있다고 믿게 만들기 때문이다.

---

## 이 백업이 지켜 주는 것과 못 지켜 주는 것

| | |
|---|---|
| 지켜 준다 | 실수로 지운 데이터, MySQL 이 자기 데이터 파일을 망가뜨린 경우 |
| **못 지켜 준다** | **디스크·서버 자체의 소실 — 백업이 같은 디스크에 있다** |

같은 디스크에 두는 것은 타협이다. 오브젝트 스토리지로 보내려면 자격증명이
필요한데 이 서버에는 없다(#51 에서 자리표시자로 두고 있는 그것이다).

**"어디에도 없다" 에서 "여기에는 있다" 로 가는 것이 먼저다.**
한계를 적어 두고, 자격증명이 생기면 목적지만 추가한다.

---

## 만들다 만난 것 둘

### 크기로 검사하려다 멀쩡한 백업을 매번 실패시켰다

덤프가 비었는지 크기로 보려 했다. MySQL 볼륨이 204MB 이니
10KB 미만이면 이상하다고 잡게 했다. 그랬더니 매번 실패했다.

```
덤프가 너무 작다 (4166 바이트). 내용이 비었을 수 있다
```

재 보니 그 204MB 는 대부분 InnoDB 의 자리(로그·테이블스페이스)였고
**실제 데이터는 0.6MB** 였다. 정상 덤프가 4KB 인 게 맞았다.

크기는 신호가 아니었다. 표 개수로 바꿨다 —
운영에 있는 표가 전부 덤프 안에 있어야 한다.
행이 0개여도 이 검사는 유효하다. 확인하려는 것은 "스키마 전체를 담았는가" 이기 때문이다.

### `mysqladmin ping` 은 인증이 실패해도 성공을 반환한다

훈련용 MySQL 이 뜨기를 `ping` 으로 기다렸다. 통과한 다음 복구가 죽었다.

```
ERROR 1045 (28000): Access denied for user 'root'@'localhost'
```

`ping` 은 **"서버가 응답했다"** 만 확인한다. MySQL 컨테이너는 초기화 중에
임시 서버를 한 번 띄웠다 내리므로, root 비밀번호가 설정되기 전에 통과해 버린다.

기다리는 조건을 **우리가 실제로 할 일**로 바꿨다 — 비밀번호로 붙어 질의해 본다.

### 배포 확인이 `list-timers` 를 grep 하다 실패했다

타이머를 설치한 뒤 "정말 걸렸나" 를 확인하려고 `systemctl list-timers` 를 grep 했다.
배포가 실패했다. 그런데 서버에서 보면 타이머는 멀쩡했다.

```
edumeet-backup: is-active=active is-enabled=enabled next=[Sun 2026-08-30 04:13:26 UTC]
```

`list-timers` 는 **사람이 보는 표**라 터미널 폭에 맞춰 열을 자른다.
CI 에는 tty 가 없어 80칸으로 접히면서 유닛 이름이 잘려 나갔다.

**사람이 읽는 출력을 grep 하는 검사는 그 출력의 서식만큼만 믿을 수 있다.**
`is-active` · `is-enabled` · 다음 실행 시각을 직접 묻는 것으로 바꿨다.

## 지표가 없으면 경보도 없다

백업은 컨테이너가 아니라 systemd 타이머다. 그래서 Prometheus 가 긁을 것이 없다.
node-exporter 의 **textfile 수집기**를 쓴다 — 스크립트가 `.prom` 파일을 쓰고
수집기가 그것을 읽어 올린다.

스크립트는 **실패해도 지표를 쓴다**(`edumeet_backup_success 0`).
아무것도 안 쓰고 죽으면 조용해지기 때문이다.
그리고 지난 성공 시각은 보존한다 — 이번에 실패해도
"며칠째 실패 중" 을 말할 수 있어야 한다.

경보가 네 개인 이유도 같다. `BackupMetricsMissing` 은 **경보에 대한 경보**다.
지표 자체가 없으면 `BackupStale` 은 빈 결과를 내고,
빈 결과는 "정상" 과 구분되지 않는다.

### 임계값의 근거

| 경보 | 임계값 | 근거 |
|---|---|---|
| `BackupStale` | 36시간 | 매일 04:00 주기. 한 회차 놓친 것은 봐주고 두 회차째부터 운다 |
| `BackupMetricsMissing` | 30분 | 스크립트는 실패해도 지표를 쓴다. 지표가 없다 = 한 번도 안 돌았다 |
| `RestoreDrillStale` | 9일 | 주 1회 주기. 하루 이틀 밀리는 것은 정상, 9일이면 한 회차를 건넜다 |
| `RestoreDrillFailed` | 5분 | 값이 주 1회만 바뀐다. 기다리는 동안 다음 회차까지 일주일이 지나간다 |

---

## 지금 운영 DB 는 비어 있다

솔직히 적어 둔다. 실제 데이터는 0.6MB 이고 그중 대부분이 마이그레이션 이력이다.
사용자가 없으니 당연하다.

그래서 이 작업이 증명하는 것은 **데이터를 지켰다**가 아니라
**되돌릴 수 있는 경로가 실제로 동작한다**는 것이다.
복구 훈련이 망가진 덤프를 잡아내는 것까지 확인했으므로,
데이터가 생겼을 때 이 경로가 작동하지 않을 이유는 없다.
