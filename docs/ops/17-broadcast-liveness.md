# 배포가 방송을 끊는데 아무도 몰랐다 (#168)

> 측정 2026-08-29 · OCI aarch64 2 OCPU / 12GB

## 0. 무엇이 문제였나

송출 세션은 `ConcurrentHashMap` 이라 **메모리에만 있다.**
앱이 재시작되면 ffmpeg 는 같이 죽는데 DB 의 `broadcast_session_id` 는 남는다.

```
발표자 화면   계속 "방송 중"
시청자        세그먼트가 안 늘어난다
에러 로그     한 줄도 안 난다
```

**배포할 때마다 난다.** 그런데 증상이 조용해서 아무도 이상하다고 느끼지 않는다.

### 기존 수거기는 이걸 못 잡는다

`reapIdleSessions()` 가 10초마다 유령 방송을 걷어낸다. 그런데 그것은
**메모리에 있는 세션**을 훑는다. 재시작 뒤에는 그 맵이 비어 있다.

> **훑을 것이 없으니 아무것도 안 한다.**
> 수거기가 있다는 사실이 오히려 "정리되고 있다" 는 착각을 만든다.

---

## 1. 측정 설계

**두 버전을 같은 DB 상태에 붙였다.**

```
재시작 직전 상태
  meeting.broadcast_session_id 가 채워져 있다      <- 방송 중
  ffmpeg 프로세스는 없다                            <- 재시작으로 죽었다
```

이 상태는 실제 방송이 남기는 것과 같은 행이다.
재는 대상은 **"그 행을 각 버전이 어떻게 다루는가"** 다.

### 왜 실제 방송을 돌려서 만들지 않았나

송출을 시작하려면 **MediaRecorder 가 만든 조각을 브라우저가 밀어 넣어야** 한다.
스크립트로 그 클라이언트를 흉내 내는 데 시간이 더 들고,
그렇게 만든 상태나 직접 쓴 상태나 **DB 에 남는 행은 같다.**

### 한 번 틀렸다 — 스키마가 매번 새로 만들어지고 있었다

처음 재니 **고치기 전에도 유령이 0** 이었다. 고쳐도 안 고쳐도 같은 값이면
그 측정은 아무것도 말하지 않는다.

원인은 측정 환경이었다. perf 프로파일은 `ddl-auto: create` 라
**재시작마다 스키마를 새로 만든다.** 재시작 전 상태가 통째로 사라지니
잴 대상 자체가 없어진 것이다.

두 번째 기동만 `ddl-auto=none` 으로 올려 조건을 만들었다.

> **"차이가 없다" 가 나오면 먼저 조건이 만들어졌는지 본다.**
> 이 저장소에서 같은 실수를 [`performance/15`](../performance/15-caption-backpressure-landing.md) 3절에서도 했다.

## 2. 결과

| | 고치기 전 | 고친 뒤 |
|---|---:|---:|
| 재시작 직전 방송중 표시 | 2건 | 2건 |
| **재시작 뒤 DB 가 방송중이라고 믿는 회의** | **2건** | **0건** |
| 실제로 돌고 있는 ffmpeg | 0 | 0 |
| **그 사이 남긴 ERROR 로그** | **0줄** | **0줄** |
| 정리했다는 로그 | 0 | 2 |
| `broadcast_stale_reconciled_total` | 지표 없음 | **2** |

**고치기 전에는 DB 가 방송 중이라고 믿는 회의가 2건인데 ffmpeg 는 0개다.**
그리고 그 어긋남을 알리는 **에러가 한 줄도 없다.**

```
DB 가 믿는 것   방송 2건 진행 중
실제            프로세스 0개
알림            없음
```

고친 뒤에는 0건이 되고, **정리했다는 사실이 로그와 지표로 남는다.**

### 되살리지 않고 정리만 하는 이유

되살릴 수가 없다. 송출은 **발표자 브라우저가 조각을 밀어 넣어야** 이어진다.
서버 혼자 다시 시작할 수 있는 것이 아니다.

**상태를 사실에 맞추는 것이 할 수 있는 전부다.** 발표자는 다시 시작해야 한다.
그래서 경보를 붙였다 — 정리했다는 것은 *"직전 배포가 누군가의 방송을 끊었다"* 는 뜻이다.
근본 대책은 **배포 창을 방송 시간과 겹치지 않게 잡는 것**이다.

## 3. 아무도 안 듣는데 인코딩 중인 방

2코어에서 방송 하나가 CPU 를 쓴다. 동시 상한이 2라
**안 보는 방송이 하나 있으면 볼 사람이 있는 방송이 못 시작할 수 있다.**

### 시청자를 어떻게 세나

HLS 세그먼트는 **nginx 가 직접 내준다.** 앱이 그 요청을 못 본다.
그리고 nginx 는 호스트에서 돌아 **로그 수집기(Alloy)도 안 닿는다.**

대신 시청 화면이 어차피 자막과 채팅을 받으려고 **STOMP 로 방을 구독한다.**
그 구독자 수가 시청자 수의 근사다. 이미 세고 있던 값이라 새로 만들 것이 없었다.

**근사다.** 탭을 백그라운드로 둔 사람도 세고, 채팅을 끄고 영상만 보는
클라이언트가 생기면 못 센다. 지금 프론트는 접속하면 무조건 둘 다 구독한다.

### 자동으로 멈추지 않는다

발표자가 **의도해서 켠 것**이고, 아직 아무도 안 들어왔을 뿐일 수 있다.
켠 지 1분 만에 서버가 꺼 버리면 그게 더 나쁘다.

경보의 `for` 를 10분으로 둔 이유가 그것이다. **끄는 판단은 사람이 한다.**

## 4. 아직 안 한 것

- **다시보기가 없다.** `delete_segments` 로 도니 방송이 끝나면 영상이 사라진다.
  자막 다시보기는 있는데 영상은 없다. 별도 녹화 경로가 필요하다
- **재시작을 감지해 발표자에게 알리지 않는다.** 지금은 DB 만 정리한다.
  발표자 화면은 새로고침하기 전까지 "방송 중" 으로 보인다
