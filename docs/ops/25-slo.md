# 25. SLO · 에러 버짓 · 다중 창 소진율 경보 (#234)

지금까지의 경보는 **임계값**이었다 - "큐가 50% 를 넘으면", "유실이 0 이 아니면".
그건 지금 상태를 말해 주지만 **이번 달을 어떻게 쓰고 있는지는 말해 주지 않는다.**
유실 1건이 한 번 난 것과 매시간 나는 것을 같은 소리로 울린다.

여기서는 **예산 소진 속도**를 본다. 목표(SLO)를 정하고, 못 지킨 몫(에러 버짓)을 정하고,
그 예산이 얼마나 빨리 타고 있는지로 경보를 나눈다.

---

## 1. SLO

28일 창이다. 28일 = 672시간.

| SLI | 식 (운영에 있는 지표) | SLO | 출처 |
|---|---|---|---|
| 재생 끊김 비율 | `playback_stall_seconds_total / (stall + playback_playing_seconds_total)` | ≤ 1% | **이 저장소 측정만** - 정상망 0~0.05%(#198·#233 그리드), 제한망 약 11~12%. 업계 공개 벤치마크(Conviva·Mux 류)는 "1% 안팎" 으로 인용되지만 **1차 출처를 확인하지 못해 숫자를 옮기지 않았다** |
| 송출 조각 수락률 | `http_server_requests_seconds_count{uri="/api/v1/meeting/{meetingId}/broadcast/chunk", status!~"2..\|409"} / 전체` | ≥ 99.9% | 그리드 수천 조각 실패 0. **409 는 분자에서 뺀다** - #229 의 복구 신호다 (아래) |
| 자막 전달률 | `1 - caption_broadcast_dropped / (published + dropped)` | ≥ 99.9% | #157 · #159 유실 0 |
| 채팅 저장률 | `1 - (chat_archive_dropped + persist_failed + stream_dead + stream_trimmed + stream_discarded) / enqueued` | ≥ 99.99% | #201 스트림 방식 유실 0 |

**두 가지 유실을 더 셌다 (#234b).**

- `chat_archive_stream_trimmed` 는 **비상 트림**이다. `ChatArchiveStream` 의 `EMERGENCY_MAX_LEN`
  주석이 그대로 적고 있다 - 여기서 지워지는 것은 **아직 저장하지 못한 항목일 수 있다.**
  ACK 뒤 정상 트림은 이 카운터에 안 잡히므로, 여기 잡히는 것은 유실이다.
  (이전 판에 "상한 트림은 보호라 SLI 로는 정상" 이라고 적었는데 **틀렸다**. 고쳤다.)
- `chat_archive_stream_discarded` 는 uid 가 없어 저장하지 않은 것(**유실**)과 회의가 지워진 것
  (**의도**)이 섞인다. 회의 삭제분까지 유실로 세는 것은 과하지만, 유실을 놓치는 쪽이 더 나쁘다 -
  그래서 넣고 여기 적는다. 회의 삭제는 드물다.

**송출 조각에서 409 는 실패가 아니다.** 배포 중 새 슬롯에 그 방송이 없으면 발표자가
409 를 받고 다시 붙는다(#229 의 복구 신호). 이걸 실패로 세면 배포할 때마다 조각 SLI 가 무너진다.
방송이 정말 멈추면 재생 끊김 SLI 가 본다. 그래서 분자는 `2xx` 와 `409` 를 뺀 나머지다.

**출처에 대해.** 세 번째 열의 "정상망 0~0.05%" 같은 수는 이 저장소가 직접 잰 것이다
(`docs/performance/` 의 그리드 측정). 그 밖의 수치는 **확인한 것만** 적었다 -
기억나는 벤치마크 숫자를 출처처럼 적으면 나중에 그 숫자를 근거로 결정하게 된다.

**SLO 를 이 값으로 정한 이유.**

- 재생 끊김 1%: 정상망에서 이미 0~0.05% 다. 여유가 20배 이상이라 1% 는 "정상망에서는 절대 안 닿는" 선이다.
  제한망(11~12%)은 이 SLO 를 크게 넘는데, **그건 사용자 망의 문제이지 우리 서비스의 실패가 아니다** -
  그래서 이 SLI 는 "우리가 못 준 것" 을 보는 값이고, 제한망 실험의 숫자는 목표가 아니라 참고다.
- 조각 수락률 99.9%: 조각은 2초마다 하나다. 한 방송·한 시간이면 1,800개다.
  0.1% 는 그 중 2개까지다 - 그 이상이면 방송이 실제로 끊긴다.
- 자막 전달률 99.9%: 자막은 초당 몇 개 나온다. 화면에서 사라지는 것은 전사에도 남지만
  **사용자는 그 사실을 모른다.** 조용한 실패라 0.1% 를 넘으면 사람이 봐야 한다.
- 채팅 저장률 99.99%: 다시보기 채팅은 한 번 빠지면 복구할 방법이 없다.
  0.1% 로 두면 방송 한 번(수천 건)에 몇 건이 사라진다 - 그건 "다시보기가 조금 다른 것" 이 아니라
  **다른 것**이다. 그래서 여기만 두 자릿수 더 조인다.

## 2. 에러 버짓

에러 버짓 = 1 − SLO. 28일 동안 그만큼은 못 지켜도 된다.

| SLI | 버짓 | 28일 환산 | 건수 환산 |
|---|---|---:|---|
| 재생 끊김 | 1% | **6시간 43분 12초** | - (시간 비율이라 초 단위) |
| 송출 조각 | 0.1% | **40분 19초** | 요청 수에 따라 다르다 - 방송 1개·2초 조각이면 28일 120만 개 중 1,200개 |
| 자막 전달 | 0.1% | **40분 19초** | 방송 시간에 따라 다르다 - 초당 3개면 28일 725만 개 중 7,250개 |
| 채팅 저장 | 0.01% | **4분 2초** | 메시지 수에 따라 다르다 - 분당 10건이면 28일 40만 건 중 40건 |

**"28일 환산" 을 왜 시간으로 적나.** 요청·건수는 트래픽에 따라 매달 달라진다.
시간 환산은 트래픽과 무관하게 같은 뜻이고, "이대로 가면 언제 다 쓰는가" 를 바로 말해 준다.

```
버짓 시간 = 28일 x (1 - SLO) = 2,419,200초 x (1 - SLO)
```

## 3. 경보 설계 - 다중 창 · 다중 소진율

소진율(번 레이트)은 이렇게 정의한다.

```
소진율 = (그 창의 오류율) / (1 - SLO)
```

소진율 1 이면 28일을 꼭 채우고 예산을 다 쓴다. 13.44 면 50시간에 다 쓴다.

**창을 둘 쓰는 이유.** 긴 창만 보면 짧게 튄 것에도 울리고, 짧은 창만 보면 이미 지나간 것에도 울린다.
그래서 **긴 창과 짧은 창이 둘 다** 문턱을 넘을 때만 울린다. 짧은 창이 "지금도 타고 있나" 를 답한다.
(Google SRE Workbook 의 표와 같은 구조다 - 태우는 비율 2% · 5% · 10%.)

**28일 창으로 다시 계산했다.** Workbook 의 14.4 · 6 · 1 은 **30일** 창 기준이다.
이 저장소는 28일이므로 배수가 달라진다.

```
배수 = (태우려는 예산 비율) x 672시간 / (창 길이, 시간)

  2%  x 672 / 1h  = 13.44   1h & 5m    급하다 - 페이지        50시간에 예산 소진
  5%  x 672 / 6h  =  5.6    6h & 30m   페이지                5일에 소진
  10% x 672 / 72h =  0.933… 3d & 6h    티켓(급하지 않다)       30일에 소진
```

0.933 은 반복소수의 근사값이라 **규칙에는 식 그대로**(`(0.1 * 672 / 72)`) 쓴다 (`#234b`).
30일 기준 14.4 를 그대로 쓰면 같은 "2%" 가 30일 기준이 되어 **28일 예산을 7% 더 태운 뒤에** 울린다.
급한 쪽에서 7% 는 크다.

### 문턱 (예산 x 배수)

| SLI | 예산 | 급함 13.44x | 느림 5.6x | 티켓 0.933x |
|---|---:|---:|---:|---:|
| 재생 끊김 | 1% | 13.44% | 5.6% | 0.933% |
| 송출 조각 | 0.1% | 1.344% | 0.56% | 0.0933% |
| 자막 전달 | 0.1% | 1.344% | 0.56% | 0.0933% |
| 채팅 저장 | 0.01% | 0.1344% | 0.056% | 0.00933% |

### 라벨 없는 합계로 본다 (#184)

배포는 슬롯 둘(blue/green)이다. `instance` 별로 물으면 **페이지가 두 번 울리고**,
한 슬롯이 조용할 때 다른 슬롯의 비율이 절반으로 보인다 - #184 에서 실제로 그렇게 놓쳤다.
그래서 규칙은 전부 `sum(...)` 으로 합친 뒤 문턱과 비교한다. 경보에 `instance` 라벨이 없다.

### 심각도

| 문턱 | 라벨 | 무엇 | 뜻 |
|---|---|---|---|
| 13.44x (2%/1h) | `severity: critical` | 페이지 | 지금 깨우고 사람이 본다 |
| 5.6x (5%/6h) | `severity: critical` | 페이지 | 같은 급함 - 5일에 예산이 바닥난다 |
| 0.933x (10%/3d) | `severity: warning` | 티켓 | 급하지 않다. 다음 주에 본다 |

`for` 는 `0m` 이다. **짧은 창이 `for` 역할을 한다** - 둘 다 넘어야 울리므로
"5분만 튄 것" 은 이미 걸러진다. 여기에 `for` 를 더 얹으면 5분을 또 기다리는 셈이다.

### 검증

규칙과 시험은 `observability/rules/` 에 있다. SLI 마다 시험 파일이 하나씩이고,
각각 다섯 가지를 본다.

| 시험 | 무엇을 지키나 |
|---|---|
| 빠른 소진 | 세 경보가 다 울린다 |
| 느린 소진 | **느린 경보와 티켓만** 울린다 - 빠른 경보가 같이 울리면 문턱이 틀린 것이다 |
| 짧게 튄 것 | 5분 창은 넘지만 1시간 창이 평균을 내려 **안 울린다** |
| 분모가 작은 것 | 비율은 100% 인데 **안 울린다** (아래 4번) |
| 슬롯 둘 | 두 슬롯이 다 타도 **한 번** 울린다 (`instance` 라벨이 없다) |

```
docker run --rm -v "$PWD/observability/rules:/rules:ro" --entrypoint sh \
  prom/prometheus:v3.1.0 -c 'promtool check rules /rules/*.yml && promtool test rules /rules/tests/*.test.yml'
```

CI(`.github/workflows/ci.yml`)가 같은 명령을 돈다. 시험 파일 이름이 `*.test.yml` 이므로
새 파일도 와일드카드에 걸린다.

규칙이 물어보는 **지표와 라벨**은 백엔드 시험이 지킨다.

| 시험 | 무엇 |
|---|---|
| `AlertMetricsExposedTest` | 규칙이 쓰는 지표 이름이 실제 노출 목록에 있는가 (기록 규칙 이름은 제외) |
| `ChunkUriTagContractTest` | 규칙의 `uri="..."` 가 실제 요청이 만든 태그와 같은가 |

```
cd backend && ./gradlew test --tests 'com.edu.edumeet.integration.observability.*'
```

## 4. 저트래픽 문제 - 지금 실사용이 거의 없다 (#178)

이 저장소의 실사용은 아직 거의 없다. 그러면 비율이 요동친다.

```
5분 동안 자막이 1건 버려지고 발행이 0건이면
  오류율 = 1 / (0 + 1) = 100%
  소진율 = 100% / 0.1% = 1,000배
```

이대로면 **한 건 때문에 페이지가 울린다.** 다음 5분에 아무 일도 없으면 조용해진다 -
울렸다 꺼졌다를 반복하는 경보는 아무도 안 본다. (#178 에서 "0 을 합친 뒤에 묻자" 로 배운 것과 같은 문제다.)

**최소 분모 조건**을 함께 건다. 창에 트래픽이 없으면 비율 자체를 믿지 않는다.

**그러면 그 게이트가 막는 드문 유실은 누가 잡나.** 즉시 경보가 잡는다 -
`ChatArchiveLosing` 의 합을 SLO 분자와 **같게** 맞췄다(다섯 가지 전부).
다르면 조용한 새벽의 1건이 어느 경보에도 안 걸린다. 합이 같은지는
`observability/rules/tests/chat-archive-losing.test.yml` 이 다섯 각각을 울려서 지킨다.

| SLI | 조건 | 값 | 뜻 |
|---|---|---:|---|
| 재생 끊김 | `traffic_1h` | **>= 0.5** | 평균 시청자 반 명. 재생 초/초가 곧 동시 시청자 수다 - 1 로 두면 **시청자 한 명이 계속 끊겨도 안 울린다**. 그 한 명에게는 100% 실패다 (#234b) |
| 송출 조각 | `traffic_1h` | > 0.1/s | 10초에 조각 하나 - 방송 하나가 올리는 속도(0.5/s)보다 낮다 |
| 자막 전달 | `traffic_1h` | > 0.01/s | 100초에 자막 하나 |
| 채팅 저장 | `traffic_1h` | > 0.01/s | 100초에 메시지 하나 |

느린 경보와 티켓은 각각의 긴 창(`traffic_6h`)을 본다 - "그 창에 트래픽이 있었다" 를 확인하는 것이다.
3일 창의 분모는 쓰지 않는다. 데이터가 창보다 짧으면 `rate` 가 창 길이로 나눠 값을 과소평가하는데,
**비율은 분자·분모가 같이 줄어 상쇄되지만 traffic 은 그대로 줄어든다.**

**비율이 0 일 때 NaN 도 막는다.** 분모가 0 이면 `0/0 = NaN` 이고, NaN 은 모든 비교에 걸리지 않아
경보가 조용해진다 - 조용한 것 자체는 맞지만 **우연히 조용한 것과 조건이 막은 것은 다르다.**
그래서 `clamp_min(분모, 1e-9)` 로 0 을 만들고, 시험은 `ratio_5m` 이 정말 100% 였다는 것을 못 박는다.

### 입력이 사라진 것을 '정상 0' 으로 삼키지 않는다 (#234b)

SLO 경보는 "오류율이 낮다" 를 조용함으로 말한다. 그런데 **입력이 아예 없어도 조용하다** -
uri 라벨이 바뀌거나(템플릿 변경) 계측이 사라지면 분모가 0 이 되고 `0 / 1e-9 = 0` 이라 정상으로 보인다.
그 조용함이 '괜찮다' 인지 '못 본다' 인지 구분해야 한다.

그래서 `SloInputMissing` 경보를 둔다 - **방송이 켜져 있는데**(`sum(broadcast_active) > 0` 10분)
조각 SLI 나 재생 SLI 의 입력이 0 이면 경고한다. 트래픽이 없을 때 입력이 0 인 것은 정상이므로
기준을 "방송 중" 으로 잡았다.

**라벨 계약은 시험이 지킨다.** 조각 SLI 는 `uri="/api/v1/meeting/{meetingId}/broadcast/chunk"` 를
물어보는데, 이 문자열을 손으로 적어 두면 컨트롤러 매핑을 바꿨을 때 한쪽만 바뀐다.
`contracts/` 와 같은 발상으로 `ChunkUriTagContractTest` 가 **규칙 파일을 읽어**
실제 요청이 만든 uri 태그와 대조한다(요청을 실제로 보낸다 - 태그는 핸들러 매핑이 정한다).

## 5. 기존 임계값 경보 - 대체할까, 남길까

**제안만 한다. 지우지 않았다.** 지금 이 경보들은 각자 다른 것을 본다 - 판단은 이 세션 몫이다.

| 기존 경보 | 같은 신호를 보나 | 제안 | 이유 |
|---|---|---|---|
| `CaptionBroadcastDropping` | 자막 전달 SLI 와 겹친다 | **남긴다** | SLO 경보는 창 평균이라 1시간이 지나야 울린다. 이건 5분 안에 1건이라도 버리면 즉시 울린다 - 첫 유실을 아는 것은 여전히 이쪽이다 |
| `ChatArchiveLosing` | 채팅 저장 SLI 와 겹친다 | **남긴다** | 트래픽이 없으면 SLO 는 분모 조건으로 조용하다. 조용한 시간의 1건은 이 경보만 잡는다 - 그래서 **합을 SLI 분자와 같게** 맞췄다(다섯 가지) |
| `ChatArchiveStreamBehind` | 아니다 (지연) | **남긴다** | 저장이 밀리는 것은 결과가 아니라 과정이다. 밀리다 잘리면 그때 SLI 가 움직이는데, 그 전에 알아야 한다 |
| `ChatArchiveStreamBacklog` | 아니다 (적체) | **남긴다** | 위와 같다 - 잘리기 전에 잡는 경보 |
| `ChatArchiveStreamTrimming` | **겹친다** (비상 트림은 유실) | **남긴다** | SLI 는 5분·1시간 창의 비율이라 즉시성이 없다. 트림이 시작되는 순간을 이쪽이 알린다 |
| `ChatArchiveBacklog` | 아니다 (폴백 큐) | **남긴다 (정리 후보)** | 큐 방식은 이제 폴백이다. 폴백을 없애면 함께 정리한다 - 지금 지우면 폴백이 도는 날 아무도 모른다 |
| `ErrorLogsRising` | 아니다 | **남긴다** | 로그는 SLI 에 안 잡히는 실패(설정 오류·예외)를 잡는다 |
| (재생 끊김 · 조각 수락) | **없다** | **새로 만든다** | 지금은 재생 품질을 보는 경보가 없다. 조각 실패는 `ErrorLogsRising` 에 묻힌다 |

정리하면: **SLO 경보는 "이번 달을 어떻게 쓰고 있나" 를 보고, 임계값 경보는 "지금 무슨 일이 났나" 를 본다.**
둘은 같은 지표를 보지만 답하는 질문이 다르다. 그래서 대체가 아니라 **추가**다.
