# 답을 못 할 것 같다고 지목된 질문 셋을 재 봤다

> **#143.** 포트폴리오 리뷰에서 *"이건 아마 답 못한다"* 로 지목된 셋.
> 셋 다 문서로 얼버무릴 수 있는 것이 아니라 **재면 답이 나오는 것**이었다.

---

## 1. `CallerRunsPolicy` 로 넘긴 역압은 어디에 착지하나

**질문**: *"그 스레드가 다른 요청도 처리하는 스레드면 뭐가 죽나요?"*

`WebSocketConfig` 에 *"역압을 위로 전달한다"* 고 적어 뒀는데 **위가 어디인지는 안 적었다.**

### 재 본 것

세 채널의 실행기 구성을 런타임에 찍었다.

```
clientInbound   core 24 / max 48 · 큐 2,000  · CallerRunsPolicy
clientOutbound  core 24 / max 48 · 큐 20,000 · CallerRunsPolicy
brokerChannel   실행기 없음 → 호출 스레드에서 직접 실행
```

**세 번째가 답을 정한다.** `convertAndSend` 는 brokerChannel 로 가는데 거기 실행기가 없으므로
`SimpleBrokerMessageHandler` 가 호출 스레드에서 그대로 돌고, 그 스레드가
`clientOutboundChannel.send()` 를 부른다.

**따라서 아웃바운드 큐가 찼을 때 전송을 떠안는 것은 브로커 스레드가 아니라 원래 호출자다.**

### 호출자가 둘인데 성격이 다르다

```
채팅  @MessageMapping  →  chat-in- 실행기 스레드
자막  @PostMapping     →  Tomcat HTTP 요청 스레드
```

자막 경로를 실제로 찍으니 `http-nio-auto-1-exec-1` 이 나왔다.

**두 번째가 위험하다.** 파이썬 STT 가 계속 POST 하는 동안 아웃바운드가 포화하면
Tomcat 요청 스레드(기본 200)가 전송에 묶인다 —
**자막이 채팅을 막는 것이 아니라 REST API 전체를 막는다.**

채팅 경로도 안전하지는 않다. `chat-in-` 스레드가 전송을 떠안으면 인바운드 처리가 멈추고,
인바운드 큐(2,000)까지 차면 그쪽 `CallerRunsPolicy` 가 **WebSocket 컨테이너 스레드**로 넘긴다.
그 지점부터는 새 프레임을 읽지 못한다.

### 고정한 것

`BackpressureLandingTest` 가 넷을 잡는다.

| | |
|---|---|
| brokerChannel 에 실행기가 없다 | 여기 실행기가 생기면 착지점 분석 전체를 다시 해야 한다 |
| 자막이 `http-nio-` 스레드에서 시작한다 | 비동기로 바꾸면 이 시험이 깨지고, 그때 이 문서도 같이 고쳐야 한다 |
| 큐 상한이 코드 선언값과 같다 | 경보가 이 값과의 비율을 묻고 있다 |
| 두 채널 모두 `CallerRunsPolicy` | `DiscardPolicy` 로 바뀌면 조용히 메시지가 사라진다 |

### 아직 안 고친 것

자막 브로드캐스트를 비동기로 빼면 HTTP 스레드는 풀린다. **안 했다.**
지금 응답에 세 개의 타임스탬프(`spokenAt`·`receivedAt`·`publishedAt`)를 담아 홉 비용을 재고 있는데,
비동기로 빼면 `publishedAt` 이 "큐에 넣은 시각"이 되어 **측정의 의미가 바뀐다.**
바꾸려면 무엇을 재는 값인지 먼저 다시 정해야 한다. 그 전까지는 **한계로 적어 둔다.**

## 2. 경보 50% 는 사람이 대응할 시간을 주는가

**질문**: *"임계값 근거는 댔는데, 큐 50% → 100% 도달까지의 lead time 은 쟀나요?"*

**안 쟀다.** 임계값이 왜 50%인지는 적었지만(정상 최대가 상한의 2.6%),
**그 시점에 무엇을 할 수 있는지**는 따지지 않았다.

### 재 본 것

무한 큐 실험의 순증에서 나온다.

```
1,077,906건 / 84초  =  초당 12,832건 순증
```

상한 20,000 기준으로 환산하면

| | |
|---|---:|
| 50% → 100% | **0.78초** |
| 70% → 100% | 0.47초 |
| 0 → 100% | **1.56초** |

**`scrape_interval` 이 15초이고 `for` 가 1분이다.**
그 부하에서는 **경보가 평가되기도 전에 큐가 찬다.**

### 이 경보가 유효한 창은 좁다

| 원하는 여유 | 필요한 순증 | 소비가 따라잡아야 하는 비율 |
|---:|---:|---:|
| 15초 | ≤ 667건/s | **98.15%** |
| 60초 | ≤ 167건/s | 99.54% |
| 5분 | ≤ 33건/s | 99.91% |

(그 부하의 총 전달 요구는 발행 240/s × 구독 150 = **초당 36,000건**이다.)

즉 소비가 98% 밑으로 떨어지는 순간부터 경보는 늦는다.

### 그래서 경보의 역할을 다시 적었다

> **급성 붕괴를 막는 것은 경보가 아니라 상한과 `CallerRunsPolicy` 다.**
> 이 경보는 그보다 완만한 열화(소비가 조금씩 밀리는 구간)를 잡고,
> 급성 구간에서는 *"무슨 일이 있었나"* 를 알려 주는 **사후 기록**으로 쓴다.

임계값을 더 내리는 것은 답이 아니다. 90% → 100% 도 0.16초라 마찬가지이고,
낮출수록 완만한 열화 구간에서 오탐만 늘어난다.

**경보로 못 막는 구간이 있다는 것을 아는 것이 경보를 더 조이는 것보다 낫다고 봤다.**

## 3. 하이브리드의 +16%p 는 의미 이해 덕인가

**질문**: *"2-gram 이 못 잡는 오탈자·띄어쓰기를 임베딩이 우연히 커버한 것은 아닌가?"*

recall 집계만 있고 **실패 원인 분해가 없었다.**

### 재 본 것

질의 30개를 하나씩 열어 2-gram · 임베딩 단독 · 하이브리드를 나란히 놓고,
**개선된 질의의 어휘 겹침**을 같이 봤다.

```
2-gram 대비   개선 5 · 회귀 0 · 동일 25
```

개선된 5건은 **전부 어휘 겹침 0%** 였다.

| 질의 | 정답 조각의 표현 | 겹침 |
|---|---|---:|
| 락을 걸어서 순서를 보장하는 방법 | "자물쇠를 거는 겁니다 / 비관적 잠금" | 0% |
| 측정 환경 바뀌면 결과가 달라지나요 | "저장소 엔진에 따라 다릅니다 / 인메모리로 재면" | 0% |
| 커넥션을 유지하는 프로토콜 | "한 번 연결하면 계속 열려 있습니다" | 0% |
| 트래픽 없을 때 커넥션 끊김 | "아무 말도 안 오가면 프록시가 연결을 끊어" | 0% |
| 블로킹 연산이 이벤트 루프를 막는 문제 | "오래 걸리는 계산 / 한 줄로 도는 구조" | 0% |

**오탈자·띄어쓰기 변형은 한 건도 없었다.** 전부 *"같은 것을 다른 말로 물은"* 경우다.
그래서 답은 **의미 이해 덕이 맞다.**

### 다만 하이브리드가 손해인 경우도 있었다

| 질의 | 2-gram | 임베딩 단독 | 하이브리드 |
|---|---:|---:|---:|
| 블로킹 연산이 이벤트 루프를 막는 문제 | 0% | **67%** | **33%** |

RRF 병합이 **렉시컬의 오답을 상위로 끌어올려 임베딩의 정답 하나를 밀어냈다.**
전체로는 이득이지만(회귀 0건) **병합이 공짜가 아니라는 증거**다.

지금은 두 순위에 같은 가중치를 준다. 가중치를 조정하면 이 한 건은 살릴 수 있겠지만,
**질의 30개로 가중치를 튜닝하면 그 30개에 과적합된다.** 질의 세트를 늘리기 전까지는 안 만진다.

## 이 세 개를 재고 나서 바뀐 것

| | |
|---|---|
| 문서 | *"역압을 위로 전달한다"* → **어디로 전달되는지**를 적었다 |
| 경보 | *"사람이 볼 시간이 남는다"* → **틀렸다.** 급성 구간에서는 늦고, 그래서 역할을 다시 적었다 |
| 검색 | *"하이브리드가 낫다"* → **무엇 덕분에 나은지**와 **어디서 손해인지**를 적었다 |

셋 다 **주장이 틀린 것은 아니었지만 한 겹이 빠져 있었다.**
빠진 겹은 전부 *"그래서 그 다음은?"* 이었다.
