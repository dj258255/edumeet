# 22. 한 번도 평가된 적 없던 경보 두 개 (#178)

[#174](07-declared-but-unused.md) 에서 Prometheus 가 8월 27일 설정으로 돌고 있던 것을 고쳤다.
설정을 다시 읽게 하자마자, **그때까지 한 번도 평가된 적 없던 규칙들의 결함이 드러났다.**

배포 직후 확인해 보니 경보 다섯 개가 울리고 있었다.

```
NoLogsFromApp   level=debug
NoLogsFromApp   level=trace
NoLogsFromApp   level=warn
NoLogsFromApp   level=error
DiskFillingUp
```

둘 다 오탐이었다. 그리고 둘 다 **경보를 무의미하게 만드는 종류**의 오탐이다 —
상시 울리는 경보는 사람이 채널을 끄게 만들고, 그 뒤로는 진짜 경보도 같이 안 보인다.

---

## 하나 — 합치지 않고 0인지 물었다

```promql
increase(logback_events_total[10m]) == 0        # 틀렸다
```

의도는 **"앱이 로그를 한 줄도 안 남긴다"** 였다. 로그 경로가 끊기면
대시보드가 조용히 비는데, 빈 화면은 "아무 일도 없었다" 와 구분되지 않으므로
지표 쪽에서 따로 묻자는 것이었다(#167).

그런데 `logback_events_total` 에는 `level` 라벨이 있다.
Prometheus 는 **시계열마다 따로 평가**하므로 이 식은 수준마다 하나씩 묻는다.

```
debug  0.0
error  0.0      <- 정상이다. 이 앱의 에러는 예외 경로에서만 난다
info  34.9
trace  0.0
warn   0.0
```

즉 **"ERROR 가 10분간 0건" 이 경보가 됐다.** 그건 좋은 상태다.

합친 뒤에 묻는다.

```promql
sum by (job, instance) (increase(logback_events_total[10m])) == 0
```

합계가 0일 때도 식이 결과를 내는지 확인했다 — 안 그러면
로그가 진짜 끊겼을 때도 조용하다.

```
sum by (job) (increase(logback_events_total{level="error"}[10m])) == 0
  -> 결과 1개, 값 0
```

## 둘 — 창이 비었는데 추세를 말했다

```promql
predict_linear(node_filesystem_avail_bytes{mountpoint="/"}[6h], 4*24*3600) < 0
```

디스크 경보를 붙인 지(#173) **40분 만에** 울렸다. 실제 여유는 14.4GB 였다.

6시간 창에 40분치 표본만 들어 있으면, 그 짧은 구간의 기울기를 4일로 늘리는 것이다.

```
현재 여유        14.43 GB
4일 뒤 예측    -145.40 GB
하루 변화량     -39.93 GB      <- 46GB 디스크에서 나올 수 없는 숫자다
```

배포가 이미지를 몇 개 받은 구간이 통째로 기울기가 됐다.

조건 두 개를 붙였다. **둘 다 오탐을 보고 나서 붙인 것이고, 각각 근거가 있다.**

### ① 창이 실제로 차 있어야 한다

```promql
count_over_time(node_filesystem_avail_bytes{mountpoint="/"}[6h]) > 720
```

scrape 가 15초이므로 6시간이면 표본 1,440개다. 절반(3시간)은 차야 추세라고 부른다.
울릴 때의 표본 수는 **128개**였다.

### ② 여유가 이미 적어야 한다

```promql
node_filesystem_avail_bytes{mountpoint="/"} < 12e9
```

실측한 최악의 증가 속도가 2.9GB/일이다(#173). 4일이면 11.6GB.
여유가 그보다 많은데 "4일 뒤 0" 이 나온다면 **우리가 관측한 적 없는 속도**라는 뜻이고,
그런 기울기는 추세가 아니라 계단이다 — 정리 직후가 정확히 그 경우다.

즉 이제 **"빨리 줄고 있다"** 만으로는 안 울린다.
**"빨리 줄고 있고, 이미 얼마 없다"** 여야 한다.

### 뒷이야기 — 합치긴 했는데 라벨 하나를 남겨 뒀다

처음 고칠 때 이렇게 썼다.

```promql
sum by (job, instance) (increase(logback_events_total[10m])) == 0
```

슬롯이 하나일 때는 맞았다. 그런데 무중단 배포([#180](24-zero-downtime-deploy.md))로
슬롯이 둘이 되자 **`instance` 가 다시 갈랐다** — 갓 뜬 슬롯은 카운터가 0에서 시작해
잠깐 증가분이 0으로 잡힌다. 배포마다 그 순간이 온다.

묻고 싶은 것은 *"이 인스턴스가 로그를 남기나"* 가 아니라 **"앱이 로그를 남기나"** 다.

```promql
sum by (job) (increase(logback_events_total[10m])) == 0
```

**라벨을 남길 때마다 "이 라벨로 갈라서 물어도 뜻이 같은가" 를 봐야 한다.**
같은 실수를 한 겹 얕게 다시 했다.

## 곁가지 — 규칙을 고치니 규칙을 검사하는 시험이 깨졌다

`AlertMetricsExposedTest` 는 규칙 파일에서 지표 이름을 뽑아 앱의 노출 목록과 대조한다.
PromQL 을 제대로 파싱하지는 않고, 중괄호 안을 지운 뒤 지표처럼 생긴 식별자를 남긴다.

새 식이 그 어림짐작을 벗어났다.

```promql
sum by (job, instance) (increase(logback_events_total[10m])) == 0
```

`job` 과 `instance` 는 **라벨 이름인데 중괄호 밖에 있다.** 그래서 지표로 잡혔고
"앱이 `job` 이라는 지표를 안 낸다" 며 빨개졌다. `count_over_time` 도 함수 목록에 없었다.

집계 절(`by` · `without` · `on` · `ignoring`)의 괄호를 통째로 지우도록 고쳤다.
고친 뒤에도 **진짜 위반은 여전히 잡는지** 확인했다 —
없는 지표를 규칙에 넣어 그 시험만 빨개지는 것을 봤다.

파서를 느슨하게 만들어 통과시키는 것이 제일 쉬운 길이었는데,
그러면 이 시험이 하는 일이 사라진다.

---

## 이 일이 말해 주는 것

규칙 파일을 커밋하는 것과 그 규칙이 도는 것은 다른 일이다.
그 사이가 끊겨 있으면(#174) **규칙이 틀렸다는 사실조차 알 수 없다.**
문법은 `promtool` 이 통과시키고, 리뷰는 사람이 통과시킨다.
틀렸다는 것은 **돌려 봐야만** 드러난다.

그래서 지금은 배포가 리로드하고, 리로드한 뒤 개수를 대조하고,
울리고 있는 것이 있으면 그것도 본다.

새로 넣은 규칙은 **실제 데이터로 두 방향을 다 확인한다** —
울려야 할 때 울리는지, 그리고 울리면 안 될 때 조용한지.
한쪽만 보면 절반만 확인한 것이다.
