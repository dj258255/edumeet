> 작성 2026-08-22 · 상태: 계획

## 0. 이 문서의 목적

기능을 나열하는 문서가 아니다. **무엇을 만들지보다 무엇을 측정할지**를 먼저 정한다.
지금까지의 작업(#17, #19)이 그랬듯, 각 단계는

```
가설 -> 구현 -> 측정 -> 결론(도입 / 미도입, 근거 기록)
```

순으로 진행한다. **측정 계획이 없는 단계는 만들지 않는다.**

---

## 1. 현재 상태

| | |
|---|---|
| WebSocket | **없음.** 프로젝트에 코드 0줄 |
| 채팅 | **없음** |
| 영상 | LiveKit(WebRTC). 시그널링은 LiveKit이 자체 처리 |
| HLS | **없음.** 다시보기(VOD)도 없음 |
| 세션 타입 | `INTERACTIVE`(화상강의) / `BROADCAST`(라이브방송) — #2 에서 도입 |

`BROADCAST` 를 만들어놓고 채팅이 없는 것은 부자연스럽다. 라이브 방송에서 채팅은
부가 기능이 아니라 **본체의 절반**이다.

---

## 2. 핵심 설계 판단 — 두 채팅은 요구사항이 반대다

이것이 이 작업의 지적 중심이다. **하나의 채팅을 만들어 양쪽에 붙이면 틀린다.**

| | `INTERACTIVE` 화상강의 | `BROADCAST` 라이브방송 |
|---|---|---|
| 인원 | 정원 제한 (기본 30) | 제한 없음 (수천) |
| fan-out | 메시지 1건 → 쓰기 **30회** | 메시지 1건 → 쓰기 **수천 회** |
| 이력 | **보존해야 함** (수업 기록·질의응답) | 휘발 (최근 N건이면 충분) |
| 메시지 유실 | **허용 안 됨** | 허용 (도배 상황에서 일부 드롭 가능) |
| 순서 보장 | 엄격 | 느슨 |
| 저장소 | MySQL | Redis 최근분 or 저장 안 함 |
| rate limit | 느슨 | **엄격** (도배 방지) |
| 발언 권한 | 전원 | 전원 (단, 영상은 단방향) |

**결론** — 전송 계층은 공유하되 **정책은 `SessionType` 으로 분기**한다.
#2 에서 만든 `hasParticipantLimit()` / `allowsParticipantPublish()` 옆에
`persistsHistory()`, `allowsMessageDrop()` 이 붙는 형태다.

> 이 분기가 억지가 아니라는 근거는 **fan-out 수치**로 보인다. Phase 2 에서 잰다.

## 3. 단계별 계획

각 Phase 는 이슈 1개 + PR 1개로 간다. **Phase 4 까지 끝나면 포트폴리오는 성립한다.**
Phase 5 부터는 시간이 남을 때만 한다.

### Phase 1 — WebSocket 채팅 최소 동작 (단일 인스턴스)

**만들 것**

```
브라우저 ──WebSocket──> Spring ──> 방 단위 브로드캐스트
                          │
                          └─> MySQL (INTERACTIVE 만)
```

- STOMP + Spring `SimpleBroker` 로 시작한다
- 방 = `meetingId`. 입장 권한은 기존 `MeetingParticipant` 로 검증한다
- `SessionType` 별 정책 분기 (이력 저장 여부, rate limit)

**왜 STOMP 로 시작하나** — 가장 빨리 동작한다. `SimpleBroker` 는 단일 JVM 안에서만
동작하고 성능 한계가 있다고 알려져 있는데, **그 한계가 몇 명에서 나타나는지를 재는 것이
Phase 2 의 목적**이다. 처음부터 raw WebSocket 으로 가면 "무엇을 피했는지" 를 말할 수 없다.

**측정 계획** — 없음. 동작 확인만.

---

### Phase 2 — fan-out 부하 측정

**가설** — 연결 유지는 싸고 **브로드캐스트가 비싸다.** 비용은 인원 수에 비례한다.

**측정**

```bash
k6 run -e ROOM_SIZE=30   k6/chat-fanout.js   # 화상강의 규모
k6 run -e ROOM_SIZE=300  k6/chat-fanout.js
k6 run -e ROOM_SIZE=1000 k6/chat-fanout.js   # 라이브 규모
k6 run -e ROOM_SIZE=3000 k6/chat-fanout.js
```

| 재는 것 | 왜 |
|---|---|
| 메시지 전파 지연 (발신 → 마지막 수신자) p50/p95/p99 | 체감 지표 |
| 초당 처리 메시지 수 | 처리량 |
| 연결당 메모리 | *"Java 는 연결 많으면 죽는다"* 를 실측으로 확인/반박 |
| 앱 CPU (#17 과 같은 방식) | 병목 위치 |
| `SimpleBroker` 스레드 상태 | 브로커가 병목인지 |

**예상되는 결론 후보**
- (a) `SimpleBroker` 가 특정 인원에서 무너진다 → raw WebSocket + 자체 fan-out 으로 교체
- (b) 무너지지 않는다 → 교체하지 않고 근거를 기록한다

**어느 쪽이든 결과다.** (b) 여도 *"바꿀 뻔했는데 재보니 필요 없었다"* 로 #17 의
`쿼리 수는 대리 지표` , [06 문서](../performance/06-lock-determinism.md)와 같은 계열의 기록이 된다.

### Phase 3 — 백프레셔: 느린 시청자 하나가 방 전체를 막는가

**이 Phase 가 이 작업에서 가장 값이 크다.** 신입 포트폴리오에서 거의 나오지 않는다.

**가설** — 브로드캐스트는 N명에게 순차적으로 쓴다. 그중 한 명의 소켓 버퍼가 가득 차면
쓰기가 블로킹되고, **나머지 N-1명의 메시지가 밀린다.**

**재현 방법** — #19 에서 이미 띄운 Toxiproxy 를 쓴다.

```
정상 시청자 N-1명 ──────────────> Spring
느린 시청자 1명   ──[bandwidth 제한]──> Spring
```

`bandwidth` toxic 으로 특정 연결만 좁힌다. 그 상태에서 정상 시청자들의
메시지 전파 지연이 어떻게 되는지 잰다.

**대응 선택지 (측정 후 결정)**

| 방식 | 대가 |
|---|---|
| 느린 연결 강제 종료 | 그 사용자는 끊긴다 |
| 연결별 송신 큐 + 상한 초과 시 드롭 | 그 사용자만 메시지를 잃는다 |
| 비동기 논블로킹 전송 | 구현 복잡도 |

**`SessionType` 이 여기서도 갈린다** — `BROADCAST` 는 드롭 허용,
`INTERACTIVE` 는 유실 불가라 다른 정책이 필요하다.

### Phase 4 — 다중 인스턴스 확장

**먼저 버그를 재현한다.** 인스턴스 2대를 띄우고 같은 방에 접속시키면
**서로의 메시지가 안 보인다.** `SimpleBroker` 는 JVM 안에서만 동작하기 때문이다.

```
시청자 A ──> 인스턴스 1 ──X──> 시청자 B (인스턴스 2)
```

이걸 먼저 측정으로 보이고, 그 다음에 해결한다. (#19 에서 대조군을 먼저 잰 것과 같다)

**해결** — Redis Pub/Sub. **프로젝트에 Redis 가 이미 있다.**

```
인스턴스 1 ──publish──> Redis ──subscribe──> 인스턴스 2
```

**측정** — 인스턴스 간 전파 지연이 얼마나 추가되는지.

---

### 4-1. NATS 는 왜 안 쓰나 (또는 언제 쓰나)

> 사전에 채택 기준을 정해둔다. 재고 나서 기준을 만들면 결과에 맞춰 논리를 짜게 된다.

**NATS 가 주는 것**

| | |
|---|---|
| 지연 | sub-ms 급. 팬아웃 전용 설계 |
| 주제 계층 | `chat.room.123`, 와일드카드 구독 (`chat.room.*`) |
| 클러스터링 | 내장 |
| JetStream | 지속성·재전송·at-least-once |

**Redis Pub/Sub 의 약점 (NATS 가 해결하는 것)**

- **at-most-once 다.** 구독자가 없거나 순간적으로 끊기면 **메시지가 사라진다.**
- **백프레셔가 없다.** 느린 구독자는 버퍼 상한(`client-output-buffer-limit pubsub`)에
  걸려 **연결이 끊긴다.**
- 채널 수가 많아지면 관리가 거칠다.

**그런데 지금 도입하지 않는 이유**

1. **Redis 가 이미 있다.** NATS 는 운영 대상 하나가 더 늘어난다.
   그 값을 지불할 근거가 아직 **측정으로** 나오지 않았다.
2. **라이브 채팅은 유실을 허용한다.** 위 표에서 정한 대로 `BROADCAST` 는
   at-most-once 로 충분하다. NATS Core 도 at-most-once 라 **이 요구사항만 보면 차이가 없다.**
   차이가 나는 건 JetStream 인데, 그건 `INTERACTIVE` 이력 보존용이고
   **그건 이미 MySQL 이 한다.**
3. #17·[06](../performance/06-lock-determinism.md) 에서 세운 원칙 —
   **필요하다고 생각한 것을 재보니 필요 없었던 사례가 이미 있다.** 같은 실수를 반복하지 않는다.

**언제 도입하나 — 사전 등록 기준**

아래 중 **하나라도** 측정에서 나오면 NATS 를 도입하고, 그 수치를 근거로 기록한다.

- [ ] Redis Pub/Sub 경유 전파 지연 p95 가 **50ms** 를 넘는다
- [ ] 부하 중 `client-output-buffer-limit` 로 인스턴스 구독이 **끊긴다**
- [ ] 메시지 유실률이 `BROADCAST` 허용치(**1%**)를 넘는다
- [ ] Redis 가 채팅 때문에 세션·캐시 용도에 지장을 준다 (CPU/메모리 경합)

**여유가 되면 A/B 로 잰다.** 기준에 안 걸려도 *"Redis 는 X ms, NATS 는 Y ms 였고
차이가 Z 라 도입하지 않았다"* 가 *"안 써봤다"* 보다 훨씬 강하다.

> **Kafka 는 후보에서 뺀다.** 채팅 fan-out 에는 지연·운영 부담이 과하다.
> Kafka 가 맞는 자리는 채팅 로그 적재·분석 파이프라인이지 실시간 전파가 아니다.

### Phase 5 — HLS (여기부터는 시간이 남을 때)

**범위를 먼저 자른다.** 이 영역은 끝없이 커진다.

| 선택지 | 난이도 | 판단 |
|---|---|---|
| A. LiveKit Egress → HLS | 중 | **채택.** 공식 경로. 컨테이너 하나 추가 |
| B. 별도 RTMP ingest + FFmpeg 직접 | 상 | 제외. LiveKit 을 쓰는데 파이프라인을 또 만들 이유가 없다 |
| C. 녹화 파일 → HLS 변환 (VOD) | 하 | **폴백.** A 가 막히면 이걸로 |
| LL-HLS (저지연) | 상 | **제외.** 함정. 표준 HLS 도 안 해본 상태에서 갈 곳이 아니다 |

**측정할 것 — 핵심 트레이드오프 하나**

```
세그먼트 길이 ↓  →  재생 지연 ↓   요청 수 ↑   오버헤드 ↑
세그먼트 길이 ↑  →  재생 지연 ↑   요청 수 ↓   안정성 ↑
```

세그먼트 2초 / 4초 / 6초로 바꿔가며

- 방송 시작 → 시청자 첫 프레임까지 걸리는 시간
- 실시간 대비 지연 (glass-to-glass 근사)
- 세그먼트 요청 수 · 총 전송량

를 잰다. **이 표 하나가 HLS 를 이해했다는 증거다.**

**ABR(다중 화질)** — 시간이 남으면. 240p/480p/720p 래더를 만들고
대역폭을 Toxiproxy 로 좁혀 **실제로 화질이 내려가는지** 확인한다.
*"래더를 만들었다"* 가 아니라 *"좁혔더니 내려갔다"* 를 보여야 한다.

**자체 플레이어** — `hls.js` 를 쓴다. HLS 파서를 직접 만들지 않는다(함정).
대신 **버퍼 상태·현재 화질·전환 시점을 화면에 노출하는 계측 플레이어**로 만든다.
그래야 위 측정을 눈으로 보여줄 수 있다.

## 4. 우선순위와 중단 지점

```
Phase 1  채팅 최소 동작          ★★★  반드시
Phase 2  fan-out 측정            ★★★  반드시
Phase 3  백프레셔                ★★★  반드시 ← 가장 차별화됨
Phase 4  다중 인스턴스 + Redis    ★★☆  가능하면
  4-1    NATS 비교               ★☆☆  여유 있으면
Phase 5  HLS                     ★★☆  가능하면
  ABR / 자체 플레이어             ★☆☆  여유 있으면
Phase 6  문서                    ★★★  반드시
```

**Phase 3 까지 끝나면 멈춰도 된다.** 그 지점에서 이미

> *"라이브 채팅을 만들고, 느린 시청자 하나가 방 전체를 막는 것을 측정으로 발견해
> 정책으로 해결했다"*

가 성립한다. Phase 4·5 는 여기에 얹는 것이지 없으면 안 되는 것이 아니다.

**포트폴리오 문서와 자소서가 Phase 5 보다 우선이다.** 만들어놓고 안 쓰면 0점이다.

## 5. 미리 정해두는 것들

**측정 원칙은 [개발 컨벤션 1.6](../team-convention.md) 을 그대로 따른다.**
워밍업 분리, 운영과 같은 DB, 대조군 병행, 한계 명시.

**하지 않기로 이미 정한 것**

| | 이유 |
|---|---|
| LL-HLS | 표준 HLS 도 안 해봤다. 순서가 아니다 |
| Kafka | 채팅 실시간 전파에는 지연·운영 부담이 과하다 |
| 서킷 브레이커 | [#19](https://github.com/dj258255/edumeet/issues/19) 와 같은 이유. 근거가 나오면 그때 |
| HLS 파서 직접 구현 | `hls.js` 로 충분하다. 여기에 시간을 쓰면 측정을 못 한다 |
| NATS (현재) | 위 4-1 의 사전 등록 기준에 걸리면 그때 |

**언어는 Java 를 유지한다.** 라이브 스트리밍의 **미디어 코어**(코덱·패킷·트랜스코딩)는
C/C++ 영역이 맞지만, 이 작업은 그 위의 **플랫폼 계층**이다. fan-out·백프레셔·
분산 전파는 언어가 아니라 설계 문제이고, Java(Netty 계열)로 같은 방식으로 푼다.
