# 오디오 라이브 방송 — 라디오를 "볼 수 있게" 만든다

> 계획 · #65 · 아직 측정 없음

## 0. 문제 정의

**라디오는 청각장애인에게 접근이 원천 차단된 매체다.**

자막이 붙는 TV·영화와 달리 오디오 전용 방송에는 붙일 자리가 없다.
그리고 **EduMeet 은 이미 실시간 STT 자막 파이프라인을 갖고 있다.**

```
지금    화상강의 ─── 오디오 ──→ STT ──→ 자막
없음    오디오 방송 ──────────→  ?
```

같은 파이프라인인데 **입구가 없다.**

> **질문:** 오디오 전용 라이브 방송을 붙이면 대역폭·비용·구조가 어떻게 달라지는가?

이건 기능 추가가 아니라 **이미 있는 자산(STT)을 접근 불가능한 매체에 연결하는 일**이다.

---

## 1. 지금 구조의 한계 — 송출과 배포가 같은 프로토콜이다

```
지금    발행자 ──WebRTC──> LiveKit ──WebRTC──> 시청자
```

**같은 프로토콜로 받고 같은 프로토콜로 뿌린다.** 그래서:

| | |
|---|---|
| CDN 캐싱 | **원천 불가.** 커넥션마다 SRTP 키가 달라 같은 바이트를 재사용할 수 없다 |
| 오리진 부담 | 시청자 수에 **선형 비례** |
| 임계 | [비용 모델](../ops/02-egress-cost-model.md) 기준 **시청자 7,400명 × 1시간** 이면 무료 한도 소진 |

### Spoon Radio 의 Echo 는 이걸 나눴다

```
Echo    DJ ──SRT/RTMP──> 서버 ──HLS──> 청취자
                           └──> 녹음(AAC/M4A) = '캐스트'
```

**송출은 저지연 프로토콜, 배포는 CDN 을 탈 수 있는 프로토콜.**
그리고 서버가 녹음해서 VOD 로 재활용하고, **분쟁 시 증거로도 쓴다.**

> Echo 는 SRT·RTMP·MP4·HLS 를 **전부 Rust 로 직접 구현**했다.
> 우리는 그 계층을 만들지 않는다 — 그 판단의 근거는
> [언어 경계 조사](../research/04-language-boundary.md)에 있다.
> **가져올 것은 코드가 아니라 "구간별로 프로토콜을 나눈다" 는 구조다.**

---

## 2. 오디오라서 달라지는 것 — 숫자로

측정 기준점은 [비용 모델](../ops/02-egress-cost-model.md)의 실측 하나에서 나온다.

| | 비트레이트 | 시청자당 시간당 | 무료 10TB 소진 |
|---|---:|---:|---:|
| 비디오 (LiveKit 실측) | 1.42 Mbps | 0.622 GB | **7,400 시청자-시간** |
| 오디오 128 kbps | 0.128 Mbps | 0.056 GB | **약 82,000 시청자-시간** |
| 오디오 64 kbps (음성) | 0.064 Mbps | 0.028 GB | **약 164,000 시청자-시간** |

**11~22배 차이다.**

> 비디오에서 *"비용보다 가용성이 먼저 터진다"* 였는데,
> **오디오면 그 격차가 한 자릿수 더 벌어진다.** 2 OCPU VM 이 훨씬 먼저 한계다.

### 그래서 이 프로젝트에서 오디오 방송은 "싸서" 하는 게 아니다

대역폭은 애초에 문제가 아니었다. **하는 이유는 접근성이다.**
다만 **싸다는 사실이 "해볼 수 있다" 를 만든다** — 개인 서버에서 실측 가능한 규모다.

---

## 3. 설계 — 어디까지 만들고 어디부터 안 만드나

### 만든다

```
발행자 ──WebRTC(오디오만)──> LiveKit ──> 구독자
                               │
                               ├─> STT ──> 자막 브로드캐스트 (WebSocket)
                               └─> 녹음 ──> VOD + 다시보기 자막·채팅
```

| | 근거 |
|---|---|
| **오디오 전용 세션 타입** | `SessionType` 에 세 번째 값. 정원·발행 권한·저장 정책이 또 갈린다 |
| **자막 실시간 브로드캐스트** | 채팅 fan-out 인프라(#33·#39)를 그대로 쓴다. **새로 만들 게 없다** |
| **녹음 + 다시보기** | Echo 의 '캐스트'. #61 과 같은 축 |

### 만들지 않는다

| | 근거 |
|---|---|
| SRT/RTMP 인제스트 | LiveKit Ingress 를 띄우면 되지만 **측정할 질문이 없다.** 프로토콜을 늘려도 배우는 게 없다 |
| HLS 배포 | [별도 문서](02-hls-optional.md)에 이미 계획이 있다. **오디오 방송이 먼저 서면 그때 붙인다** |
| 자체 미디어 서버 | Echo 가 Rust 로 한 일. **우리는 프로토콜 바이트를 만지지 않는다** |

## 4. 무엇을 측정할 것인가

**기능을 붙이는 게 목적이 아니다. 이 질문들에 숫자로 답하는 게 목적이다.**

| # | 질문 | 어떻게 |
|---|---|---|
| 1 | 오디오 전용이면 대역폭이 실제로 몇 배 줄어드나 | LiveKit 지표 · 위 표는 계산값이다 |
| 2 | 자막 브로드캐스트는 채팅과 부하 특성이 같은가 | **다르다고 본다** — 자막은 발신자 1명, 채팅은 N명. fan-out 배수는 같고 발행량이 다르다 |
| 3 | STT 지연이 실시간 자막으로 쓸 만한가 | 발화 → 자막 도착까지 end-to-end. **채팅에서 쓴 `publishedAt` 방식 그대로** |
| 4 | 녹음이 브로드캐스트 지연에 영향을 주나 | #43 하네스 재사용 |

### 2번이 특히 중요하다

```
채팅     발신자 N명 × 각자 가끔   → 발행량이 시청자 수에 비례
자막     발신자 1명 × 끊임없이    → 발행량이 시청자 수와 무관
```

**같은 fan-out 인프라인데 부하 형태가 반대다.**
채팅은 발행량이 문제고, 자막은 **한 발신자의 지연**이 문제다.
#43 에서 만든 큐 상한이 자막에 맞는 값인지는 **다시 재봐야 안다.**

---

## 5. 순서

```
1. 오디오 세션 타입 + 발행 권한        측정 없음. 대상을 만든다
2. 자막 브로드캐스트 (STT -> WebSocket) 채팅 인프라 재사용
3. 자막 end-to-end 지연 측정            질문 3
4. 자막 vs 채팅 부하 특성 비교          질문 2 ★
5. 녹음 + 다시보기                      #61 과 합류
```

**3·4번이 이 계획의 값어치다.** 1·2는 그걸 재기 위한 준비다.

---

## 6. 미확인

- **오디오 비트레이트 실측을 아직 안 했다.** 위 표는 128/64 kbps 가정에서 나온 계산이다
- LiveKit 이 오디오 전용 세션에서 실제로 얼마를 쓰는지 — 비디오처럼 공식 벤치마크가 있는지 확인 못 했다
- STT 파이프라인의 실시간성 — 지금은 **회의 종료 후 요약본**을 받는 구조다.
  실시간 자막은 **파이썬 쪽 구조가 다를 수 있다.** 저장소가 이 리포에 없어 확인 불가
- 녹음을 LiveKit Egress 로 할지 앱에서 할지
