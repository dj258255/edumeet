# 100명 화상채팅을 어떻게 볼 것인가

EduMeet 의 화상채팅 목표를 Zoom 같은 최대 100명 회의로 잡으면,
직접 WebRTC mesh 로 구현하는 것은 현실적이지 않다.

1:1 은 P2P WebRTC 로 충분하다.
하지만 100명 방에서 모든 참가자가 서로 직접 연결되면,
각 브라우저가 유지해야 하는 연결 수와 업로드/다운로드 부담이 급격히 커진다.

그래서 이 규모에서는 SFU 구조가 필요하다.

```
참가자 A ─┐
참가자 B ─┼─ LiveKit SFU ─ 필요한 구독자에게만 트랙 전달
참가자 C ─┘
```

LiveKit 을 쓰는 이유는 "튜토리얼을 붙였다"가 아니다.
WebRTC 다자간 회의에는 SDP/ICE, STUN/TURN, RTP/RTCP, simulcast, adaptive stream,
NACK/PLI, bandwidth estimation 같은 요소가 같이 움직인다.
이것을 직접 구현하면 포트폴리오의 중심이 교육 플랫폼이 아니라 미디어 서버가 된다.

## 현재 구현

현재 EduMeet 은 화상채팅에서 LiveKit 을 WebRTC SFU 로 사용한다.
방송 HLS 에서 LiveKit Egress 를 걷어냈을 뿐, 화상채팅에서 LiveKit 을 제거하지 않았다.

프론트에서는 `Room` 생성 시 다음 옵션을 켠다.

```ts
new Room({
  adaptiveStream: true,
  dynacast: true,
})
```

의도는 두 가지다.

| 옵션 | 의미 |
|---|---|
| `adaptiveStream` | 화면에 실제로 필요한 비디오 레이어만 받도록 돕는다 |
| `dynacast` | 구독자가 없는 비디오 레이어는 송출을 줄이도록 돕는다 |

이것은 100명 정책의 시작이지 완성은 아니다.
SDK 옵션만으로 "100명 회의 설계"가 끝났다고 말하면 안 된다.

## 아직 필요한 정책

100명이 모두의 영상을 동시에 주고받는 구조는 비현실적이다.
SFU 를 쓰더라도 구독 정책이 필요하다.

| 정책 | 이유 |
|---|---|
| 동시 카메라 송출자 제한 | 모든 사람이 HD 영상을 올리면 SFU 이전에 클라이언트가 무너진다 |
| 화면에 보이는 참가자만 video subscribe | 보이지 않는 영상은 받을 이유가 없다 |
| active speaker 중심 전환 | 수업 화면에서 실제로 필요한 영상은 말하는 사람과 발표자다 |
| 나머지는 audio-only 또는 저해상도 thumbnail | 대역폭과 디코딩 비용을 줄인다 |
| 발표자/청중 역할 분리 | 청중의 publish 권한을 기본으로 열어 두면 비용 예측이 깨진다 |
| 모바일은 audio 우선 | 모바일 CPU·네트워크·배터리 비용이 더 크다 |
| 네트워크 상태가 나쁘면 video unsubscribe | 화질 저하보다 수업 연결 유지가 먼저다 |
| TURN relay 비용 측정 | NAT 환경에서는 TURN 이 비용 중심이 될 수 있다 |

## 합성 비용은 어디서 드는가

화상채팅 자체에는 화면 합성 비용이 없다.
SFU 는 트랙을 전달한다.

합성 비용은 녹화나 방송처럼 여러 참가자의 화면을 하나의 영상으로 만들어야 할 때 생긴다.
LiveKit Egress 의 `RoomComposite` 가 CPU 를 크게 요구하는 이유도 여기에 있다.

| 경로 | 합성 비용 | 설명 |
|---|---|---|
| 화상채팅 SFU | 없음 | 참가자별 트랙을 라우팅한다 |
| 화면 녹화/RoomComposite | 있음 | 여러 화면을 레이아웃으로 합성하고 다시 인코딩한다 |
| 발표자 1명 라이브 방송 | 없음 | 합성 대상이 없다. 그래서 직접 HLS 로 대체했다 |

## 포트폴리오에서 말할 선

이렇게 말하는 것이 정확하다.

> 최대 100명 규모의 화상채팅을 목표로 했기 때문에 P2P mesh 는 적합하지 않다고 판단했습니다.
> 그래서 화상채팅은 LiveKit SFU 로 두고, 방송 HLS 에서만 LiveKit Egress 를 제거했습니다.
> 방송은 발표자 한 명의 단방향 송출이라 화면 합성이 필요 없었기 때문입니다.
>
> 다만 100명이 동시에 모든 영상을 송수신하는 구조는 비현실적이므로,
> `adaptiveStream`/`dynacast` 를 켜고, 다음 단계로 active speaker·가시 영역·역할 기반 구독 정책을 설계했습니다.

반대로 이렇게 말하면 과장이다.

> LiveKit 을 붙였기 때문에 100명 회의가 됩니다.

LiveKit 은 필요한 기반이고, 100명 회의의 핵심은 그 위의 publish/subscribe 정책이다.
