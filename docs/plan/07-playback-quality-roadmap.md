# 07. 시청 품질을 재고, 그 숫자로 정하고, 몰릴 때 지킨다

> 작성 2026-09-23 · 추적 이슈 [#202](https://github.com/dj258255/edumeet/issues/202)
> **이 문서는 진행 중에 계속 고친다.** 예상이 틀리면 그날 고치고 이유를 남긴다.

## 0. 왜 시작하나

[#193](../performance/28-latency-knobs.md) 에서 지연을 4.82초에서 1.51초로 줄일 수 있다는 것을 쟀다.
그런데 **안 바꿨다.** 그 손잡이는 버퍼를 깎는 것과 같은 일이고, 대가인 재생 끊김을 잴 수단이 없었다.

그때 적어 둔 조건이 이것이다.

```
p95 가 5초를 계속 넘고, 재생 끊김을 잴 수단이 생기면  ->  liveSync 를 1로 내린다
```

찾아보니 수단의 절반은 이미 있었다. `frontend/src/features/broadcast/hlsMetrics.js` 가
버퍼·지연·대역폭·드롭 프레임을 **매초 계산한다.** 그런데 결과가 그 시청자 화면에만 뜨고
서버로 오지 않는다. 그리고 끊김(`waiting`)과 첫 화면까지의 시간은 아예 세지 않는다.

**계산은 하는데 아무도 못 본다** — 이 저장소에서 여러 번 만난 모양이다.

## 1. 목표와 순서

```
M1 보이게 만든다    시청자의 끊김·첫 화면 시간이 서버에 온다. 그 숫자가 맞는지 대조한다
M2 그 숫자로 정한다  liveSync · 송출 비트레이트를 지연·화질·끊김으로 결정
M3 몰릴 때 지킨다    400명 구간에서 송출 조각 업로드가 밀리는지 재고, 밀리면 우선순위로 지킨다
M4 유실 경계        다시보기 채팅 저장의 유실 경로 넷을 재고 저장 방식을 정한다 (독립)
M5 문서 반영
```

**M2 · M3 는 M1 의 숫자가 있어야 판단할 수 있다.** liveSync 를 내리면 끊김이 느는지,
우선순위로 지킨 뒤 시청자 끊김이 줄었는지 — 둘 다 끊김을 재는 수단이 먼저다.

M3 · M4 는 **게이트 측정부터** 한다. 문제가 없으면 구현하지 않고 기각으로 적는다.

## 3. 먼저 정한 설계 — 시청 품질 수집

| 결정 | 채택 | 버린 대안 |
|---|---|---|
| 무엇을 | **30초 주기 누적 요약** + 떠날 때 마지막 요약 | 끊김 이벤트만 — **분모(끊김 없이 본 시간)가 없어 리버퍼율을 못 낸다** / 매초 스냅샷 — 300명에 초당 300건 |
| 어디로 | 별도 HTTP | STOMP — 미디어·채팅 경로를 나눈 원칙([`05`](05-own-hls.md))과 충돌하고, **몰릴 때 경로로 골라 버릴 수 없다** |
| 어디에 | Prometheus 는 **라벨 없는 합계**, 세션 단위는 JSON 로그 → Loki | MySQL — 운영 DB 쓰기 / meetingId 라벨 — 카디널리티 |
| 떠날 때 | `pagehide` 에서 `fetch keepalive` | `sendBeacon` — 토큰이 Authorization 헤더라 못 싣는다 |
| 입력 | 서버가 상한을 건다. 넘으면 버리고 센다 | 그대로 받기 — 클라이언트 하나가 합계를 오염시킨다 |

## 4. 주요 불확실성

| | 영향 | 언제 알게 되나 |
|---|---|---|
| 헤드리스 브라우저를 몇 대까지 띄우나 | 대조 표본 크기. 적으면 대조는 N대, 부하는 k6 로 가른다 | #197 대조 첫날 |
| `keepalive` + preflight 로 탭 종료 때 마지막 보고가 도착하나 | 떠난 시청자의 마지막 30초 | #197 브라우저 확인 |
| MediaRecorder 1초 조각이 1초 세그먼트가 되나 | #193 의 1.51초 재현 여부 | #198 첫 측정 |
| VMAF 와 OCR 이 같은 방향으로 움직이나 | 갈라지면 그 자체가 결과 | #199 중반 |
| 운영 서버의 다른 부하 컨테이너 두 개 (측정 시점 CPU 0.00%) | 측정 중 깨어나면 잡음 | 매 측정 직전 CPU 기록 |
