# HLS 를 직접 만든다 — LiveKit egress 를 걷어낸 이유 (#123)

## 시작은 잘못된 결론이었다

`docs/plan/02-hls-optional.md` 에 **"2코어라 비디오 방송 HLS 를 못 한다"** 고 적어 뒀다.
egress 를 실제로 띄워 보니 절반만 맞았다.

```
ERROR  not enough cpu for some egress types
       minimumCpu: 4  recommended: 4  available: 2
INFO   service ready                              ← 그러고도 뜬다
```

`minimumCpu: 4, available: 2` 를 보면 누구나 *"최소 4개 필요한데 2개뿐"* 으로 읽는다.
그런데 LiveKit 소스를 보면

```go
logger.Errorw("not enough cpu for some egress types", nil,
    "minimumCpu", requirements[len(requirements)-1],   // ← 최댓값이 들어간다
```

**`minimumCpu` 라는 이름으로 최댓값이 찍힌다.** 실제 하한은 `trackCpuCost = 0.5` 이고,
오디오 방송은 1이라 2코어에서 돈다. **이름이 잘못된 로그 필드 하나가 기능 하나를 접게 만들었다.**

## 그런데 더 큰 것이 보였다 — 합성이 필요 없다

egress 의 `RoomComposite` 가 CPU 4를 요구하는 이유는

> **여러 참가자 화면을 헤드리스 Chrome 으로 레이아웃 렌더링해서 하나로 합성**하기 때문이다.

**방송 모드는 발표자 한 명만 나간다. 합성할 것이 없다.**

합성이 필요 없는데 합성기를 쓰고 있었고, 그 대가로 2코어에서 비디오 방송을 포기하고 있었다.
`SYS_ADMIN`·Chrome·Xvfb·Redis 도 전부 그 합성기 때문에 필요했던 것이다.

## 구조

```
발표자 브라우저 MediaRecorder(2초 조각)
   │ webm/mp4
   ▼ POST /api/v1/meeting/{id}/broadcast/chunk        ← HTTP 다. 채팅만 WebSocket 을 쓴다
백엔드  순서 버퍼 → 유계 큐 → ffmpeg stdin
   ▼
ffmpeg  세그먼트(.ts) + live.m3u8
   ▼
nginx /hls/  →  시청자 <video> + hls.js
```

**채팅과 미디어의 경로를 나눈 이유:** 미디어를 WebSocket 에 얹으면 방송이 밀릴 때
채팅도 같이 밀린다. 나누면 한쪽이 막혀도 다른 쪽은 산다.

**세그먼트를 nginx 가 파일로 내보내는 이유:** 앱이 서빙하면 시청자가 늘 때마다
톰캣 스레드를 먹는다. 파일로 내보내면 **시청자가 늘어도 서버 연산은 그대로다.**

## 실측 — 세 경로의 CPU (60초 분량, 720p30)

| 경로 | user CPU | 실시간 대비 |
|---|---:|---:|
| **리먹싱** (H264 그대로 복사) | **0.06초** | 0.1% |
| **재인코딩** (VP8 → H264) | **12.34초** | 20.6% |
| **오디오 전용** (Opus → AAC) | **0.56초** | 0.9% |

> 노트북(Apple Silicon) 수치다. 서버(OCI aarch64 2 OCPU)에서 다시 잰다.

**200배 차이다.** 그래서 브라우저가 H264 를 주는지 아닌지가 결정적이고,
클라이언트는 H264 를 먼저 시도하고 **실제로 정해진 값**을 서버에 보낸다.
(MediaRecorder 는 못 쓰는 mimeType 을 조용히 바꾼다.)

## ★ 리먹싱은 공짜가 아니다 — 지연 통제권을 브라우저에 넘긴다

HLS 세그먼트는 키프레임에서 시작해야 한다(Apple HLS 스펙 7.4).
그런데 `-c:v copy` 는 프레임을 그대로 옮기므로 **키프레임을 새로 만들 수 없다.**

같은 소스(키프레임 5초 간격)에 `hls_time 2` 를 준 결과다.

```
리먹싱     → 5.000  5.000  5.000  5.000        요청은 2초였다
재인코딩   → 2.000  2.000  2.000  2.000 ...    강제된다
```

HLS 체감 지연은 대략 **세그먼트 길이 x 3**(플레이어가 보통 3개를 버퍼링한다)이므로

| | 세그먼트 | 대략 지연 |
|---|---:|---:|
| 리먹싱, 브라우저 키프레임이 5초면 | 5초 | **~15초** |
| 재인코딩, `-g` 로 강제하면 | 2초 | **~6초** |

**CPU 200배를 아끼는 대신 지연을 브라우저 손에 맡기는 것이다.** 공짜가 아니라 교환이다.

## 운영에서 터지는 것들을 먼저 막았다

| | 안 막으면 | 어떻게 |
|---|---|---|
| ffmpeg stderr 를 아무도 안 읽음 | 파이프가 차서 **ffmpeg 가 이유 없이 멈춘다** | 전용 스레드가 계속 읽는다 |
| stdin 쓰기가 요청 스레드를 붙잡음 | 톰캣 스레드가 묶인다 | 유계 큐 + 전용 쓰기 스레드 |
| 큐가 무한 | **메모리가 터진다** (이 프로젝트에서 채팅으로 이미 겪었다) | 상한 + 넘치면 **429 로 거부** |
| 청크 순서 뒤바뀜 | 에러 없이 **영상이 깨진다** | 순서 버퍼, 창을 넘으면 실패 |
| 발표자가 탭을 닫음 | stop 이 안 와서 **ffmpeg 가 영원히 남는다** | 유휴 30초면 정리 |
| 동시 방송 무제한 | 2코어에서 **전체가 멈춘다** | 상한 2, 재인코딩은 1 |
| 세그먼트를 안 지움 | 디스크가 방송 내내 찬다 | `delete_segments` |
| `omit_endlist` 누락 | 라이브가 **VOD 로 재생된다** (처음부터 튼다) | 플래그 + 시험 |

**429 를 200 으로 바꾸고 싶은 유혹이 크다.** 그러면 발표자 화면은 조용해지지만
조각이 버려져 영상이 깨진다. 거부해야 발표자가 안다.

## 안 만든 것

- **다시보기(VOD) 영상.** 송출은 `delete_segments` 로 도니 세그먼트가 남지 않는다.
  다시보기를 하려면 별도 녹화 경로가 필요하고, 지금은 없다.
  `Meeting.stopBroadcast()` 주석에 그 사실을 적어 뒀다 — 주소는 남지만 그 주소로는 못 본다.
- **적응형 비트레이트(ABR).** 화질 계단을 만들려면 계단 수만큼 인코딩해야 한다.
  2코어에서 할 일이 아니고, 지금은 화질보다 지연이 문제다.
- **LL-HLS.** LiveKit 때와 이유가 같다. 부분 세그먼트는 CMAF 를 전제하는데 우리는 TS 다.
