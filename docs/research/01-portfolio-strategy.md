## 2. 감점 요인

### 2-1. 가장 강력한 감점: "그냥요, 유명해서요"

velog 「기술 면접에서 탈락하는 개발자 유형」 1번 유형 — **대충형**

> *"그냥요... 유명해서요..."* / *"그냥.. 다 쓰길래요..."*
> 문제점: 프레임워크·라이브러리의 장단점을 설명하지 못함.
> **문제 해결 능력과 사고력이 부족해 보임.**

나머지 탈락 유형: 과묵형(사고 과정을 말 안 함) / 고집형 / **버그 경험이 없다고 답하는 유형**
— https://velog.io/@yuhyerin/기술-면접에서-탈락하는-개발자-유형

### 2-2. ★ 오버엔지니어링이 터지는 장면 — "localhost:8080의 함정"

F-Lab 「백엔드 주니어 개발자를 위한 경험담과 조언」의 면접 재현:

```
면접관: 해당 클러스터들은 어떤 환경에 구축하였나요?
지원자: 학습 목적이었으므로 로컬에 구축하였습니다.
면접관: 데이터의 크기는요?
지원자: 약 5만 건 정도였습니다.
면접관: 5만 건 정도의 데이터라면 더 쉽고 좋은 방법이 있었을 것 같은데
```

같은 글의 핵심:

> *"다양한 기술을 학습해 보려고 한 시도는 멋지지만, **자신이 갖고 있는 대안에 대해서도
> 함께 이야기한 후, '학습 목적'에서 그런 시도들을 했다고 멋지게 말할 수 있는 지원자는
> 많이 보지 못한 것 같습니다.**"*
> — https://f-lab.kr/blog/developer-experience

**해석**: 면접관은 *"왜 그걸 썼냐"* 보다 **"규모 대비 적정했냐"** 를 친다.
**오버엔지니어링 자체보다, 그게 오버엔지니어링임을 본인이 모르는 상태가 감점이다.**

### 2-3. 기술 나열 / 미담당 부분 기재

- *"강의에서 잠깐 사용해본 기술까지 나열하기보다 프로젝트에서 실제로 사용한 기술 중심으로"*,
  스킬에 상중하·별점 표기는 신뢰도 낮음
- 팀 프로젝트에서 미담당 부분까지 쓰면 꼬리질문에 답변 불가 → **"신뢰도 급격히 하락"**

### 2-4. 서류 탈락 1위는 기술 스택 불일치

원티드랩: 서류 탈락 주요 원인 = **"지원한 회사와 기술 스택이 잘 맞지 않거나"**,
이력서 3장 초과, 프로젝트 규모·기간·팀 구성·기여도 미기재
— https://brunch.co.kr/@wantedlab/43

### 2-5. "저수준 흉내"가 어떻게 읽히는가 — **근거 없음**

이를 정면으로 다룬 국내 채용 측 자료는 찾지 못했다.
**"저수준을 직접 구현했다"가 감점된다는 직접 증거도, 가점된다는 직접 증거도 없다.**

## 3. "왜 이 기술을 썼나요"를 검증하는 방식

### 3-1. 표준 3단 질문

velog 「포트폴리오와 기술 면접」:
> 1. **"왜 이거 씀? (대체제는? 언급하면서 비교.)"**
> 2. "해당 기술의 특징은?"
> 3. "해당 기술에서 중요하게 알아야 할 개념은?"

### 3-2. 실제 받은 질문 (2025 신입 백엔드 후기)

- **"JPA를 누가 사용하자고 했나요?"** ← 선택의 주체/책임
- **"JPA를 이용할 때 성능상의 단점은 없었나요?"** ← 트레이드오프 인지
- **"포트폴리오를 보니 카프카가 있는데, 왜 카프카를 사용하셨죠?"**
- (꼬리) *"크롤링을 막는 입장입니다. 어떻게 방지할 수 있을까요?"* → *"그러면 세션으로 막을 수 있을까요?"*
— https://ash-tensor.github.io/web/java/2025/03/29/backend-interview-question.html

- **"Redis를 사용하신 이유가 무엇인가요?"** / **"엘라스틱서치를 왜 사용하셨나요?"**
  / **"JWT는 왜 사용을 하셨나요?"**
- 저자 코멘트: **"모든 질문이 사용 스택과 연관"**, 스택이 겹치면 *"깊게 파고드는 경향"*
— https://velog.io/@yukina1418/최근-면접을-다니면서-받았던-질문들

### 3-3. 검증 메커니즘 요약

```
① 왜 썼나  →  ② 그 기술의 단점을 아는가  →  ③ 대안과 비교했나  →  ④ 안 썼으면 어떻게
```

②를 못 답하면 *"써봤을 뿐 이해 못 함"*, ③을 못 답하면 **2-1의 "대충형"** 으로 분류된다.

### 3-4. 답변 길이

> *"최대한 짧고 간결하게 대답해야만 유리합니다. 궁금하면 면접관님께서 꼬리질문으로
> 깊이있게 물어보실 것입니다."*

## 4. 좋은 답변의 형태

### 4-1. 핵심은 "트레이드오프의 언어"

기술 면접 플레이북:
> 면접관이 보는 신호는 **"트레이드오프 감각: '이 방법은 빠르지만 메모리를 더 씁니다' 같은
> 문장이 나오는가."**
>
> 모범 답변: *"캐시를 두면 읽기 지연은 줄지만 무효화 복잡성이 생깁니다.
> 이 서비스는 읽기가 압도적이므로 감수할 가치가 있습니다"*
>
> **"차별화되는 것은 지식의 나열이 아니라 트레이드오프의 언어"**
— https://www.youngju.dev/blog/2026-07-06-tech-interview-playbook

**답변 구조** = ① 선택지의 이점 → ② 그에 따른 비용 → ③ 우리 요구사항으로 정당화

### 4-2. 신입에게만 허용되는 "정직 카드"

F-Lab이 지적한, **대부분의 지원자가 못 하는 답변 형태**:

> *"실무 규모였다면 X가 맞았을 것 같습니다. 이 프로젝트에선 Y를 학습·검증하는 게
> 목적이어서 Y로 갔고, 대신 Z를 실측해서 근거를 남겼습니다"*

### 4-3. ADR로 문서화하라

F-Lab:
> **"현업에서는 ADR이라는 문서를 작성하기도 합니다. 이렇게 정리된 근거와 이유들은
> 나의 이력서를 빛나게 해줄 것이고, 면접장에서도 나를 돋보이게 만들어줄 것입니다."**

ADR 표준 구성: **컨텍스트 / 결정 / 근거 / 결과 / 검토했던 대안들과 선택하지 않은 이유**
— https://www.cncf.co.kr/blog/adr-guide/ , Microsoft Well-Architected

## 6. 저수준 vs 고수준 — 신입 권장 균형점

### 6-1. 라이브러리 우선 논거

> *"표준 라이브러리를 사용하면 그 코드를 작성한 전문가의 지식과 여러분보다 앞서 사용한
> 다른 프로그래머들의 경험을 활용할 수 있다"* / *"따로 노력하지 않아도 성능이 지속해서 개선된다"*

### 6-2. 가장 실용적인 한 문장

> **"문제를 해결하는 최소한의 설계를 하되, 퇴로는 열어두자."**
> 현재 필요한 최소 수준만 설계 + 나중에 바꿀 때의 **변경 비용을 미리 검토** +
> 충분한 테스트 커버리지로 퇴로 확보. *"아는 만큼 본다."*
— https://huns.me/posts/2019-09-26-overengineering-vs-underengineering

관련: YAGNI / XP의 "설계 결정 순간을 최대한 미룬다"

### 6-3. 저수준 학습 자체의 가치

> *"학습 시간의 80%는 본질적인 것에 투자하고 나머지 20%를 프레임워크나 라이브러리 등의
> 도구를 배우는 데에 투자해야"*

실무에서 *"핵심 로직을 만들거나 복잡한 문제를 해결할 때 알고리즘, 스레드와 프로세스,
스택과 힙 구조 등의 공학 이론이 큰 도움"*. 네이버 신입 공채도 CS 전형을 별도로 둔다.

### 6-4. SFU 선택에 대한 업계 통설 (LiveKit 선택의 방어 근거)

> *"팀이 작고 시간이 제한된 경우, **SFU 내부를 처음부터 구축하는 것은 피해야 한다**"*
> LiveKit: *"WebRTC 룸/SFU가 주요 관심사이고 현대적인 실시간 스택을 원할 때 최적"*
> mediasoup: *"커스텀 SFU 기반 제품을 구축하려는 경우에 최적"*

### 6-5. 종합 결론 (**추론** — 6-1~6-4의 합성)

- **구현은 고수준으로, 설명은 저수준으로.** 라이브러리를 쓰되 그 안에서 무슨 일이
  일어나는지 말로 설명할 수 있으면, **"몰라서 쓴 사람"과 완전히 구분된다.**
  §2-1의 "대충형" 판정을 피하는 유일한 방법이다.
- **직접 구현이 정당화되는 순간은 둘뿐**: ① 라이브러리로 측정된 요구사항을 못 맞출 때,
  ② 명시적 학습 목적임을 스스로 선언할 때(§4-2)
- 저수준을 **"구현"으로 증명하려 들면 5만 건 하둡 사례의 반대편에 서게 되고,
  "설명"으로 증명하면 리스크 없이 가점만 가져간다.**

## 7. 이 지원자에게 주는 권고 (우선순위)

### 1순위 — ADR을 써서 "다 알고 있으면서 골랐다"를 문서로 못 박아라

| ADR | 내용 |
|---|---|
| 001 미디어 서버 | LiveKit vs mediasoup vs Janus vs P2P Mesh vs **직접 SFU 구현** |
| 002 동시성 제어 | 비관적 락 vs 낙관적 락 vs DB 제약 vs 앱 큐 (150명 실험 근거 있음) |
| 003 외부 호출 방어 | 타임아웃 범위, 서킷 브레이커 미도입 근거 |
| 004 채팅 전송 계층 | raw WebSocket vs STOMP vs SSE vs 폴링 |
| 005 팬아웃 브로커 | Redis vs NATS vs Kafka vs 룸-서버 고정 |
| 006 Java 버전 | 17 vs 21 vs 25 |

**형식 5칸 고정: 컨텍스트 / 결정 / 근거 / 결과 / 기각한 대안과 이유**

### 2순위 — negative result를 면접 필살기로 배치하라

**"필요할 줄 알았는데 재보니 필요 없었다"는 가장 희귀한 자산이다.**

근거: (a) 요즘IT 감동 사례에서 면접관을 움직인 건 솔직함,
(b) NC소프트가 합격자 특징으로 "솔직함" 명시,
(c) F-Lab이 *"많이 보지 못했다"* 고 한 그 빈자리.

**면접 대사 템플릿**
> *"처음엔 X가 필요할 거라고 가정하고 설계했는데, k6로 재보니 병목이 거기가 아니어서
> 도입을 취소했습니다. 그 판단 기록을 남겨뒀습니다."*

이 한 문장이 **"오버엔지니어링 안 하는 사람" + "측정하는 사람" + "솔직한 사람"** 을 동시에 증명한다.

### 3순위 — WebSocket에서 "저수준 흉내"를 하지 말고 "저수준 설명"을 하라

**하지 말 것**: RFC 6455 프레임 파싱 직접 구현, 자체 프로토콜 설계, 커스텀 브로커
**할 것**: STOMP를 고르되 **왜 다른 쪽이 아닌지를 측정 또는 요구사항으로 답한다.**

**최고의 카드**: 화상강의 채팅과 라이브방송 채팅에 **다른 결정을 내리고 그 차이를 설명하는 것.**
*"같은 채팅인데 왜 다르게 만들었나요?"* 는 반드시 나오는 질문이고,
답이 준비돼 있으면 §3-1의 3단 질문을 통째로 통과한다.

**말로 설명할 수 있어야 하는 것**: HTTP Upgrade 핸드셰이크, 프레임 opcode/마스킹,
하트비트와 유휴 커넥션, 스케일아웃 시 커넥션이 노드에 고정되는 문제, 백프레셔

### 4순위 — HLS는 도메인 적합성이 가장 높은 카드. 단 인코딩을 직접 만들지 마라

근거: SBS 우대사항에 **"동영상 인코딩 및 플레이어 개발 경험자"** 명시,
iMBC에 라이브스트리밍 직무 실재, CJ ENM은 방송 이벤트/투표.
→ **미디어 업계에서 스트리밍 경험은 명시적 우대 사유다.**

범위: 세그먼트 길이 ↔ 지연 트레이드오프 측정, 플레이리스트 갱신, 캐시 헤더.
**코덱을 직접 구현하지 말 것.**

### 5순위 — iMBC 맞춤 포장

- **JD 키워드 정면 배치** — 기술 스택 첫 줄이 Java 17 / Spring Boot / MySQL
- **"닷넷 전향 의지" 답변 준비** — 거의 확정적으로 면접에서 확인하는 항목
  > *"언어보다 웹 요청 처리 모델·ORM·트랜잭션 경계가 본질이라고 생각합니다.
  > JPA에서 겪은 N+1과 self-invocation 문제는 EF Core와 ASP.NET MVC 필터에서도
  > 형태만 다르게 나타나는 문제로 알고 있어서, 전향은 학습 비용 문제라고 봅니다."*

  **→ AOP self-invocation 발견 경험이 여기서 결정적으로 쓰인다.**
  프록시 기반 AOP는 .NET에서도 동일 구조라 **"프레임워크를 넘어 원리를 아는 사람"** 의 증거가 된다.
- **운영 친화 시그널** — Toxiproxy 실험을 *"신규 기능"* 이 아니라
  **"이미 돌아가는 서비스를 안 죽게 만드는 작업"** 으로 프레이밍
- **분량** — EduMeet 중심 2~3개, 10장 내외, 기여도 % 명시, 별점 금지
