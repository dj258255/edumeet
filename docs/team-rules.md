## 우리 팀은 이런 팀입니다

**우리는 규칙을 먼저 정하고 시작하는 팀입니다.**

프로젝트 초반에 "코딩 컨벤션은 나중에", "리뷰는 여유되면"으로 미루면
마감 2주 전에 브랜치 이름이 제각각이고, 리뷰 없이 머지된 코드가 쌓이고,
결국 "누가 왜 이렇게 짰는지 모르는 코드"를 붙잡고 밤을 새우게 됩니다.
그래서 우리는 **일을 시작하기 전에 일하는 방식부터 합의**했습니다.

이 문서는 그 합의를 적어둔 것입니다.
애자일에서 말하는 **팀 워킹 어그리먼트(team working agreement)** — 팀이 함께 일하며
서로에게 무엇을 기대할 수 있는지 미리 정해두는 가이드라인 — 에 해당합니다.
([Scrum.org](https://www.scrum.org/resources/creating-team-working-agreement))

**우리 팀을 한 문장으로 요약하면**

> 막히면 30분 안에 말하고, 결정은 근거로 하고, 정한 규칙은 도구로 강제하는 팀.

**구체적으로는 이렇게 일합니다**

| 우리가 중요하게 보는 것 | 실제로 하는 일 |
| --- | --- |
| **막힌 것을 빨리 드러내기** | 30분 룰 · 데일리 스크럼에서 "막힌 것"을 필수로 말함 |
| **모든 코드는 최소 1명이 읽는다** | `master` 직접 push 금지 · PR 필수 · 24시간 내 1차 응답 |
| **취향이 아니라 근거로 결정한다** | 제안·반대 시 이유 필수 · 결정과 폐기된 대안을 이슈에 기록 |
| **성능은 느낌이 아니라 숫자로 말한다** | 쿼리 수·실행계획을 1차 지표로 · `perf` 커밋에 측정치 첨부 |
| **규칙은 사람이 아니라 도구가 지킨다** | Checkstyle · ESLint · CI · PR/이슈 템플릿 |
| **문서는 살아 있어야 한다** | 규칙이 현실과 어긋나면 회고에서 고침 |

**이 문서를 처음 보는 사람은**

1. **이 문서**를 읽는다 (우리가 왜 이렇게 일하는지)
2. [`team-convention.md`](./team-convention.md) **Part 1(공통)** 을 읽고 브랜치를 하나 파본다
3. 담당에 따라 컨벤션 **Part 2(백엔드)** 또는 **Part 3(프론트엔드)** 를 읽는다
4. 첫 PR은 작게 올린다. **첫 주에 30분 이상 막히면 그냥 물어본다. 그게 우리 규칙이다.**

## 1. 데일리 스크럼 [필수]

**매일 같은 시간, 같은 자리에서 15분 이내.**
시간이 들쭉날쭉해지면 가장 먼저 사라지는 것이 스크럼이다.

**각자 말하는 것 — 3가지**

1. 어제 한 것
2. 오늘 할 것
3. **막힌 것 / 도움이 필요한 것** ← 이게 제일 중요하다

**진행 규칙**

- **상세한 논의는 스크럼에서 하지 않는다.**
  논의가 필요한 안건이 나오면 **"추후 논의" 목록에 적어두고**, 스크럼이 끝난 뒤
  관련된 사람만 따로 모인다. 15분 안에 모든 것을 논의할 수는 없다.
- 남이 못 알아듣는 세부 구현을 말하지 않는다. **이슈 단위, 상황 단위**로 말한다.
- 막힌 것이 나오면 팀은 **"누가 도울 수 있는가"** 만 그 자리에서 정한다.
- "막힌 것 없음"이 3일 연속이면 점검한다. 진짜 없거나, 말을 못 하고 있거나 둘 중 하나다.

**진행이 안 될 때**

- 시간이 계속 초과된다 → 논의를 스크럼 밖으로 빼지 못하고 있는 것이다
- 보고회처럼 느껴진다 → 서로에게 말하는 게 아니라 한 사람에게 말하고 있는 것이다

## 2. 회의와 토론 [필수]

**회의 전**

- 안건을 미리 올린다. 안건 없는 회의는 잡지 않는다.
- 결정이 필요한 회의인지, 공유가 목적인 회의인지 명시한다.

**회의 중**

- **1인 1의견 이상.** 침묵은 동의가 아니라 정보의 손실이다.
- **제안하거나 반대할 때 붙인다** — ① 무엇을 ② 왜 ③ 대안 대비 이점 ④ 비용(시간·학습·유지보수)
- **이유 없는 거부는 의견으로 보지 않는다.** "그냥 별로"는 안건을 멈출 수 없다.
- 말이 세지면 **10분 중단하고 다시 이야기한다.** 그 자리에서 이기는 것은 목표가 아니다.
- 다루는 대상은 **코드와 결정**이다. 사람이 아니다.

**결정 방법**

- **판단 기준 우선순위** — ① 마감 내 동작 → ② 팀 전체 효율 → ③ 개인 선호
- **2인 의견이 충돌하면 당사자를 제외한 나머지 인원이 논의해 결정한다.**
- 결정된 뒤에는 **반대했던 사람도 그대로 실행한다.** 결정 순간보다 결정 이후에 팀이 깨진다.
- 결정은 **이슈에 기록한다** — 결정 내용 / 이유 / **폐기한 대안**.
  폐기 이유가 없으면 같은 논쟁을 2주 뒤에 다시 한다.

**결론이 안 나는 안건**

시간을 정해두고, 끝나면 **"기한 안에 검증할 수 있는 실험"** 으로 바꾼다.
(예: "Repository 분리 여부" → 한 도메인에만 적용해보고 다음 회고에서 판단)

## 3. 코드 리뷰 [필수]

> 기준: [Google Engineering Practices — Code Review Developer Guide](https://google.github.io/eng-practices/review/)
> ([한국어 요약](https://soojin.ro/review/)) · [우아한형제들 코드 리뷰 문화 개선 이야기](https://techblog.woowahan.com/7152/)

### 리뷰의 목적

코드 리뷰는 **검사가 아니라 코드 건강도를 유지하고 지식을 퍼뜨리는 활동**이다.
"완벽한 코드"가 기준이 아니라 **"머지되면 코드베이스가 더 나아지는가"** 가 기준이다.

### 리뷰어가 볼 것 (순서대로)

| 순서 | 항목 | 보는 것 |
| --- | --- | --- |
| 1 | **설계** | 이 변경이 이 위치에 있는 게 맞는가. 레이어 경계를 넘지 않는가 |
| 2 | **기능** | 작성자가 의도한 대로 동작하는가. 엣지 케이스·동시성은 |
| 3 | **복잡도** | 더 단순하게 할 수 있는가. **지금 필요 없는 일반화(과설계)를 하고 있지 않은가** |
| 4 | **테스트** | 적절한 테스트가 **같은 PR 안에** 있는가. 그 테스트가 실제로 무언가를 검증하는가 |
| 5 | **네이밍** | 이름만 보고 무엇인지 알 수 있는가 |
| 6 | **주석·문서** | 무엇이 아니라 **왜**를 설명하는가. Swagger·README 갱신이 필요한가 |
| 7 | 스타일 | **사람이 보지 않는다. Checkstyle / ESLint 가 본다** |

> **과설계 경계** — "나중에 필요할 것 같아서" 만든 추상화는 지금 지적한다.
> 미래의 요구사항은 실제로 도착했을 때 그 모양을 보고 풀면 된다.

### 리뷰어 규칙

- **리뷰는 개인 취향이 아니라 기술적 근거로 한다.**
  작성자가 근거를 제시했고 여러 방식이 모두 타당하면 **작성자의 선택을 존중한다.**
  근거가 없을 때만 설계 원칙과 기존 코드베이스와의 일관성을 기준으로 삼는다.
- **코멘트에 의도 수준을 붙인다.**

| 접두사 | 의미 |
| --- | --- |
| `P1:` | 반드시 반영 (머지 차단) |
| `P2:` | 반영 권장, 논의 필요 |
| `P3:` | 사소한 제안, 반영은 자유 |
| `Q:` | 단순 질문 |

- **좋은 부분은 좋다고 말한다.** 지적만 쌓이는 리뷰는 리뷰를 피하게 만든다.
- 읽기 어려워서 리뷰가 막히면 **추측하지 말고 작성자에게 설명을 요청한다.**
- 리뷰 요청 후 **24시간 이내 1차 응답.** 통과시킬 때는 `LGTM`.

### 작성자 규칙

- **PR은 작게, 자주.** (변경 파일 10개 / 300줄 이내 권장)
  큰 PR은 리뷰어가 "대충 훑고 승인"하게 만든다. 그러면 리뷰가 없는 것과 같다.
- PR 본문에 **무엇을 · 왜 · 어떻게 확인하는지**를 쓴다. (템플릿 참고)
- 반영했으면 코멘트에 답글을 달고 resolve 한다.
- **지적을 방어하지 않는다.** 동의하지 않으면 근거를 대고, 근거가 없으면 고친다.

### 의견이 갈릴 때

1. 작성자와 리뷰어가 먼저 근거를 놓고 합의를 시도한다
2. 합의가 안 되면 **PR 안에서 계속 싸우지 않고 팀 논의로 올린다** (2. 결정 방법)
3. 결정되면 이슈에 기록한다

## 4. 소통과 태도 [필수]

### 막히면 빨리 드러낸다 — 30분 룰

- 같은 문제로 **30분 이상 진전이 없으면 팀 채널에 공유한다.** 해결을 요청하지 않더라도 공유는 한다.
- 질문할 때 함께 적는다 — **① 하려던 것 ② 시도한 것과 에러 ③ 내 가설**
- 해결되면 **원인 한 줄을 채널에 남긴다.** 다음 사람이 같은 데서 안 막힌다.
- 급하지 않은 질문은 모아서 스크럼 때 한다. 서로의 몰입 시간을 지킨다.

> 학습 속도를 결정하는 것은 투입 시간이 아니라 **피드백을 받는 주기**다.
> 3시간 헤맨 뒤 받는 피드백보다 30분 만에 받는 피드백이 훨씬 많이 남는다. (『함께 자라기』)

### 실수를 다루는 방식

- **장애·실수·잘못된 머지는 즉시 공유한다.** 공유가 빠를수록 복구가 싸다.
- 원인 정리는 **"누가"가 아니라 "어떤 조건이면 누구라도 그랬을까"** 로 한다.
- 실수를 탓하면 실수가 줄지 않고 **보고가 준다.**

### 기본

- 반대할 때는 이유를 붙인다.
- 다른 사람의 의견을 무시하지 않는다. 이해가 안 되면 되묻는다.
- 말하기 전에 한 번 더 생각한다. 특히 남의 코드에 대해 말할 때.
- **출결 이슈(지각·조퇴·결석)는 확인 즉시 공유한다.** 늦는 것보다 모르고 기다리는 게 비용이다.
- 공지는 확인 후 팀 채널에 한 번 더 공유한다.

## 5. 회고와 학습

| 활동 | 주기 | 시간 | 내용 |
| --- | --- | --- | --- |
| 데일리 스크럼 | 매일 | 15분 이내 | 어제 / 오늘 / **막힌 것** |
| 회고 (KPT) | 주 1회 | 30분 | Keep · Problem · **Try는 다음 주에 실행 가능한 크기로** |
| 학습 공유 | 주 1회 | 15분 | 이번 주에 새로 안 것 1개 |
| 페어 프로그래밍 | 필요 시 | 30~60분 | 신규 기술 도입 · 난이도 높은 구현 |

- **회고에서 나온 Try 중 규칙이 된 것은 이 문서에 반영한다.** 문서가 갱신되지 않으면 회고는 대화로 끝난다.
- 규칙이 현실과 맞지 않으면 몰래 어기지 말고 **회고 안건으로 올린다.**
- 야근이 **주 2회 이상 반복되면** 의지 문제가 아니라 계획 문제로 보고 회고 안건으로 올린다.
  (마감·장애 상황에 함께 붙는 것은 별개다)

## 6. 생활 수칙

- 퇴근 전 진행 중인 작업은 원격에 push 한다. **내가 없어도 팀이 움직일 수 있어야 한다.**

## 7. 작업 흐름 체크리스트

```
이슈 등록 → 브랜치 생성 → 개발 → 셀프 리뷰 → PR → 코드 리뷰 → Squash merge → 브랜치 삭제
```

**작업 시작 전**

- [ ] 이슈를 등록했다 (템플릿 · Label)
- [ ] `master` 최신 상태에서 브랜치를 팠다
- [ ] 브랜치 이름이 `<type>/<이슈번호>-<설명>` 이다 (`#` 없이)

**PR 올리기 전**

- [ ] 커밋 메시지가 `<type>: <한국어 subject>` 형식이다
- [ ] Checkstyle / ESLint 를 통과했다
- [ ] 테스트를 작성했고 통과한다
- [ ] `perf` 작업이면 **쿼리 수 / 실행계획 개선 전후**를 본문에 넣었다
- [ ] 불필요한 주석 · 로그 · `console.log` 를 제거했다
- [ ] 셀프 리뷰를 했다
- [ ] PR 템플릿을 채웠다 (`Closes #번호` 포함)

**리뷰할 때**

- [ ] 설계 → 기능 → 복잡도 → 테스트 순으로 봤다
- [ ] 코멘트에 `P1` / `P2` / `P3` / `Q` 를 붙였다
- [ ] 24시간 내 1차 응답했다

**머지 후**

- [ ] Squash merge 커밋 메시지를 정리했다
